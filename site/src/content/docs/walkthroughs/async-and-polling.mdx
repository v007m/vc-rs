Real APIs are not always instant or reliable. A report takes a few seconds to build. A cold cache answers 503 on the first call. A dependency hangs. This walkthrough shows the tools Vibranium gives you for each case, and how they differ:

| Tool | What it repeats | When to use it |
| --- | --- | --- |
| `poll` | one call, until a check holds | waiting for an async job to finish |
| test `retry` | the whole test | a test that fails now and then; a pass after a failure is reported as **flaky** |
| `http.retry` | one request, on a network error, timeout or 5xx | a server that drops the odd request |
| `timeout` | nothing; it sets a limit | making slow calls fail fast |
| `--repeat` | every selected test, N times | finding out whether a test is flaky |

## Before you start

- `vc` is on your `PATH` (see [Install](/vc-rs/start/install/)).
- You have a clone of the Vibranium repo for the mock server. In the clone, start it with either command and leave it running:

  ```console
  $ mise run mock
  $ cargo run -p vc-mock-server -- --port 18080
  vc-mock-server listening on http://127.0.0.1:18080
  ```

  This page uses these mock endpoints:
  - `GET /poll/{id}?after=N` answers `{"status":"pending"}` until it has been called N times for that id, then `{"status":"done"}`. It also returns `attempt`, the call count.
  - `GET /flaky?key=K&failTimes=N` answers 503 to the first N calls for a key, then 200.
  - `GET /slow?ms=N` waits N milliseconds before it answers.
  - `GET /__stats` counts the requests it has seen. `POST /__reset` clears all counters.

## Build it

<Steps>

1. **Create the project.** Start with a config and one api file. `defaults.timeout` is the per-request limit. It is 30 seconds unless you set it.

   ```yaml title="vibranium.config.yaml"
   syntaxVersion: 2
   project: async-demo
   vars:
     mockUrl: http://localhost:18080
   profiles:
     - id: default
       default: true
   defaults:
     timeout: 5s
   ```

   ```yaml title="services/jobs/jobs.api.yaml"
   name: Jobs on the mock server
   baseUrl: ${var.mockUrl}
   apis:
     - id: jobStatus
       name: Read a job's status
       path: /poll/${var.jobId}
       query:
         after: 3
       expect:
         status: 200
     - id: flaky
       name: Fail the first calls for a key
       path: /flaky
       query:
         key: ${var.key}
         failTimes: ${var.failTimes}
     - id: slow
       name: Answer after a delay
       path: /slow
       query:
         ms: ${var.ms}
   ```

   <Aside type="caution">
   Path parameters are templates: write `/poll/${var.jobId}`. An OpenAPI-style `/poll/{jobId}` passes `vc check` but is sent as the literal text `{jobId}`.
   </Aside>

2. **Poll until the job is done.** `poll` sends the same call again and again until its `until` checks hold. `every` is the pause between calls, and `timeout` is how long to keep trying. All three are required. Once `until` holds, the test's `expect` is checked against that last response.

   ```yaml title="services/jobs/polling.test.yaml"
   name: Polling
   tests:
     - id: waitsForJobToFinish
       name: Waits until the job is done
       call: jobs#jobStatus
       vars:
         jobId: export-1
       poll:
         until:
           body:
             match:
               status: done
         every: 200ms
         timeout: 5s
       expect:
         body:
           match:
             attempt: 3
   ```

   ```console
   $ curl -s -X POST localhost:18080/__reset
   $ vc run jobs.polling
   plan  1 test in 1 file · profile default

   ✓ jobs.polling#waitsForJobToFinish                              412ms

   1 passed                                                     419ms · profile default
   reports  /home/you/async-demo/.vibranium/reports/1/ctrf.json
   $ curl -s localhost:18080/__stats
   {"requests":{"GET /poll/{id}":3},"logins":0,"maxInFlight":{"GET /poll/{id}":1},"maxInFlightTotal":1}
   ```

   Three calls, 200 ms apart: two `pending`, then `done`.

   `until` uses the same checks as `expect`, so you can wait on a status or a header too. Leave out `every` and `vc check` tells you:

   ```console
   error[V1005]: a poll needs `every`
    --> services/jobs/polling.test.yaml:9:7
     |
   9 |       until:
     |       ^^^^^ `every` is missing
     = help: add `every: 2s`: Pause between calls
   ```

3. **See a poll give up.** Add a test whose job never finishes in time. The test's `query` replaces the api's `after: 3` with `after: 100`.

   ```yaml title="services/jobs/polling.test.yaml (add)"
     - id: givesUpOnStuckJob
       name: Gives up when the job never finishes
       call: jobs#jobStatus
       vars:
         jobId: stuck-1
       query:
         after: 100
       poll:
         until:
           body:
             match:
               status: done
         every: 250ms
         timeout: 1s
   ```

   ```console
   $ curl -s -X POST localhost:18080/__reset
   $ vc run jobs.polling
   plan  2 tests in 1 file · profile default

   ✓ jobs.polling#waitsForJobToFinish                              408ms
   ✕ jobs.polling#givesUpOnStuckJob                                760ms
     error[V5104]: `poll.until` did not hold within 1s: match.status: expected "done", got "pending"
        = at: call jobs#jobStatus

   1 passed · 1 failed                                          761ms · profile default
   reports  /home/you/async-demo/.vibranium/reports/2/ctrf.json
   next     vc run --failed
   seed 605022505046727078: pass `--seed 605022505046727078` to run with the same generated data
   ```

   The failure shows the last value it saw. vc called at 0, 250, 500 and 750 ms, and stopped there because the next call would land past the 1 s limit.

4. **Retry a flaky test.** `retry` on a test re-runs the whole test after a failure, including its cleanups. `attempts` is the number of extra tries, and `delay` is the pause before each one. A test that fails and then passes is reported as **flaky**, not passed.

   ```yaml title="services/jobs/retry.test.yaml"
   name: Retries
   tests:
     - id: passesOnSecondTry
       name: Passes when the second try succeeds
       call: jobs#flaky
       vars:
         key: test-retry
         failTimes: 1
       retry:
         attempts: 2
         delay: 100ms
       expect:
         status: 200
   ```

   ```console
   $ curl -s -X POST localhost:18080/__reset
   $ vc run jobs.retry
   plan  1 test in 1 file · profile default

   ~ jobs.retry#passesOnSecondTry flaky (2 attempts)               106ms

   0 passed · 1 flaky                                           108ms · profile default
   reports  /home/you/async-demo/.vibranium/reports/3/ctrf.json
   $ echo $?
   0
   ```

   A flaky test still counts as a pass for the exit code, so CI stays green, but the report keeps a record of it. With `failTimes: 2` the line reads `flaky (3 attempts)`. When every try fails, the test fails and you get the error from each try.

   To give every test the same retry, set `defaults.retry` in the config. A test's own `retry` wins.

5. **Hunt flakiness with `--repeat`.** A test that passes once can still be flaky. `--repeat N` runs every selected test N times, in place of its own `repeat`, and reports each run. Add a test with no `retry`:

   ```yaml title="services/jobs/retry.test.yaml (add)"
     - id: readsWarmCache
       name: Reads from a warm cache
       call: jobs#flaky
       vars:
         key: warm-cache
         failTimes: 3
       expect:
         status: 200
   ```

   Run it once (it fails), then ten more times:

   ```console
   $ vc run jobs.retry#readsWarmCache --repeat 10
   plan  1 test in 1 file · profile default

   ✕ jobs.retry#readsWarmCache [repeat 3]                            7ms
     error[V5101]: expect.status
       --> services/jobs/retry.test.yaml:21:15
        |
     21 |       status: 200
        |               ^^^ expected [200], got 503
   ✕ jobs.retry#readsWarmCache [repeat 5]                            8ms
     error[V5101]: expect.status
       --> services/jobs/retry.test.yaml:21:15
        |
     21 |       status: 200
        |               ^^^ expected [200], got 503
   ✓ jobs.retry#readsWarmCache [repeat 10]                           9ms
   ✓ jobs.retry#readsWarmCache [repeat 2]                            9ms
   ✓ jobs.retry#readsWarmCache [repeat 6]                           10ms
   ✓ jobs.retry#readsWarmCache [repeat 8]                           10ms
   ✓ jobs.retry#readsWarmCache [repeat 7]                           10ms
   ✓ jobs.retry#readsWarmCache                                      10ms
   ✓ jobs.retry#readsWarmCache [repeat 9]                           10ms
   ✓ jobs.retry#readsWarmCache [repeat 4]                           11ms

   8 passed · 2 failed                                          13ms · profile default
   reports  /home/you/async-demo/.vibranium/reports/5/ctrf.json
   next     vc run --failed
   seed 12003489792329356816: pass `--seed 12003489792329356816` to run with the same generated data
   ```

   Two of ten failed: the test is flaky. The runs go in parallel, so they finish in any order. Add `--concurrency 1` to run them one after another.

6. **Retry single requests with `http.retry`.** Sometimes the test is fine and the network is not. `http.retry` re-sends one request, without re-running the test, when the request fails to connect, times out, or gets one of the listed statuses. It is off by default (`attempts: 0`). Add it to the config:

   ```yaml title="vibranium.config.yaml (add)"
   http:
     retry:
       attempts: 2
       on: [connect, timeout, 503]
       backoff:
         base: 100ms
         max: 1s
   ```

   `backoff` grows the wait between tries, starting at `base` and never past `max`. Now a call that gets two 503s in a row still passes:

   ```yaml title="services/jobs/transport.test.yaml"
   name: Transport retries
   tests:
     - id: survivesTwoUnavailableAnswers
       name: Survives two 503 answers in a row
       call: jobs#flaky
       vars:
         key: transport
         failTimes: 2
       expect:
         status: 200
         body:
           match:
             attempt: 3
   ```

   ```console
   $ curl -s -X POST localhost:18080/__reset
   $ vc run jobs.transport
   plan  1 test in 1 file · profile default

   ✓ jobs.transport#survivesTwoUnavailableAnswers                  275ms

   1 passed                                                     276ms · profile default
   reports  /home/you/async-demo/.vibranium/reports/6/ctrf.json
   $ curl -s localhost:18080/__stats
   {"requests":{"GET /flaky":3},"logins":0,"maxInFlight":{"GET /flaky":1},"maxInFlightTotal":1}
   ```

   The server saw three requests, but the test is a plain pass, not flaky. That is the difference from a test `retry`.

   It also means `passesOnSecondTry` is now a plain pass, because `http.retry` absorbs its 503 first:

   ```console
   $ vc run jobs.retry#passesOnSecondTry
   plan  1 test in 1 file · profile default

   ✓ jobs.retry#passesOnSecondTry                                   83ms

   1 passed                                                     85ms · profile default
   reports  /home/you/async-demo/.vibranium/reports/7/ctrf.json
   ```

   To turn transport retries off for one api, give it its own `http.retry`. Keys set on an api replace the config's. Add a second flaky api and point both tests in `retry.test.yaml` at it:

   ```yaml title="services/jobs/jobs.api.yaml (add)"
     - id: flakyNoRetry
       name: Fail the first calls, with no transport retry
       path: /flaky
       query:
         key: ${var.key}
         failTimes: ${var.failTimes}
       http:
         retry:
           attempts: 0
   ```

   ```console
   $ curl -s -X POST localhost:18080/__reset
   $ vc run jobs.retry#passesOnSecondTry jobs.transport
   plan  2 tests in 2 files · profile default

   ~ jobs.retry#passesOnSecondTry flaky (2 attempts)               105ms
   ✓ jobs.transport#survivesTwoUnavailableAnswers                  186ms

   1 passed · 1 flaky                                           187ms · profile default
   reports  /home/you/async-demo/.vibranium/reports/8/ctrf.json
   ```

   <Aside type="note" title="Only safe methods are retried">
   By default `http.retry` re-sends only `GET`, `HEAD`, `OPTIONS`, `PUT` and `DELETE`. A `POST` is sent once, because sending it twice could create two orders. List it in `methods` if your API makes `POST` safe to repeat.
   </Aside>

7. **Set timeouts.** There are two kinds:
   - `timeout` on a **test** limits the whole test, for each attempt.
   - `timeout` on an **action** (a `call` step here) limits each request attempt of that call. It wins over the api's `timeout` and `defaults.timeout`.

   ```yaml title="services/jobs/timeouts.test.yaml"
   name: Timeouts
   tests:
     - id: finishesReportInTime
       name: Builds the report within a second
       call: jobs#slow
       vars:
         ms: 1500
       timeout: 1s
     - id: answersHealthCheckQuickly
       name: Answers a quick check within 300ms
       steps:
         - call: jobs#slow
           vars:
             ms: 100
           timeout: 300ms
         - call: jobs#slow
           vars:
             ms: 600
           timeout: 300ms
   ```

   ```console
   $ curl -s -X POST localhost:18080/__reset
   $ vc run jobs.timeouts
   plan  2 tests in 1 file · profile default

   ✕ jobs.timeouts#finishesReportInTime                             1.0s
     error[V5104]: the test ran past its `timeout`
        = at: call jobs#slow
   ✕ jobs.timeouts#answersHealthCheckQuickly                        1.2s
     error[V5104]: no response within 300ms
        = at: call jobs#slow

   0 passed · 2 failed                                          1.2s · profile default
   reports  /home/you/async-demo/.vibranium/reports/9/ctrf.json
   next     vc run --failed
   seed 2594348556432023605: pass `--seed 2594348556432023605` to run with the same generated data
   $ curl -s localhost:18080/__stats
   {"requests":{"GET /slow":5},"logins":0,"maxInFlight":{"GET /slow":2},"maxInFlightTotal":2}
   ```

   Why five requests and 1.2 s? `http.retry` lists `timeout` in `on`, so the 600 ms call was tried three times, 300 ms each, with backoff in between. Each attempt gets the full timeout. The test-level timeout is not a request timeout, so `finishesReportInTime` was sent only once.

</Steps>

## What you learned

- `poll` repeats one call until `until` holds. `every` and `timeout` are required, and a poll that runs out of time fails with V5104.
- Test `retry` re-runs the whole test. `attempts` counts the extra tries. A pass after a failure is **flaky**, which still exits 0.
- `http.retry` re-sends one request on a connection error, a timeout or a listed status, with backoff. It is off by default, skips `POST` unless you list it, and can be changed per api.
- A test `timeout` limits the whole test. An action `timeout` limits each request attempt of that call.
- `vc run --repeat N` runs a test N times so a flaky one shows itself.
