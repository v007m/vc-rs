In this walkthrough you define one of each auth type in the config, then point your apis and tests at them. You run them against the demo service that ships with vc. It echoes your request back, and it has real sign-in routes.

By the end you will know how to:

- keep secrets out of your YAML with `.env.schema` and `.env`
- use `bearer`, `basic`, `apiKey` (in a header and in the query) and `oauth2ClientCredentials`
- write a multi-step `flow` login with `apply`, `expiresIn` and `refreshOn`
- confirm that a token is fetched once per run, not once per call
- override auth for one test, or turn it off with `auth: none`

<Aside type="caution" title="Needs the demo from master">
This page uses `vc demo` routes that are newer than v0.1.0: `/auth/token`, `/auth/me`, `/auth/logout` and `/oauth/token`. Until the next release, install `vc` and `vc-demo` from `master`: `brew install --HEAD v007m/tap/vibranium` (see [Homebrew](/vc-rs/start/install/#homebrew)), or `cargo install --git https://github.com/v007m/vc-rs vc-cli vc-demo --locked` (see [Cargo](/vc-rs/start/install/#cargo)).
</Aside>

## Before you start

- `vc` and `vc-demo` are on your `PATH` (see [Install](/vc-rs/start/install/)).
- The demo is running. Start it in the background and leave it running:

  ```console
  $ vc demo start --detach
  demo running on http://localhost:7421 (pid 61554); `vc demo stop` stops it
  ```

  It has a few routes this page uses (all of them are in [`vc demo`](/vc-rs/reference/cli/demo/#what-it-serves)):
  - `/echo` answers with the method, path, query, headers and body it received.
  - `POST /auth/token` hands out a token, `demo-token-1`, then `demo-token-2`, and so on.
  - `POST /oauth/token` is an OAuth2 token endpoint. It accepts the client `vc-client` with the secret `vc-secret` in HTTP basic auth.
  - `GET /auth/me` returns 200 for a valid token and 401 otherwise.
  - `POST /auth/logout` revokes the token it is sent.

## Build it

<Steps>

1. **Create the project.** Make an empty folder with a config file. The var holds the demo's base URL.

   ```yaml title="vibranium.config.yaml"
   syntaxVersion: 2
   project: auth-demo
   vars:
     demoUrl: http://localhost:7421
   profiles:
     - id: default
       default: true
   secrets:
     provider: env
     schema: .env.schema
   ```

   The `secrets` block shown here is the default. You can leave it out.

2. **Declare your secrets.** List every secret name in `.env.schema`, one `NAME=` line each. This file holds names only, never values, and you commit it.

   ```text title=".env.schema"
   # The secret names this project uses, one NAME= line each, never their values.
   API_TOKEN=
   CLIENT_PASSWORD=
   SHOP_API_KEY=
   OAUTH_CLIENT_SECRET=
   ```

   Put the values in `.env`. Vibranium reads the process environment first. `.env` fills in any name the environment does not set.

   ```text title=".env"
   API_TOKEN=s3cr3t-bearer-token
   CLIENT_PASSWORD=vc-secret
   SHOP_API_KEY=key-0123456789
   OAUTH_CLIENT_SECRET=vc-secret
   ```

   <Aside type="caution" title="Keep .env out of git">
   `vc init` lists `.vibranium/` (run history and reports) and `.env` in `.gitignore`. If your project was not made by `vc init`, add them yourself:

   ```console
   $ printf '.vibranium/\n.env\n' >> .gitignore
   ```
   </Aside>

3. **Add the simple auth types.** Each entry in the config's `auth` list has an `id` and a `type`. Apis and tests refer to it by `id`. Add this to the end of the config:

   ```yaml title="vibranium.config.yaml (part)"
   auth:
     - id: apiBearer
       type: bearer
       token: ${secret.API_TOKEN}

     - id: clientBasic
       type: basic
       vars:
         user: vc-client
       username: ${var.user}
       password: ${secret.CLIENT_PASSWORD}

     - id: headerKey
       type: apiKey
       in: header
       name: x-api-key
       value: ${secret.SHOP_API_KEY}

     - id: queryKey
       type: apiKey
       in: query
       name: api_key
       value: ${secret.SHOP_API_KEY}
   ```

   `clientBasic` has its own `vars`. A caller can change them, so one definition can sign in as different users.

   `vc check` makes sure each `${secret.X}` you use is declared in `.env.schema`. A typo fails the check and suggests the closest name. Write `${secret.SHOP_APIKEY}` in `headerKey` and run it:

   ```console
   $ vc check
   error[V2106]: `${secret.SHOP_APIKEY}` is not declared in `.env.schema`
     --> vibranium.config.yaml:27:12
      |
   27 |     value: ${secret.SHOP_APIKEY}
      |            ^^^^^^^^^^^^^^^^^^^^^ SHOP_APIKEY is not in .env.schema
      = help: add the line `SHOP_APIKEY=` to `.env.schema` at the project root, or fix the name
      = help: did you mean `SHOP_API_KEY`?
      = fix: Replace with SHOP_API_KEY (certain)

   1 error · 0 warnings · 1 file checked
   ```

   Put the name back to `SHOP_API_KEY` before you go on.

4. **Write the apis and tests.** An api picks its auth with `auth:`. A test can override it in three ways: with another auth `id`, with the same `id` and different `vars`, or with `auth: none`. `echo` shows what was sent; `token` is a real basic-auth check, since the demo hands out a token only to `vc-client` with the right password.

   ```yaml title="services/demo/demo.api.yaml"
   name: The demo's echo and OAuth2 token routes
   baseUrl: ${var.demoUrl}

   apis:
     - id: echo
       name: Echoes the whole request
       path: /echo

     - id: token
       name: Hands a token to the client vc-client
       method: POST
       path: /oauth/token
       auth: clientBasic
       headers:
         content-type: application/x-www-form-urlencoded
       body:
         grant_type: client_credentials
   ```

   ```yaml title="services/demo/auth.test.yaml"
   name: Auth schemes against the demo

   tests:
     - id: sendsBearerToken
       name: Sends the bearer token
       call: demo#echo
       auth: apiBearer
       expect:
         status: 200
         body:
           match:
             headers.authorization:
               startsWith: "Bearer "

     - id: logsInWithBasicAuth
       name: Logs in with HTTP basic auth
       call: demo#token
       expect:
         status: 200
         body:
           match:
             token_type: Bearer

     - id: rejectsWrongUser
       name: Rejects basic auth for another user
       call: demo#token
       auth:
         id: clientBasic
         vars:
           user: someone
       expect:
         status: 401

     - id: sendsKeyInHeader
       name: Sends the API key in a header
       call: demo#echo
       auth: headerKey
       expect:
         body:
           match:
             headers.x-api-key:
               exists: true

     - id: sendsKeyInQuery
       name: Sends the API key in the query string
       call: demo#echo
       auth: queryKey
       expect:
         body:
           match:
             query.api_key:
               exists: true

     - id: rejectsMissingCredentials
       name: Rejects a token request without credentials
       call: demo#token
       auth: none
       expect:
         status: 401
   ```

   The `content-type` header makes vc send the body as a form, `grant_type=client_credentials`. Run the file:

   ```console
   $ vc run demo.auth
   plan  6 tests in 1 file · profile default

   Auth schemes against the demo
   ✓ demo.auth#rejectsMissingCredentials — Rejects a token request without credentials   16ms
   ✓ demo.auth#sendsKeyInHeader — Sends the API key in a header     16ms
   ✓ demo.auth#sendsBearerToken — Sends the bearer token            16ms
   ✓ demo.auth#logsInWithBasicAuth — Logs in with HTTP basic auth   18ms
   ✓ demo.auth#sendsKeyInQuery — Sends the API key in the query string   19ms
   ✓ demo.auth#rejectsWrongUser — Rejects basic auth for another user   25ms

   6 passed                                                     28ms · profile default
   reports  /home/you/auth-demo/.vibranium/reports/1/ctrf.json
   ```

   `rejectsWrongUser` sends `someone` instead of `vc-client`, so the demo answers 401. `rejectsMissingCredentials` sends no `Authorization` header at all.

   To see the resolved request for a test without sending it, use `vc explain`:

   ```console
   $ vc explain demo.auth#rejectsWrongUser
   demo.auth#rejectsWrongUser  Rejects basic auth for another user
   profile  default
   call demo#token
     POST http://localhost:7421/oauth/token
     vars
       demoUrl  http://localhost:7421  (vibranium.config.yaml)
     headers
       content-type  application/x-www-form-urlencoded  (api demo#token)

       status: 401  (test demo.auth#rejectsWrongUser)
   ```

   The `auth` line names the auth in effect and the level that chose it: `(call)` is the test's own `auth:`. For `logsInWithBasicAuth` it reads `(api demo#token)`. It does not list the `vars` the test passes to the auth, so `user: someone` is not shown.

5. **Add token-based auth.** Real APIs usually make you fetch a token first. Add two more entries to the config's `auth` list.

   ```yaml title="vibranium.config.yaml (part)"
     - id: demoOauth
       type: oauth2ClientCredentials
       tokenUrl: ${var.demoUrl}/oauth/token
       clientId: vc-client
       clientSecret: ${secret.OAUTH_CLIENT_SECRET}
       scopes: [users.read]

     - id: demoLogin
       type: flow
       vars:
         lifetime: 60          # a default; the login step saves the real value
       steps:
         - id: login
           method: POST
           url: ${var.demoUrl}/auth/token
           expect:
             status: 200
           save:
             accessToken: ${response.body.access_token}
             lifetime: ${response.body.expires_in | int}
       apply:
         headers:
           authorization: Bearer ${var.accessToken}
       expiresIn: ${var.lifetime}s
       refreshOn: [401]
   ```

   - `oauth2ClientCredentials` posts the client ID and secret to `tokenUrl` and sends the token it gets back as a bearer token.
   - `flow` is for any other login. Its `steps` are ordinary requests, and their `save` values become vars. `apply` says what to add to each request that uses the flow. `expiresIn` says when to log in again. `refreshOn` lists the statuses that mean "the token is no longer good": on one of them, vc logs in again and retries the request once.

   `expiresIn` and `apply` both see what the steps save, so `vc check` needs no default for `lifetime`. The one in the flow's `vars` is kept as documentation: the value the login step saves replaces it when the flow runs.

6. **Call the signed-in routes with them.** Here the whole api file uses `demoLogin`, and one api overrides it with `demoOauth`. Each test runs three times with `repeat: 3`.

   ```yaml title="services/account/account.api.yaml"
   name: The demo's signed-in routes
   baseUrl: ${var.demoUrl}
   auth: demoLogin

   apis:
     - id: me
       name: Who am I
       path: /auth/me

     - id: meWithOauth
       name: Who am I, with an OAuth2 client-credentials token
       path: /auth/me
       auth: demoOauth

     - id: logout
       name: Signs out, which revokes the token
       method: POST
       path: /auth/logout
       expect:
         status: 204
   ```

   ```yaml title="services/account/session.test.yaml"
   name: Signed-in calls against the demo

   tests:
     - id: readsProfileAfterLogin
       name: Reads the profile after a flow login
       call: account#me
       repeat: 3
       expect:
         status: 200
         body:
           match:
             user: demo

     - id: readsProfileWithOauth
       name: Reads the profile with a client-credentials token
       call: account#meWithOauth
       repeat: 3
       expect:
         status: 200

     - id: rejectsAnonymousCaller
       name: Rejects a caller with no token
       call: account#me
       auth: none
       expect:
         status: 401
   ```

   The demo numbers its tokens from one counter, so asking it for a token before and after the run shows how many the run took. The counter runs for the demo's whole life: a freshly started demo shows the numbers on this page, and one that has run for a while shows higher ones. For matching output, restart it first with `vc demo stop && vc demo start --detach`.

   ```console
   ✓ account.session#readsProfileAfterLogin [repeat 3] — Reads the profile after a flow login    5ms
   ✓ account.session#readsProfileAfterLogin [repeat 1] — Reads the profile after a flow login    8ms
   ✓ account.session#readsProfileWithOauth [repeat 2] — Reads the profile with a client-credentials token    8ms
   ✓ account.session#readsProfileWithOauth [repeat 3] — Reads the profile with a client-credentials token    8ms

   $ curl -s -X POST localhost:7421/auth/token
   {"access_token":"demo-token-5","expires_in":3600,"token_type":"Bearer"}
   ```

   Six signed-in calls to `/auth/me`, but only two tokens, `demo-token-3` and `demo-token-4`: one from the `demoLogin` flow and one from `/oauth/token`. It runs again only when `expiresIn` passes or a response matches `refreshOn`.

7. **Watch `refreshOn` log in again.** `POST /auth/logout` revokes the token it is sent, just as a session ends on a real server. This test calls `/auth/me`, signs out with the cached token, and expects the next call to pass anyway.

   ```yaml title="services/account/refresh.test.yaml"
   name: Token refresh
   tests:
     - id: logsInAgainAfterLogout
       name: Signs in again once the token is revoked
       steps:
         - call: account#me
         - call: account#logout
         - call: account#me
           expect:
             status: 200
   ```


9. **Know the common failures.** If a declared secret has no value (it is in `.env.schema` but in neither the environment nor `.env`), vc stops before it plans the run. Take the `OAUTH_CLIENT_SECRET` line out of `.env` and run everything:

   ```console
   $ vc run
   error: secrets: V5114: the declared secret `OAUTH_CLIENT_SECRET` has no value
     = help: set it in the environment or the project's `.env` (or in the `secrets.provider`), or remove it from `.env.schema`
   $ echo $?
   2
   ```

   No test ran, not even the `demo.auth` ones that don't need it. Before it sends anything, vc checks that every declared secret the selected tests read has a value, so a run never fails halfway for want of one. A run stopped this way writes no report. A selection that does not read the secret runs as usual, and takes the next report number, 6 (the stopped run took none):

   ```console
   $ vc run demo.auth
   plan  6 tests in 1 file · profile default

   Auth schemes against the demo
   ✓ demo.auth#sendsBearerToken — Sends the bearer token            15ms
   ✓ demo.auth#sendsKeyInQuery — Sends the API key in the query string   17ms
   ✓ demo.auth#rejectsMissingCredentials — Rejects a token request without credentials   20ms
   ✓ demo.auth#sendsKeyInHeader — Sends the API key in a header     23ms
   ✓ demo.auth#logsInWithBasicAuth — Logs in with HTTP basic auth   22ms
   ✓ demo.auth#rejectsWrongUser — Rejects basic auth for another user   30ms

   6 passed                                                     37ms · profile default
   reports  /home/you/auth-demo/.vibranium/reports/6/ctrf.json
   ```

   `vc check` reads no secret values, so it still reports `0 errors`.

   If some runs can do without a secret, mark it `# @optional` in `.env.schema`, on the line just above its name (see [`.env.schema`](/vc-rs/reference/config/env-schema/)):

   ```text title=".env.schema"
   # The secret names this project uses, one NAME= line each, never their values.
   API_TOKEN=
   CLIENT_PASSWORD=
   SHOP_API_KEY=
   # @optional
   OAUTH_CLIENT_SECRET=
   ```

   If the value is there but wrong, the token endpoint refuses it. vc names the auth and the status, but never the request or response, so nothing secret leaks:

   ```console
   error[V5114]: credentials could not be obtained: the token endpoint for `demoOauth` answered 401
      = at: call account#meWithOauth
   ```

   A failed login is kept for the rest of the run, so your tests don't each retry it and lock the account. When you are done, `vc demo stop` stops the demo.

## What you learned

- Secret names go in `.env.schema`, which you commit. Values go in the environment or `.env`, which you don't. `vc check` catches an undeclared name (V2106).
- Auth is defined once in the config and picked by `id` on an api file, an api or a test. A test can pass different `vars`, choose another `id`, or send nothing with `auth: none`.
- `oauth2ClientCredentials` and `flow` fetch a token once per run and share it. `expiresIn` and `refreshOn` decide when to fetch a new one.
- Secrets and tokens show as `••••` in the console, reports and history.
