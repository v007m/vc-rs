**Goal:** turn an OpenAPI spec into api and test files, check responses against the spec's schemas, then follow the spec as it changes. `vc sync` merges each new version of the spec into your files and keeps your edits. In CI, `vc sync --check` fails the build when the spec has drifted.

## Prerequisites

- `vc` on your `PATH` (see [Install](/vc-rs/start/install/)).
- `git`. The snapshot that `vc sync` merges against is a file you commit.
- The mock server from a clone of the repo. It serves a users API, plus that API's spec at `/openapi/users.yaml`. The spec comes in two versions, so you can watch it change. Start it in its own terminal:

  ```console
  $ git clone https://github.com/v007m/vc-rs && cd vc-rs
  $ mise run mock
  ```

  Without mise, run `cargo run -p vc-mock-server -- --port 18080`. Either way it listens on `http://localhost:18080` and serves version 1 of the spec.

## Import, test, follow the spec

<Steps>
1. **Create a project.** Start without the sample service, and put it under git.

   ```console
   $ mkdir users-api && cd users-api
   $ vc init --no-sample
   ✓ created a Vibranium project in /home/you/users-api
     .env.schema
     .gitignore
     vibranium.config.yaml
     schemas/  datasets/  hooks/  openapi/  load/
   next: vc new api <service>#<id> --path /…
   $ git init
   ```

2. **Import the spec.** `--id users` names the api file. `--tests` writes one happy-path test per operation, which creates the user a `GET` or `DELETE` needs first and checks the response against the snapshot's schema. `--negative` adds a test with a row per body field the schema rejects. `--auth` adds a test per secured operation that expects `401` without credentials.

   ```console
   $ vc import openapi http://localhost:18080/openapi/users.yaml --id users --tests --negative --auth
   ✓ imported http://localhost:18080/openapi/users.yaml
   ```

   The import writes three files and adds one var:

   | File | What it holds |
   | --- | --- |
   | `services/users/users.api.yaml` | One api per operation, with `source.openapi` pointing back at the spec |
   | `services/users/openapi.test.yaml` | The generated tests (file ID `users.openapi`) |
   | `openapi/users.yaml` | A snapshot of the spec, converted to OpenAPI 3.1. `vc sync` merges against it. Commit it, and do not edit it |
   | `vibranium.config.yaml` | Gains `usersUrl: http://localhost:18080` under `vars` |

   Each api keeps its `operationId`. That is how `vc sync` matches an api to its operation later.

   ```yaml title="services/users/users.api.yaml (as imported)"
   id: users
   name: Users
   baseUrl: ${var.usersUrl}
   source:
     openapi: http://localhost:18080/openapi/users.yaml

   apis:
     - id: listUsers
       name: List users
       path: /users
       operationId: listUsers
     - id: createUser
       name: Create user
       method: POST
       path: /users
       vars:
         email: ada@example.com
         name: Ada
       body:
         email: ${var.email}
         name: ${var.name}
       operationId: createUser
     - id: getUser
       name: Get user
       path: /users/${var.id}
       vars:
         id: ${fake.number.int(1, 100)}
       operationId: getUser
     - id: deleteUser
       name: Delete user
       method: DELETE
       path: /users/${var.id}
       vars:
         id: ${fake.number.int(1, 100)}
       operationId: deleteUser
   ```

   The body and vars come from the spec's examples. The users spec has no security schemes, so `--auth` added nothing here. On a secured spec, such as the public Petstore (`vc import openapi https://petstore3.swagger.io/api/v3/openapi.json --id petstore --tests --auth`), it writes tests such as `rejectsFindPetsByStatusWithoutAuth`, which call the api with `auth: none` and expect `401`.

   ```console
     27 |       status: 200
        |               ^^^ expected [200], got 404

   2 passed · 3 failed                                          9ms · profile default
   reports  /home/you/users-api/.vibranium/reports/1/{ctrf.json,junit.xml,index.html}
   next     vc run --failed
   seed 9565021513075289666: pass `--seed 9565021513075289666` to run with the same generated data
   ```

   `getsUser` and `deletesUser` ask for a random user ID between 1 and 100, and no such user exists yet. `rejectsCreateUserWithoutEmail` expects a `400`, but the mock stores any JSON you send it.

4. **Give the tests a user to work on.** In the api file, make `createUser` save the new ID and delete the user again when the test ends. Let `deleteUser` accept a `404`, so the cleanup does not fail when a test already deleted that user.

   ```yaml title="services/users/users.api.yaml"
     - id: createUser
       # ...
       expect:
         status: 201
       save:
         userId: ${response.body.id}
       cleanup:
         call: deleteUser
         vars:
           id: ${response.body.id}
     # ...
     - id: deleteUser
       # ...
       expect:
         status: [204, 404]
   ```

   In the test file, have `getsUser` and `deletesUser` create a user first and use its ID:

   ```yaml title="services/users/openapi.test.yaml"
     - id: getsUser
       name: Get user returns 200
       before:
         - call: users#createUser
       call: users#getUser
       vars:
         id: ${var.userId}
       expect:
         status: 200
   ```

   Do the same for `deletesUser`.

5. **Skip the test the mock cannot pass.** `vc skip` writes a `skip:` reason into the file, so the test still shows up in every report.

   ```console
   $ vc skip users.openapi#rejectsCreateUserWithoutEmail --reason "the mock accepts any body; re-enable against the real service"
   ✓ skipped users.openapi#rejectsCreateUserWithoutEmail: the mock accepts any body; re-enable against the real service
   ```

6. **Check the response against the spec's schema.** `expect.body.schema` takes a `$file`. A JSON pointer after `#` picks one schema inside the file, so you can point straight into the snapshot:

   ```yaml title="services/users/openapi.test.yaml"
       expect:
         status: 200
         body:
           schema:
             $file: ../../openapi/users.yaml#/components/schemas/User
           match:
             email: ada@example.com
   ```

   The path is relative to the test file. When `vc sync` updates the snapshot, this check follows the new schema without any edit from you.

   ```console
   $ vc run
   plan  4 tests in 1 file · 1 skipped · profile default

   - users.openapi#rejectsCreateUserWithoutEmail skipped: the mock accepts any body; re-enable against the real service
   ✓ users.openapi#listsUsers                                       50ms
   ✓ users.openapi#getsUser                                         65ms
   ✓ users.openapi#createsUser                                      65ms
   ✓ users.openapi#deletesUser                                      65ms

   4 passed · 1 skipped                                         72ms · profile default
   reports  /home/you/users-api/.vibranium/reports/3/{ctrf.json,junit.xml,index.html}
   ```

   Commit everything, the snapshot included: `git add -A && git commit -m "import users api"`.

7. **Change the spec.** The mock can switch to version 2 of its spec. It adds a `limit` query parameter to `listUsers`, a `PATCH /users/{id}` operation and a `role` field on users. It also drops `DELETE /users/{id}`.

   ```console
   $ curl -X POST http://localhost:18080/__openapi/users/v2
   ```

   (`curl -X POST http://localhost:18080/__openapi/users/v1` switches back.)

8. **Detect the drift.** `vc sync --check` fetches the spec, compares it with the snapshot and writes nothing. It exits with code `4` when something changed. That is the check to run in CI.

   ```console
   $ vc sync --check
   fetched http://localhost:18080/openapi/users.yaml (4 operations)
     ↑ users#listUsers query limit none → ${var.limit}
     + users#updateUser new operation PATCH /users/${var.id}
     - users#deleteUser removed from the spec: kept, marked deprecated
   $ echo $?
   4
   ```

   ```console
   +      limit: 20

   @@ -45,3 +49,18 @@

          status: [204, 404]

   +      id: ${fake.number.int(1, 100)}
   +      name: Ada
   +    headers:
   +      content-type: application/merge-patch+json
   +    body:
   +      email: ${var.email}
   ```

   Your `expect`, `save` and `cleanup` edits are not touched. Sync owns only the parts the spec decides: the method, the path, the query and the content type. It adds apis for new operations. It never deletes an api.

10. **Sync.**

11. **Pin down the new field with your own schema.** The spec's `User` schema lists `role` but does not require it. If your clients rely on `role`, write a stricter schema of your own:

    ```json title="schemas/users/user.json"
    {
      "$schema": "https://json-schema.org/draft/2020-12/schema",
      "type": "object",
      "required": ["id", "name", "email", "role"],
      "properties": {
        "id": { "type": "integer", "exclusiveMinimum": 0 },
        "name": { "type": "string" },
        "email": { "type": "string", "format": "email" },
        "role": { "enum": ["admin", "member"] }
      }
    }
    ```

## When you and the spec both change something

Sync makes a three-way merge between the old snapshot, the new spec and your file. When the spec and your file both changed the same field in different ways, that api is a conflict. Sync leaves the api as it is and tells you how to settle it.

Say you had set a page size on `listUsers` by hand (`query: { limit: 50 }`) before the spec added its own `limit`:

```console
$ vc sync
fetched http://localhost:18080/openapi/users.yaml (4 operations)
  ! users#listUsers conflict: the spec and the file both changed query limit
    resolve: vc sync users --take spec users#listUsers | --take mine users#listUsers | edit, then --resolved users#listUsers
  + users#updateUser new operation PATCH /users/${var.id}
  - users#deleteUser removed from the spec: kept, marked deprecated
✓ synced · snapshot openapi/users.yaml updated · 1 conflict left
```

The rest of the merge is applied. A plain `vc sync` exits `0` even with a conflict left, but `vc sync --check` keeps failing with exit `4` until you settle it:

```console
$ vc sync --check
fetched http://localhost:18080/openapi/users.yaml (4 operations)
  ! users#listUsers conflict: the spec and the file both changed query limit
    resolve: vc sync users --take spec users#listUsers | --take mine users#listUsers | edit, then --resolved users#listUsers
```

There are three ways to settle it:

- **Take the spec's version.**

  ```console
  $ vc sync users --take spec users#listUsers
  fetched http://localhost:18080/openapi/users.yaml (4 operations)
    ↑ users#listUsers query limit 50 → ${var.limit}
  ✓ synced · snapshot openapi/users.yaml updated
  ```

  The api now has `limit: ${var.limit}` and the spec's default, `vars: { limit: 20 }`.

- **Keep yours.**

  ```console
  $ vc sync users --take mine users#listUsers
  fetched http://localhost:18080/openapi/users.yaml (4 operations)
    = users#listUsers kept your query limit
  ✓ synced · snapshot openapi/users.yaml updated
  ```

- **Edit the api by hand, then mark it resolved.** For example, change it to `limit: ${var.pageSize}` with `vars: { pageSize: 50 }`, then run:

  ```console
  $ vc sync users --resolved users#listUsers
  fetched http://localhost:18080/openapi/users.yaml (4 operations)
    = users#listUsers kept your query limit
  ✓ synced · snapshot openapi/users.yaml updated
  ```

After any of the three, `vc sync --check` exits `0` again. `--take` and `--resolved` can be repeated to settle several apis in one go.

<Aside type="tip" title="What the generator leaves to you">
The generated tests are a starting point. They create the resource a `GET` or `DELETE` needs through the collection's `POST`, or skip the test when the spec has none. `--negative` writes one test per operation with a JSON body, a row per field it breaks. Review them as you would any generated code.
</Aside>

## What you learned

- `vc import openapi <url> --id <fileId> --tests` writes an api file, a test file and a 3.1 snapshot in `openapi/`. `--negative` and `--auth` add rejection tests.
- `expect.body.schema` takes a `$file`. Point it into the snapshot with `#/components/schemas/<Name>`, or at your own JSON Schema file.
- `vc sync --check` writes nothing and exits `4` on drift or an unsettled conflict. `vc sync --dry-run` shows the diffs. `vc sync` merges and keeps your edits.
- Operations that leave the spec stay in your file as `deprecated: true`, and `vc check` flags every call to them (V3203).
- Settle a conflict with `--take spec`, `--take mine`, or a hand edit followed by `--resolved`.
