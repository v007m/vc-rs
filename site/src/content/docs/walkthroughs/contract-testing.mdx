**Goal:** turn an OpenAPI spec into api and test files, check responses against the spec's schemas, then follow the spec as it changes. `vc sync` merges each new version of the spec into your files and keeps your edits. In CI, `vc sync --check` fails the build when the spec has drifted.

<Aside type="caution" title="Needs the demo from master">
This page uses `vc demo` routes that are newer than v0.1.0: the served specs under `/openapi/` and the users store they describe. Until the next release, install `vc` and `vc-demo` from `master`: `brew install --HEAD v007m/tap/vibranium` (see [Homebrew](/vc-rs/start/install/#homebrew)), or `cargo install --git https://github.com/v007m/vc-rs vc-cli vc-demo --locked` (see [Cargo](/vc-rs/start/install/#cargo)).
</Aside>

## Prerequisites

- `vc` and `vc-demo` on your `PATH` (see [Install](/vc-rs/start/install/)).
- `git`. The snapshot that `vc sync` merges against is a file you commit.
- The demo service running. It serves a users API, and that API's spec in two versions, `/openapi/users-v1.yaml` and `/openapi/users-v2.yaml`, so you can watch the spec change (see [`vc demo`](/vc-rs/reference/cli/demo/#what-it-serves)). Start it in the background:

  ```console
  $ vc demo start --detach
  demo running on http://localhost:7421 (pid 74215); `vc demo stop` stops it
  ```

## Import, test, follow the spec

<Steps>
1. **Create a project.** Start without the sample service, and put it under git.

   ```console
   $ mkdir users-api && cd users-api
   $ vc init --no-sample
   ✓ created a Vibranium project in /home/you/users-api
     .env.schema
     .gitignore
     vibranium.config.yaml
     schemas/  datasets/  hooks/  openapi/  load/
   next: vc new api <service>#<id> --path /…
   $ git init
   ```

2. **Import version 1 of the spec.** `--id users` names the api file. `--tests` writes one happy-path test per operation, which creates the user a `GET` or `DELETE` needs first and checks the response against the snapshot's schema. `--negative` adds a test with a row per body field the schema rejects. `--auth` adds a test per secured operation that expects `401` without credentials.

   ```console
   $ vc import openapi http://localhost:7421/openapi/users-v1.yaml --id users --tests --negative --auth
   ✓ imported http://localhost:7421/openapi/users-v1.yaml
   ```

   The import writes three files and adds one var:

   | File | What it holds |
   | --- | --- |
   | `services/users/users.api.yaml` | One api per operation, with `source.openapi` pointing back at the spec |
   | `services/users/openapi.test.yaml` | The generated tests (file ID `users.openapi`) |
   | `openapi/users.yaml` | A snapshot of the spec, converted to OpenAPI 3.1. `vc sync` merges against it. Commit it, and do not edit it |
   | `vibranium.config.yaml` | Gains `usersUrl: http://localhost:7421` under `vars` |

   Each api keeps its `operationId`. That is how `vc sync` matches an api to its operation later.

   ```yaml title="services/users/users.api.yaml (as imported)"
   # yaml-language-server: $schema=https://v007m.github.io/vc-rs/schema/api.schema.json
   # users · api file · keys: https://github.com/v007m/vc-rs/blob/master/docs/design/syntax-reference.md#api-files
   id: users
   name: Users
   baseUrl: ${var.usersUrl}
   source:
     openapi: http://localhost:7421/openapi/users-v1.yaml

   apis:
     - id: listUsers
       name: List users
       path: /users
       operationId: listUsers
     - id: createUser
       name: Create user
       method: POST
       path: /users
       vars:
         email: ada@example.com
       body:
         email: ${var.email}
       save:
         userId: ${response.body.id}
       cleanup:
         call: deleteUser
         vars:
           id: ${response.body.id}
       operationId: createUser
     - id: getUser
       name: Get user
       path: /users/${var.id}
       vars:
         id: ${fake.lorem.word}
       operationId: getUser
     - id: deleteUser
       name: Delete user
       method: DELETE
       path: /users/${var.id}
       vars:
         id: ${fake.lorem.word}
       operationId: deleteUser
   ```

   The body and vars come from the spec's required fields and examples. `createUser` is the collection's `POST`, so it saves the new user's ID as `userId` and deletes the user again when the test ends. The users spec has no security schemes, so `--auth` added nothing here. On a secured spec, such as the public Petstore (`vc import openapi https://petstore3.swagger.io/api/v3/openapi.json --id petstore --tests --auth`), it writes tests such as `rejectsFindPetsByStatusWithoutAuth`, which call the api with `auth: none` and expect `401`.

3. **Run the generated tests.**

   ```console
   $ vc run
   plan  5 tests (6 instances) in 1 file · profile default

   ✓ users.openapi#rejectsInvalidCreateUser › email missing — Create user: rejects an invalid body   62ms
   ✓ users.openapi#listsUsers — List users                          83ms
   ✓ users.openapi#rejectsInvalidCreateUser › email is not a string — Create user: rejects an invalid body   84ms
   ✓ users.openapi#createsUser — Create user                       130ms
   ✓ users.openapi#getsUser — Get user                             130ms
   ✓ users.openapi#deletesUser — Delete user                       132ms

   6 passed                                                     163ms · profile default
   reports  /home/you/users-api/.vibranium/reports/1/{ctrf.json,junit.xml,index.html}
   ```

   `rejectsInvalidCreateUser` sends two bodies the schema rejects, one per row, and expects a `400` for each. The demo checks every body it is sent, so it answers both with a `400`.

4. **See how the tests use the spec.** `getsUser` and `deletesUser` need a user that exists, so each creates one in `before` and passes its saved ID to the path's `id`. `deletesUser` deletes that user itself, so its `before` call has `keep: true` and the cleanup does not try to delete the user a second time.

   ```yaml title="services/users/openapi.test.yaml"
     - id: getsUser
       name: Get user
       before:
         - call: users#createUser
       call: users#getUser
       vars:
         id: ${var.userId}
       expect:
         status: 200
         body:
           schema:
             $file: ../../openapi/users.yaml#/components/schemas/User
   ```

   `expect.body.schema` takes a `$file`. A JSON pointer after `#` picks one schema inside the file, and the import points each test straight into the snapshot. The path is relative to the test file. When `vc sync` updates the snapshot, this check follows the new schema without any edit from you.

   Commit everything, the snapshot included: `git add -A && git commit -m "import users api"`.

5. **Change the spec.** Version 2 adds an optional `limit` query parameter to `listUsers`, a `PATCH /users/{id}` operation and a `role` field on users. It also drops `DELETE /users/{id}`. A real service changes its spec at the same URL; the demo serves each version at its own, so point the api file at version 2:

   ```yaml title="services/users/users.api.yaml (excerpt)"
   source:
     openapi: http://localhost:7421/openapi/users-v2.yaml
   ```

6. **Detect the drift.** `vc sync --check` fetches the spec, compares it with the snapshot and writes nothing. It exits with code `4` when something changed. That is the check to run in CI.

   ```console
   $ vc sync --check
   fetched http://localhost:7421/openapi/users-v2.yaml (4 operations)
     ~ users#listUsers optional query limit added to the spec: not sent, add `query.limit` to send it
     + users#updateUser new operation PATCH /users/${var.id}
     - users#deleteUser removed from the spec: kept, marked deprecated
   $ echo $?
   4
   ```

   A `~` line is a note, not a change: sync never sends an optional parameter, so it leaves `listUsers` as it is and tells you `limit` exists.

7. **Preview the merge.** `vc sync --dry-run` prints the same lines plus a diff of every file it would write.

   ```console

     ~ users#listUsers optional query limit added to the spec: not sent, add `query.limit` to send it

     - users#deleteUser removed from the spec: kept, marked deprecated
   --- a/services/users/users.api.yaml
   +++ b/services/users/users.api.yaml
   @@ -39,3 +39,14 @@
        vars:
          id: ${fake.lorem.word}
        operationId: deleteUser
   +    deprecated: true
   +  - id: updateUser
   +    name: Update user

   +      id: ${fake.lorem.word}

   +      content-type: application/merge-patch+json
   +    body: {}
   +    operationId: updateUser
   --- a/openapi/users.yaml
   +++ b/openapi/users.yaml
   @@ -1,4 +1,4 @@
   -# Snapshot of http://localhost:7421/openapi/users-v1.yaml as OpenAPI 3.1, written by `vc import` and `vc sync`.
   +# Snapshot of http://localhost:7421/openapi/users-v2.yaml as OpenAPI 3.1, written by `vc import` and `vc sync`.
   ...
   ```

   The `save` and `cleanup` on `createUser`, and any `expect` you add, are not touched. Sync owns only the parts the spec decides: the method, the path, the query and the content type. It adds apis for new operations. It never deletes an api.

8. **Sync.**

   ```console

     - users#deleteUser removed from the spec: kept, marked deprecated
   ✓ synced · snapshot openapi/users.yaml updated
   ```

9. **Pin down the new field with your own schema.** The spec's `User` schema lists `role` but does not require it. If your clients rely on `role`, write a stricter schema of your own:

   ```json title="schemas/users/user.json"
   {
     "$schema": "https://json-schema.org/draft/2020-12/schema",
     "type": "object",
     "required": ["id", "name", "email", "role"],
     "properties": {
       "id": { "type": "string", "pattern": "^[0-9]+$" },
       "name": { "type": "string" },
       "email": { "type": "string", "format": "email" },
       "role": { "enum": ["admin", "member"] }
     }
   }
   ```

   ```yaml title="services/users/contract.test.yaml"
   tests:
     - id: returnsAUserWithARole
       name: A created user reads back with a role
       before:
         - call: users#createUser
       call: users#getUser
       vars:
         id: ${var.userId}
   ```

## When you and the spec both change something

Sync makes a three-way merge between the old snapshot, the new spec and your file. When the spec and your file both changed the same field in different ways, that api is a conflict. Sync leaves the api as it is and tells you how to settle it.

Say that, back at version 1, you had written your own api for the `PATCH` the service already took, and sent it plain JSON:

```yaml title="services/users/users.api.yaml"
  - id: updateUser
    name: Update user
    method: PATCH
    path: /users/${var.id}
    operationId: updateUser
    vars:
      name: Grace
    headers:
      content-type: application/json
    body:
      name: ${var.name}
```

Version 2 adds `updateUser` with `application/merge-patch+json`. The method and path agree with yours, the content type does not, so `vc sync` reports a conflict:

```console
$ vc sync
fetched http://localhost:7421/openapi/users-v2.yaml (4 operations)
  ~ users#listUsers optional query limit added to the spec: not sent, add `query.limit` to send it
  ! users#updateUser conflict: the spec and the file both changed content type
    resolve: vc sync users --take spec users#updateUser | --take mine users#updateUser | edit, then --resolved users#updateUser
  - users#deleteUser removed from the spec: kept, marked deprecated
✓ synced · snapshot openapi/users.yaml updated · 1 conflict left
```

The rest of the merge is applied. A plain `vc sync` exits `0` even with a conflict left, but `vc sync --check` keeps failing with exit `4` until you settle it:

```console
$ vc sync --check
fetched http://localhost:7421/openapi/users-v2.yaml (4 operations)
  ! users#updateUser conflict: the spec and the file both changed content type
    resolve: vc sync users --take spec users#updateUser | --take mine users#updateUser | edit, then --resolved users#updateUser
```

There are three ways to settle it:

- **Take the spec's version.** The api gets `content-type: application/merge-patch+json`; its vars and body stay yours.

  ```console
  $ vc sync users --take spec users#updateUser
  fetched http://localhost:7421/openapi/users-v2.yaml (4 operations)
    ↑ users#updateUser content type application/json → application/merge-patch+json
  ✓ synced · snapshot openapi/users.yaml updated
  ```

- **Keep yours.**

  ```console
  $ vc sync users --take mine users#updateUser
  fetched http://localhost:7421/openapi/users-v2.yaml (4 operations)
    = users#updateUser kept your content type
  ✓ synced · snapshot openapi/users.yaml updated
  ```

- **Edit the api by hand, then mark it resolved.** For example, read the content type from a var, so a test can send either:

  ```yaml title="services/users/users.api.yaml"
    - id: updateUser
      # ...
      vars:
        name: Grace
        patchType: application/json
      headers:
        content-type: ${var.patchType}
  ```

  Then run:

  ```console
  $ vc sync users --resolved users#updateUser
  fetched http://localhost:7421/openapi/users-v2.yaml (4 operations)
    = users#updateUser kept your content type
  ✓ synced · snapshot openapi/users.yaml updated
  ```

After any of the three, `vc sync --check` exits `0` again. `--take` and `--resolved` can be repeated to settle several apis in one go.

<Aside type="tip" title="What the generator leaves to you">
The generated tests are a starting point. They create the resource a `GET` or `DELETE` needs through the collection's `POST`, which saves its ID as `<resource>Id` (`userId`), or skip the test when the spec has none, saying which var to set. `--negative` writes one test per operation with a JSON body, a row per field it breaks. Review them as you would any generated code.
</Aside>

## What you learned

- `vc import openapi <url> --id <fileId> --tests` writes an api file, a test file and a 3.1 snapshot in `openapi/`. `--negative` and `--auth` add rejection tests.
- `expect.body.schema` takes a `$file`. Point it into the snapshot with `#/components/schemas/<Name>`, or at your own JSON Schema file.
- `vc sync --check` writes nothing and exits `4` on drift or an unsettled conflict. `vc sync --dry-run` shows the diffs. `vc sync` merges and keeps your edits.
- Operations that leave the spec stay in your file as `deprecated: true`, and `vc check` flags every call to them (V3203).
- Settle a conflict with `--take spec`, `--take mine`, or a hand edit followed by `--resolved`.
