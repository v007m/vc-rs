Tests often need a token, a password or an API key. In Vibranium, test files only name a secret, as `${secret.NAME}`. The value comes from outside the project, and `vc` masks it as `••••` in everything it prints and stores.

## Add a secret

<Steps>

1. **Use it.** Write `${secret.NAME}` where the value goes, here in an api's header:

   ```yaml title="services/sample/sample.api.yaml"
     - id: whoAmI
       name: Echo the caller
       path: /echo
       headers:
         x-api-key: ${secret.SHOP_API_KEY}
   ```

2. **Declare it.** `vc check` stops on a name that `.env.schema` does not declare:

   ```console
   $ vc check
   error[V2106]: `${secret.SHOP_API_KEY}` is not declared in `.env.schema`
     --> services/sample/sample.api.yaml:58:18
      |
   58 |       x-api-key: ${secret.SHOP_API_KEY}
      |                  ^^^^^^^^^^^^^^^^^^^^^^ SHOP_API_KEY is not in .env.schema
      = help: add the line `SHOP_API_KEY=` to `.env.schema` at the project root, or fix the name

   1 error · 0 warnings · 4 files checked
   ```

   Add the name, with no value, to `.env.schema` at the project root. `vc init` creates the file. Commit it: it lists the names, never the values.

   ```sh title=".env.schema"
   SHOP_API_KEY=
   ```

3. **Give it a value.** On your machine, put it in `.env` at the project root, or set it in your shell:

   ```sh title=".env"
   SHOP_API_KEY=sk_test_51HxAda
   ```

   A value in the environment wins over `.env`.

4. **Keep `.env` out of git.** `vc init` does not ignore it for you, so add it to `.gitignore`:

   ```text title=".gitignore"
   .vibranium/
   .env
   ```

</Steps>

Without a value, every test that needs the secret fails before its request is sent:

```console
$ vc run sample.secret
plan  1 test in 1 file · profile default

✕ sample.secret#sendsApiKey                                       0ms
  error[V5111]: `secret.SHOP_API_KEY` is missing: `secret` is {}
     = at: call sample#whoAmI

0 passed · 1 failed                                          16ms · profile default
```

## In CI

`${secret.NAME}` reads the process environment, so store the value as a CI secret with the same name and pass it to the job:

```yaml title=".github/workflows/api-tests.yml"
      - run: vc run --profile ci
        env:
          SHOP_API_KEY: ${{ secrets.SHOP_API_KEY }}
```

There is no `.env` in CI, and none is needed. See [CI](/vc-rs/guides/ci/) for GitLab and Jenkins.

## What gets masked

Every secret value of four characters or more is replaced by `••••` wherever it appears: console output, `vc call`, `--reporter json`, report files, and the requests and responses stored in `.vibranium/history.db`. That includes a response that echoes the secret back:

```console
$ vc call sample#whoAmI
200 OK · 37 ms · api expect passed
...
    "x-api-key": "••••"
...
```

A failing check shows the masked value too:

```console
$ vc run sample.secret
✕ sample.secret#sendsApiKey                                      10ms
  error[V5101]: expect.body.match.headers.x-api-key
   --> services/sample/secret.test.yaml:8:30
    |
  8 |           headers.x-api-key: nope
    |                              ^^^^ expected "nope", got "••••"
```

The values of the `Authorization`, `Cookie` and `Set-Cookie` headers are masked as well, whether or not they came from a secret. To mask more, such as a `password` field in a response or values that match a pattern, add a [`redact`](/vc-rs/reference/config/redact/) block.

<Aside type="caution">
A value shorter than four characters is not masked, so a three-letter test password shows in the output. Use longer values.
</Aside>

## Mistakes `vc check` catches

- **A typo in a name.** `${secret.SHOP_API_KY}` is [V2106](/vc-rs/reference/diagnostics/v2106/), with the closest declared name as a fix.
- **Reading a secret through `${env.NAME}`.** That would skip the masking, so it is [V2107](/vc-rs/reference/diagnostics/v2107/). The fix rewrites it as `${secret.NAME}`. `${env.NAME}` is for values that are not secret, such as a build number.

When `vc check` prints a `fix:` line for either, `vc check --fix` can apply it.

## Where secrets come from

| You have | Do this |
| --- | --- |
| Values in `.env` or the environment | Nothing: this is the default `env` provider |
| A secret manager such as 1Password, Vault or AWS | Set `secrets.provider: varlock` and install [varlock](https://varlock.dev). See [`secrets`](/vc-rs/reference/config/secrets/) |
| A HAR or curl import | `vc import` drops `authorization` headers and cookies, and turns body fields that look secret into `${secret.NAME}` references declared in `.env.schema`. See [HAR and capture](/vc-rs/guides/har-and-capture/) |
| A Vibranium v1 project | `vc migrate v1` turns the v1 accounts into `auth` entries with `${secret.…}` references, writes `.env.schema`, and does not copy the values. See [Migrating from v1](/vc-rs/guides/migrating-from-v1/) |

Auth settings such as `token`, `password` and `clientSecret` take secrets in the same way. See [Auth](/vc-rs/reference/auth/).
