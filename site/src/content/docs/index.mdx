<Section id="a-test" eyebrow="A test in ten lines" title="Say what you expect. Get told exactly what broke." lead="An <strong>api</strong> says how to call an endpoint once. A <strong>test</strong> calls it by ID and states what it expects. When a check fails, the error points at the line of YAML that set it.">
<Split startLabel="You write" endLabel="vc tells you">
<div slot="start">

`vc init` creates a project with a `sample` api for the bundled demo service. Add this file next to it:

```yaml title="services/sample/landing.test.yaml"
name: User accounts
tests:
  - id: createsUser
    name: Creates a user with the given email
    call: sample#createUser
    vars: { email: ada@example.com }
    expect:
      status: 201
      body:
        match: { email: ada@example.com, id: { type: string } }
```

</div>
<div slot="end">

```console title="It passes"
$ vc demo start --detach
$ vc run sample.landing
plan  1 test in 1 file · profile default

✓ sample.landing#createsUser                                      4ms

1 passed                                                     5ms · profile default
```

```console title="Change the email, and it fails at the exact line"
✕ sample.landing#createsUser                                     50ms
  error[V5101]: expect.body.match.email
    --> services/sample/landing.test.yaml:10:25
     |
  10 |         match: { email: bob@example.com, id: { type: string } }
     |                         ^^^^^^^^^^^^^^^ expected "bob@example.com", got "ada@example.com"
```

</div>

<Section id="features" variant="band" eyebrow="What it does" title="One engine for every kind of API test" lead="Write a test once, then check it, run it, load it or hand it to an agent. Every front end runs the same engine.">
<Grid>
<Feature title="Functional tests" icon="check" href="/vc-rs/walkthroughs/rest-crud/">
Call each endpoint from tests with matchers, data-driven examples, polling, setup and cleanup.
</Feature>
<Feature title="Contract and OpenAPI sync" icon="contract" href="/vc-rs/walkthroughs/contract-testing/">
`vc import` builds api files from OpenAPI, HAR or another tool. `vc sync` merges spec changes and keeps your edits.
</Feature>
<Feature title="Load tests" icon="load" href="/vc-rs/walkthroughs/load-testing/">
Reuse tests as load scenarios with weighted mixes, stages and thresholds. A breach exits with code 3.
</Feature>
<Feature title="Terminal UI" icon="terminal" href="/vc-rs/guides/tui/">
`vc tui` runs tests, explores apis, browses history and watches load runs without leaving the terminal.
</Feature>
<Feature title="Web UI" icon="browser" href="/vc-rs/guides/web-ui/">
`vc ui` serves a local web UI on 127.0.0.1 with a live feed of the run as it happens.
</Feature>
<Feature title="MCP for AI agents" icon="agent" href="/vc-rs/agents/">
`vc mcp` gives agents tools to check, run and author tests. Risky calls wait for a person's approval.
</Feature>
<Feature title="Plugins and alerts" icon="plug" href="/vc-rs/reference/plugins/">
Reporter and auth plugins in any language. Alerts to webhooks, Slack, Teams or PagerDuty.
</Feature>
<Feature title="Plain YAML in git" icon="git" href="/vc-rs/reference/schemas/">
Tests, apis and config are YAML with JSON Schemas for editor completion. Every change is a diff.
</Feature>
</Grid>
</Section>

<Section id="how-it-works" eyebrow="How it works" title="Write, check, run" lead="The same three steps on your laptop and in CI.">
<Grid as="ol" columns={3}>
<HowStep n={1} title="Write YAML" href="/vc-rs/start/concepts/" link="Concepts">

Describe each endpoint once in `services/<service>/<service>.api.yaml`, then write tests that call it.

```yaml title="services/users/crud.test.yaml (excerpt)"
tests:
  - id: getsUser
    call: users#getUser
    expect: { status: 200 }
```

</HowStep>
<HowStep n={2} title="<code>vc check</code>" href="/vc-rs/guides/errors-and-fixes/" link="Errors and fixes">

Parse and link every file without sending a request. Each problem has a code, a line and, where one is certain, a fix.

```console wrap
$ vc check
0 errors · 0 warnings · 3 files checked
```

</HowStep>
<HowStep n={3} title="<code>vc run</code>, here or in CI" href="/vc-rs/guides/ci/" link="Run it in CI">

Tests run in parallel. A failure exits with code 1, so CI needs no extra scripting.

```console wrap
$ vc run --profile ci --report junit,ctrf,html --out reports
```

</HowStep>
</Grid>
</Section>

<Section id="agents" variant="band" eyebrow="For AI agents" title="Built so an agent can write, run and fix tests" lead="Everything an agent needs is plain text with a stable shape, and every error says what to do next.">
<Split>
<div slot="start">

- **Nine MCP tools** over stdio with `vc mcp`, or over HTTP at `/mcp` while `vc ui` runs.
- **Rules and approvals.** Each profile's `agents` block says what an agent may run, call and write. Anything else is refused or waits for `vc approve`.
- **Diagnostics with fixes.** Every problem has a code, a span and a `help:` line. `vc check --fix` applies the certain fixes.
- **JSON everywhere.** `--json` output, an NDJSON run stream and a hosted [llms.txt](/vc-rs/llms.txt) of the whole site.

<p class="lp-links"><a href="/vc-rs/agents/mcp-setup/">Set up MCP →</a> <a href="/vc-rs/agents/mcp-tools/">See the tools →</a></p>

</div>
<div slot="end">

```console title="Claude Code, in the project folder"
claude mcp add vibranium -- vc mcp
```

```json title=".mcp.json"
{
  "mcpServers": {
    "vibranium": {
      "command": "vc",
      "args": ["mcp"]
    }
  }
}
```

</div>
</Split>
