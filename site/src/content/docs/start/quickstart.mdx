This page takes you from an empty folder to passing tests, first against a small demo API on your machine, then against a real public one. You need `vc` and `vc-demo` on your `PATH` (see [Install](/vc-rs/start/install/)). If your shell already uses `vc` for something else, type `vibranium` wherever this page says `vc`.

## Meet the API you will test

Every API test starts with an API. Vibranium ships a tiny one, the users service of a pretend shop, so you can practise without touching anything real.

<Steps>
1. **Start the demo service.** It runs in the background on port 7421.

   ```console
   $ vc demo start --detach
   demo running on http://localhost:7421 (pid 13213); `vc demo stop` stops it
   ```

2. **See what it offers.** It has four endpoints:

   | Request | What it does |
   | --- | --- |
   | `GET /users` | Lists the two seed users, Ada Lovelace and Grace Hopper |
   | `GET /users/{id}` | Returns one user |
   | `POST /users` | Creates a user from a JSON body with a `name` and an `email`; answers `201` with the new user, or `400` without an email |
   | `DELETE /users/{id}` | Deletes a user; answers `204` |

3. **Call it by hand.** This is what a test will do for you. List the users:

   ```console
   $ curl http://localhost:7421/users
   [{"id":"1","name":"Ada Lovelace"},{"id":"2","name":"Grace Hopper"}]
   ```

   And create one:

   ```console
   $ curl -i -X POST http://localhost:7421/users \
       -H 'content-type: application/json' \
       -d '{"name":"Alan Turing","email":"alan@example.com"}'
   HTTP/1.1 201 Created
   content-type: application/json

   {"email":"alan@example.com","id":"3","name":"Alan Turing"}
   ```

   A test sends requests like these and checks the answers: the status is `201`, the email is the one sent, the `id` is a string. The rest of this page writes those checks down.
</Steps>

## Create a project

A project is a folder with a `vibranium.config.yaml` in it. `vc init` creates one. `--no-sample` leaves out the sample tests, since you are about to write your own.

```console
$ mkdir shop && cd shop
$ vc init --no-sample
✓ created a Vibranium project in /home/you/shop
  .env.schema
  .gitignore
  vibranium.config.yaml
  schemas/  datasets/  hooks/  openapi/  load/
next: vc new api <service>#<id> --path /…
```

## Describe the API

An **api** is how to call one endpoint. Apis live in one file per service: the users service's file is `services/users/users.api.yaml`, and each api in it has an ID such as `users#listUsers`.

<Steps>
1. **Add the first api.** `vc new api` writes it for you from a URL:

   ```console
   $ vc new api users#listUsers --url http://localhost:7421/users
   ✓ added users#listUsers to services/users/users.api.yaml:6
   ```

   It wrote this file, with links to the reference in its comments:

   ```yaml title="services/users/users.api.yaml"
   # yaml-language-server: $schema=https://v007m.github.io/vc-rs/schema/api.schema.json
   # users · api file · keys: https://github.com/v007m/vc-rs/blob/master/docs/design/syntax-reference.md#api-files
   baseUrl: ${var.usersUrl}
   apis:
     # users#listUsers · GET /users · keys: https://github.com/v007m/vc-rs/blob/master/docs/design/syntax-reference.md#api-files
     - id: listUsers
       name: List users
       path: /users
   ```

   It also put the server's address in the config, as a **var** the api file reads with `${var.usersUrl}`. Every api of the service shares it, and later you will switch it to another server in one place.

   ```yaml title="vibranium.config.yaml (excerpt)"
   vars:
     usersUrl: http://localhost:7421
   ```

2. **Add the other endpoints.** Open the api file and make it this. Each entry under `apis` is one endpoint from the table above.

   ```yaml title="services/users/users.api.yaml"
   name: Users service
   baseUrl: ${var.usersUrl}

   apis:
     - id: listUsers
       name: List users
       path: /users
       expect:
         status: 200

     - id: getUser
       name: Get one user
       path: /users/${var.userId}
       expect:
         status: 200

     - id: createUser
       name: Create a user
       method: POST
       path: /users
       vars:
         name: ${fake.person.fullName}
         email: ${fake.internet.email}
       body:
         name: ${var.name}
         email: ${var.email}
       expect:
         status: 201
       save:
         userId: ${response.body.id}
       cleanup:
         call: deleteUser
         vars:
           userId: ${response.body.id}

     - id: deleteUser
       name: Delete a user
       method: DELETE
       path: /users/${var.userId}
       expect:
         status: [204, 404]
   ```

   A few things in it are worth a look:

   - `expect` on an api holds the checks every call of it needs, such as the status.
   - `createUser` fills its body from **vars**. By default they are fake data (`${fake.internet.email}`), so every call creates a fresh user; a test can set its own values.
   - `save` keeps the new user's `id` as `${var.userId}`, and `cleanup` deletes that user after the test. Tests leave no data behind.
</Steps>

<Aside type="tip" title="Coming from Postman?">
The api file plays the part of a Postman collection: one request per entry. The tests below play the part of the Tests tab. [Concepts](/vc-rs/start/concepts/#coming-from-postman) maps the rest, and `vc import` can turn a collection or an OpenAPI spec into an api file.
</Aside>

## Write the tests

A **test** calls an api by its ID and states what it expects. Tests live next to the api file, in files named after an area of the service, here `accounts`.

<Steps>
1. **Create the test file.**

   ```yaml title="services/users/accounts.test.yaml"
   name: User accounts
   tests:
     - id: listsSeedUsers
       name: Lists the two seed users
       call: users#listUsers
       expect:
         body:
           match:
             "[0].name": Ada Lovelace
             "[1].name": Grace Hopper

     - id: createsUser
       name: Creates a user with the given email
       call: users#createUser
       vars:
         email: ada@example.com
       expect:
         body:
           match:
             email: ada@example.com
             id:
               type: string
   ```

   `"[0].name"` is a path into the response body: the `name` of the first element. `type: string` is a [matcher](/vc-rs/reference/matchers/), a check other than "equals". Each test's full ID is the file's ID and its own: `users.accounts#createsUser`.

2. **Check the project.** `vc check` reads and links every file without sending a request. Run it whenever you edit YAML.

   ```console
   $ vc check
   0 errors · 0 warnings · 3 files checked
   ```

3. **Run the tests.**

   ```console
   $ vc run
   plan  2 tests in 1 file · profile default

   ✓ users.accounts#listsSeedUsers — Lists the two seed users        4ms
   ✓ users.accounts#createsUser — Creates a user with the given email    7ms

   2 passed                                                     9ms · profile default
   reports  /home/you/shop/.vibranium/reports/1/{ctrf.json,junit.xml,index.html}
   ```

   Each line shows the test's ID, then its `name`. Tests run in parallel, so the order changes from run to run. Open `index.html` in a browser for the full report.
</Steps>

## Break it on purpose

Mistakes are easier to fix when you have seen what they look like. Make two.

<Steps>
1. **A typo in an ID.** In `accounts.test.yaml`, change the first test's `call` to `users#listUser`:

   ```yaml title="services/users/accounts.test.yaml (excerpt)"
       call: users#listUser
   ```

   `vc check` points at it and knows the fix:

   ```console
   $ vc check
   error[V2003]: unknown api "users#listUser"
    --> services/users/accounts.test.yaml:5:11
     |
   5 |     call: users#listUser
     |           ^^^^^^^^^^^^^^ no api has this ID
     = help: did you mean `users#listUsers`?
     = fix: Replace with users#listUsers (certain)

   1 error · 0 warnings · 3 files checked
   ```

   Every diagnostic has a code, and `vc explain V2003` explains it with a wrong and a right example. When a fix is marked **certain**, `vc check --fix` applies it. It shows the change first and asks; `--yes` skips the question:

   ```console
   $ vc check --fix --yes
   --- a/services/users/accounts.test.yaml
   +++ b/services/users/accounts.test.yaml
   @@ -2,7 +2,7 @@
    tests:
      - id: listsSeedUsers
        name: Lists the two seed users
   -    call: users#listUser
   +    call: users#listUsers
        expect:
          body:
            match:
   ✓ applied 1 fix
   0 errors · 0 warnings · 3 files checked
   ```

2. **A wrong expected value.** Now misspell a name the API returns: change `Grace Hopper` to `Grace Hoper`. The file still checks, so the mistake shows up when the test runs:

   ```console
   $ vc run
   plan  2 tests in 1 file · profile default

   ✕ users.accounts#listsSeedUsers — Lists the two seed users        2ms
     error[V5101]: expect.body.match.[1].name
       --> services/users/accounts.test.yaml:10:23
        |
     10 |           "[1].name": Grace Hoper
        |                       ^^^^^^^^^^^ expected "Grace Hoper", got "Grace Hopper"
   ✓ users.accounts#createsUser — Creates a user with the given email    3ms

   1 passed · 1 failed                                          7ms · profile default
   reports  /home/you/shop/.vibranium/reports/2/{ctrf.json,junit.xml,index.html}
   next     vc run --failed
   seed 5032002959074185: pass `--seed 5032002959074185` to run with the same generated data
   ```

   A failed check points at the YAML line that made it and shows what it expected and what came back. The run exits with code 1, which fails a CI job. This run made up a name for `createsUser` with `${fake.person.fullName}`, so it also prints its `seed`: pass it back to replay the same fake data.

3. **Fix it and rerun only what failed.** Change the name back to `Grace Hopper`:

   ```console
   $ vc run --failed
   plan  1 test in 1 file · profile default

   ✓ users.accounts#listsSeedUsers — Lists the two seed users        3ms

   1 passed                                                     4ms · profile default
   reports  /home/you/shop/.vibranium/reports/3/{ctrf.json,junit.xml,index.html}
   ```
</Steps>

## Point it at a public API

The same tests can run against another server. [JSONPlaceholder](https://jsonplaceholder.typicode.com) has a `/users` endpoint of the same shape. A **profile** is a named set of values, like an environment in Postman, and switches the server without touching the tests.

<Steps>
1. **Add a profile.** In `vibranium.config.yaml`, add a `public` profile under `profiles:` that overrides `usersUrl`:

   ```yaml title="vibranium.config.yaml (excerpt)"
   profiles:
     - id: default
       default: true
     - id: public
       vars:
         usersUrl: https://jsonplaceholder.typicode.com
   ```

   `vc config explain` shows which value wins and where it comes from:

   ```console
   $ vc config explain vars.usersUrl --profile public
   vars.usersUrl = https://jsonplaceholder.typicode.com  (profile public)
     over http://localhost:7421  (vibranium.config.yaml)
   ```

2. **Run with the profile.** The request now goes to JSONPlaceholder, whose users have other names:

   ```console
   $ vc run users.accounts#listsSeedUsers --profile public
   plan  1 test in 1 file · profile public

   ✕ users.accounts#listsSeedUsers — Lists the two seed users       31ms
     error[V5101]: expect.body.match.[0].name
      --> services/users/accounts.test.yaml:9:23
       |
     9 |           "[0].name": Ada Lovelace
       |                       ^^^^^^^^^^^^ expected "Ada Lovelace", got "Leanne Graham"
     error[V5101]: expect.body.match.[1].name
       --> services/users/accounts.test.yaml:10:23
        |
     10 |           "[1].name": Grace Hopper
        |                       ^^^^^^^^^^^^ expected "Grace Hopper", got "Ervin Howell"

   0 passed · 1 failed                                          38ms · profile public
   reports  /home/you/shop/.vibranium/reports/4/{ctrf.json,junit.xml,index.html}
   next     vc run --failed
   ```

3. **Move the expected names into vars.** A test file can have its own `vars`, and its own `profiles` list that overrides them. Change the top of `accounts.test.yaml` and the first test to this:

   ```yaml title="services/users/accounts.test.yaml"
   name: User accounts
   vars:
     firstUser: Ada Lovelace
     secondUser: Grace Hopper
   profiles:
     - id: public
       vars:
         firstUser: Leanne Graham
         secondUser: Ervin Howell
   tests:
     - id: listsSeedUsers
       name: Lists the two seed users
       call: users#listUsers
       expect:
         body:
           match:
             "[0].name": ${var.firstUser}
             "[1].name": ${var.secondUser}

     - id: createsUser
       name: Creates a user with the given email
       call: users#createUser
       vars:
         email: ada@example.com
       expect:
         body:
           match:
             email: ada@example.com
             id:
               type: string
   ```

4. **Run it both ways.**

   ```console
   $ vc run users.accounts#listsSeedUsers --profile public
   plan  1 test in 1 file · profile public

   ✓ users.accounts#listsSeedUsers — Lists the two seed users       28ms

   1 passed                                                     30ms · profile public
   reports  /home/you/shop/.vibranium/reports/5/{ctrf.json,junit.xml,index.html}

   $ vc run users.accounts#listsSeedUsers
   plan  1 test in 1 file · profile default

   ✓ users.accounts#listsSeedUsers — Lists the two seed users        3ms

   1 passed                                                     4ms · profile default
   reports  /home/you/shop/.vibranium/reports/6/{ctrf.json,junit.xml,index.html}
   ```
</Steps>

When you are done, `vc demo stop` stops the demo service.

<Aside type="tip">
`vc history` lists your past runs with their results, and `vc call users#getUser --set vars.userId=1` sends one api request and prints the response, which is handy while you write an api.
</Aside>
