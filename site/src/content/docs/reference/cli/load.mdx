Runs one load scenario: a `*.load.yaml` file that mixes your existing tests, ramps virtual users through stages, and sets thresholds. It prints a live line every second, then a summary, and fails the command when a threshold is breached.

```console
$ vc load [OPTIONS] <SCENARIO>
```

## Options

| Flag | Value | Default | Description |
| --- | --- | --- | --- |
| `<SCENARIO>` | file ID | | The load file's ID: `checkout.peak` for `load/checkout/peak.load.yaml` |
| `--profile` | `<IDS>` | the config's default | The active profiles, as a comma list or repeated. Later ones win |
| `--set` | `<KEY=VALUE>` | | Sets one config value over every other config layer |
| `--json` | | | Prints the final report as JSON on stdout, with no live line |
| `--project` | `<DIR>` | | See [global flags](/vc-rs/reference/cli/#global-flags) |

## Examples

### Run a scenario

```yaml title="load/sample/smoke.load.yaml"
name: Sample smoke load
mix:
  - test: sample.extra#echoesBody
    weight: 3
  - test: sample.basics#createsUser
    weight: 1
stages:
  - duration: 3s
    users: 5
  - duration: 2s
    users: 0
thresholds:
  p95:
    lt: 200ms
  errorRate:
    lt: 1%
```

```console
$ vc load sample.smoke
    1s  0 users  0 rps  p50 0 ms  p95 0 ms  p99 0 ms  0 errors
    2s  2 users  562 rps  p50 1 ms  p95 2 ms  p99 4 ms  0 errors
    3s  3 users  1021 rps  p50 1 ms  p95 2 ms  p99 3 ms  0 errors
    4s  5 users  1962 rps  p50 1 ms  p95 2 ms  p99 4 ms  0 errors
    5s  3 users  2157 rps  p50 1 ms  p95 2 ms  p99 4 ms  0 errors
    5s  0 users  2157 rps  p50 1 ms  p95 2 ms  p99 4 ms  0 errors
sample.smoke — Sample smoke load · finished after 5 s · 7597 iterations · 1519.4 rps · 0 errors
latency p50 1.6 ms · p90 2.4 ms · p95 2.8 ms · p99 4.1 ms · max 11.7 ms
test sample.basics#createsUser · 1846 iterations · 369.2 rps · 0 errors · p50 1.7 ms · p90 2.7 ms · p95 3.3 ms · p99 4.8 ms · max 11.7 ms
test sample.extra#echoesBody · 5751 iterations · 1150.2 rps · 0 errors · p50 1.5 ms · p90 2.2 ms · p95 2.6 ms · p99 3.8 ms · max 11.4 ms
```

The live lines go to stderr; the summary goes to stdout. Each live line shows the elapsed time, active users, iterations per second over the last 3 seconds, latency percentiles and errors. The summary ends with a `test` line for each test of the mix, with that test's own iterations, rate, errors and latency.

### A breached threshold

`sample.strict` runs `sample.basics#listsUsers` for 2 s and wants `p95` under `1ms` and `errorRate` under `1%`:

```console
$ vc load sample.strict
    1s  0 users  0 rps  p50 0 ms  p95 0 ms  p99 0 ms  0 errors
    2s  1 users  323 rps  p50 1 ms  p95 2 ms  p99 2 ms  0 errors  breaching: p95
    2s  0 users  323 rps  p50 1 ms  p95 2 ms  p99 2 ms  0 errors
sample.strict — Too strict on purpose · finished after 2 s · 646 iterations · 323.0 rps · 0 errors
latency p50 1.4 ms · p90 1.8 ms · p95 2.2 ms · p99 2.9 ms · max 5.8 ms
breached p95 at 2.193 ms (lt 1 ms)
test sample.basics#listsUsers · 646 iterations · 323.0 rps · 0 errors · p50 1.4 ms · p90 1.8 ms · p95 2.2 ms · p99 2.9 ms · max 5.8 ms
$ echo $?
3
```

`breaching:` appears on the live line as soon as a threshold is over. A `breached` line gives the measured value in the metric's unit (`ms` for latency, `%` for `errorRate`, `/s` for `rps`) and, in brackets, the threshold's limit.

### Errors

When iterations fail, the summary groups them under the test that failed, by the api of the call that failed, its status and the failure's code, one indented `errors` line each. Here `sampleUrl` points at a port nothing listens on, so no call got a status and each failed with [V5105](/vc-rs/reference/diagnostics/v5105/):

```console
$ vc load sample.strict --set vars.sampleUrl=http://127.0.0.1:9
...
sample.strict — Too strict on purpose · finished after 2 s · 611 iterations · 305.5 rps · 611 errors
latency p50 1.5 ms · p90 1.9 ms · p95 2.3 ms · p99 3.3 ms · max 5.6 ms
breached p95 at 2.271 ms (lt 1 ms)
breached errorRate at 100% (lt 1%)
test sample.basics#listsUsers · 611 iterations · 305.5 rps · 611 errors · p50 1.5 ms · p90 1.9 ms · p95 2.3 ms · p99 3.3 ms · max 5.6 ms
  errors sample#listUsers V5105 × 611
```

A failed check is `V5101` with the status the call got (`errors sample#listUsers 200 V5101 × 10`). The failure is counted under the call that failed, not under a `before` call or a cleanup around it. A failure with no api, such as a `command` action's, shows just its status and code under its test.

```console
$ vc load sample.strict --json

```

## Exit codes

| Code | When |
| --- | --- |
| `0` | The scenario finished within every threshold |
| `2` | The project has errors, or there is no such scenario |
| `3` | A threshold was breached |
| `130` | Cancelled with Ctrl-C |

```console
$ vc load sample.nope
error: no load scenario has the ID `sample.nope`
  = help: the scenarios are: sample.smoke, sample.strict
```

## JSON output

| Field | Holds |
| --- | --- |
| `scenario`, `runId`, `seed` | The scenario ID, its history run number, and the data seed |
| `ending` | How it ended, such as `finished` |
| `exit` | The exit code |
| `seconds`, `iterations`, `rps` | Duration, iterations run, and requests per second |
| `p50Ms`, `p90Ms`, `p95Ms`, `p99Ms`, `maxMs` | Latency in milliseconds |
| `errors` | How many iterations failed |
| `errorKinds[]` | `{api, test, status, code, count}` for each kind of error: the test that failed, the api of the call that failed (`null` when none did, as for a `command` action), the status it got and the diagnostic code |
| `tests[]` | `{test, iterations, rps, errors, p50Ms, p90Ms, p95Ms, p99Ms, maxMs}` for each test of the mix |
| `breaches[]` | `{metric, test, actual, unit, limit}` for each breached threshold; `test` is set for a per-test threshold, `unit` is `ms`, `share` (0 to 1) or `perSecond`, and `limit` is the matcher's arguments in that unit (`{"lt": 1.0}`) |
| `blocked` | Why the scenario could not start, or `null` |
| `notices[]` | Warnings raised during the run |

## How it behaves

- `vc load` checks the whole project first, like `vc run`, and stops with exit code 2 on any error.
- The tests in the `mix` run with their file's lifecycle actions. `beforeRun` and each mixed file's `beforeAll` run once before the first stage, and `afterAll` and `afterRun` once after the last, so a file that stops a service in `afterAll` stops it after the load run as well. See [Lifecycle in load runs](/vc-rs/reference/load/lifecycle/).
- Every load run is stored in [history](/vc-rs/reference/cli/history/) as a run of kind `load`, listed as `load · 473 iterations · 0 errors`.
