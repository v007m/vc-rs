An api that creates something declares how to remove it with `cleanup`. Every successful call of that api registers the cleanup, and vc runs it when the test, file or run that made the call ends.

The lifecycle pages call the demo server through one api file, `demo`, shown here in full. `demo#createItem` declares a cleanup that deletes the user it made:

```yaml title="services/demo/demo.api.yaml"
baseUrl: ${var.sampleUrl}
apis:
  - id: createItem
    method: POST
    path: /users
    vars:
      label: item
      email: demo@example.com
    body:
      name: ${var.label}
      email: ${var.email}
    expect:
      status: 201
    save:
      itemId: ${response.body.id}
    cleanup:
      call: deleteItem
      vars:
        itemId: ${response.body.id}
  - id: deleteItem
    method: DELETE
    path: /users/${var.itemId}
  - id: whoami
    path: /echo
  - id: status
    path: /status/${var.code}
  - id: slow
    path: /slow
    query:
      ms: ${var.ms}
  - id: makeBroken
    method: POST
    path: /echo
    cleanup:
      call: status
      vars:
        code: 500
  - id: flaky
    name: Fails, then passes
    path: /flaky
    vars:
      flakyKey: flaky-${run.startedAt}
      failTimes: "1"
    query:
      key: ${var.flakyKey}
      failTimes: ${var.failTimes}
  - id: job
    name: Read a job
    path: /poll/${var.jobId}
    query:
      after: "4"
```

## Syntax

| Field | Type | Default | Required | Notes |
| --- | --- | --- | --- | --- |
| `cleanup.call` | api ID | — | yes | An api in the same file can be named bare (`deleteItem`) |
| `cleanup.vars` | map | — | no | Rendered from the response that created the thing |
| `keep` (on a call or action) | boolean | `false` | no | Skip the cleanup for this one call |
| `vc call --keep` | flag | off | no | Skip the cleanup of a call from the terminal |

## Examples

The examples call the demo server (`vc demo start`) through the `demo` api file shown in full above. `demo#createItem` creates a user, `demo#status` is a `GET /status/${var.code}` that answers with that status, and `demo#slow` is a `GET /slow?ms=${var.ms}` that waits that many milliseconds.

Cleanups run newest first. This test makes three items and keeps the last one:

```yaml title="services/demo/cleanup.test.yaml"
tests:
  - id: cleansUpNewestFirst
    steps:
      - call: demo#createItem
        vars:
          label: first
      - call: demo#createItem
        vars:
          label: second
      - call: demo#createItem
        keep: true
        vars:
          label: kept
```

The server saw `second` deleted before `first`, and `kept` left alone:

```console
POST /users body={"email":"demo@example.com","name":"first"}     → 7
POST /users body={"email":"demo@example.com","name":"second"}    → 8
POST /users body={"email":"demo@example.com","name":"kept"}      → 9
DELETE /users/8
DELETE /users/7
```

A failed test still cleans up. Here the second step gets a 500:

```yaml
  - id: cleansUpAfterFailure
    steps:
      - call: demo#createItem
      - call: demo#status
        vars:
          code: 500
```

```console
POST /users body={"email":"demo@example.com","name":"item"}
GET /status/500
DELETE /users/6
```

Ctrl-C cancels the run, and the cleanups still run before vc exits with code 130. This test makes an item, then calls `demo#slow`, which waits ten seconds:

```yaml
  - id: cleansUpOnCtrlC
    steps:
      - call: demo#createItem
      - call: demo#slow
        vars:
          ms: 10000
```

```console
$ vc run demo.cleanup#cleansUpOnCtrlC
plan  1 test in 1 file · profile default

^C
- demo.cleanup#cleansUpOnCtrlC skipped: cancelled                7.4s

0 passed · 1 skipped · cancelled                             7.4s · profile default
reports  …/.vibranium/reports/1/{ctrf.json,junit.xml,index.html}
```

```console
POST /users body={"email":"demo@example.com","name":"item"}
GET /slow?ms=10000
DELETE /users/10
```

A second Ctrl-C ends the grace period, and the cleanups still run. A third stops them: vc lists the cleanups that did not finish, the one it stopped first (its request may already have reached the server), then the rest, newest first.

`vc call` registers the cleanup too. Pass `--keep` to leave the item in place:

```console
$ vc call demo#createItem --var label=adhoc
201 Created · 2 ms · api expect passed
{
  "email": "demo@example.com",
  "id": "11",
  "name": "adhoc"
}
```

The server saw `POST /users` and then `DELETE /users/11`. With `vc call demo#createItem --keep`, no `DELETE` is sent.

A cleanup that fails is a warning. The test keeps its result:

```console
! cleanup call demo#status (instance 0) failed: status: expected ["2xx"], got 500
✓ demo.cfail#warnsOnFailedCleanup                                 6ms
```

## How it behaves

- Only a call that passed its checks registers a cleanup. A 400 that created nothing registers none.
- The owner decides when it runs: the test instance for `before`, `beforeEach` and steps; the file for `beforeAll`; the run for `beforeRun`.
- Order is newest first within the owner, so a group is deleted before the members it holds.
- Each iteration of a loop registers its own cleanup.
- A [cached](/vc-rs/reference/lifecycle/cache/) action's cleanup waits until the cache entry expires, is replaced, or is cleared with `vc cache clear`.

<Aside>
Cleanups run after `after`, `afterEach` and `afterAll`, so those blocks can still read what the test created.
</Aside>

## Common errors

- [V5107](/vc-rs/reference/diagnostics/v5107/): a cleanup failed. It is a warning; the test result does not change.
