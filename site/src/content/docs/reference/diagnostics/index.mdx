Every problem Vibranium finds has a stable code such as `V2003`. A code never changes meaning once it ships, so you can search for it, link to it, and ask `vc explain` about it. There are 72 codes today.

## Reading a diagnostic

Here is real output from `vc check` for a test that calls an api ID with a typo:

```console
$ vc check
error[V2003]: unknown api "users#listUser"
 --> services/users/crud.test.yaml:6:11
  |
6 |     call: users#listUser
  |           ^^^^^^^^^^^^^^ no api has this ID
  = help: did you mean `users#listUsers`?
  = fix: Replace with users#listUsers (certain)

1 error · 0 warnings · 3 files checked
```

| Part | Example | What it tells you |
| --- | --- | --- |
| Severity and code | `error[V2003]` | `error` stops a run; `warning` does not. The code links to its page here. |
| Message | `unknown api "users#listUser"` | The problem, in one line. |
| Location | `--> services/users/crud.test.yaml:6:11` | File, line and column, relative to the project root. |
| Excerpt | the numbered lines | The source, with `^^^` under the exact span and a label beside it. A `:::` line and `---` marks show a second, related place (for example, `called from here`). |
| `help:` | `did you mean ...?` | What to do about it. A diagnostic can have more than one. |
| `fix:` | `Replace with users#listUsers (certain)` | An edit Vibranium can make for you. `(certain)` means `vc check --fix` applies it; a fix without it is only a suggestion. |
| Summary | `1 error · 0 warnings · 3 files checked` | Totals for the whole project. |

`vc check` exits with code 2 when there is at least one error and 0 when there are only warnings. `vc run`, `vc plan` and `vc list` refuse to start while the project has errors, and say `nothing ran`.

## Applying fixes

`vc check --fix` prints each certain fix as a diff and asks before writing:

```console
$ vc check --fix
--- a/services/users/crud.test.yaml
+++ b/services/users/crud.test.yaml
@@ -3,4 +3,4 @@
 tests:
   - id: listsUsers
     name: Lists users
-    call: users#listUser
+    call: users#listUsers
Apply 1 fix? [y/N] ✓ applied 1 fix
0 errors · 0 warnings · 3 files checked
```

Nothing is written when you answer no. The exit code is that of the final check.

## Diagnostics as JSON

`vc check --json` prints the same diagnostics for editors, scripts and agents:

```json
{
  "summary": { "errors": 1, "warnings": 0, "infos": 0 },
  "diagnostics": [
    {
      "code": "V2003",
      "severity": "error",
      "message": "unknown api \"users#listUser\"",
      "primary": {
        "span": { "path": "services/users/crud.test.yaml", "line": 6, "column": 11, "endLine": 6, "endColumn": 25 },
        "text": "no api has this ID"
      },
      "secondary": [],
      "notes": [],
      "help": ["did you mean `users#listUsers`?"],
      "fixes": [
        {
          "title": "Replace with users#listUsers",
          "certain": true,
          "edits": [
            { "path": "services/users/crud.test.yaml", "range": { "start": 90, "end": 104 }, "newText": "users#listUsers" }
          ]
        }
      ]
    }
  ]
}
```

A fix's `range` is a byte offset into the file.

## Asking about a code

Every code has a page built into the binary, with a wrong and a right example. It works anywhere, even outside a project:

```console
$ vc explain V2101
V2101: Var used but never set for some profile

A `${var.x}` is used, but for some profile nothing sets `x` before that spot: no call `vars`, earlier `save`, file or
config var, or profile. The diagnostic names the profiles where it is missing and the places it could be set.

Wrong
...
```

<Aside type="tip">
Write the code in capitals: `vc explain V2101`. A lowercase `v2101` is read as a test or api ID instead.
</Aside>

## Code ranges

| Range | Category | Found by | Meaning |
| --- | --- | --- | --- |
| V1xxx | Syntax | `vc check` | The file cannot be read as YAML of the right shape: bad YAML, an unknown or missing key. |
| V2xxx | References and types | `vc check` | An ID, var, secret or value does not resolve, or has the wrong type. |
| V3xxx | Lifecycle | `vc check` | Profiles, skips, shared setup and cleanup: legal but risky, or missing a reason. |
| V4xxx | Conventions | `vc check` | Names that break the naming rules (camelCase IDs, kebab-case tags). Always warnings. |
| V5xxx | Run time | `vc run`, `vc call`, `vc load` | What went wrong while a test, hook, auth flow or plugin ran. |

In a run, a V5 error marks the test **failed**, except V5106, which marks it **blocked** because a setup action it needed failed. V5 warnings (a failed cleanup, an alert that could not be sent, the cache being off) are reported but do not change the result.
