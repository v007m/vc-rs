An api's `type` decides which keys it takes: on the api item, in an `expect`, and on a test or step that calls it.
A key that the type does not use is an error, since it would be ignored. The fix removes it.

The same holds for a key a test with `steps` hands its `call` steps, such as `body`, when a step without its
own calls an api whose type does not take it. Other steps may still send it, so that one has no fix: move the key
onto the steps that send it. A `graphql` api's `body` takes only `query`, `variables` and `operationName`; the fix
for another key is the close one. A `graphql` or `sse` block is read only on a file of that type; elsewhere the
fix removes it.

`http`, the default type, takes nearly every key: on it, only `expect.errors`, which reads GraphQL errors, and an
`sse` block are reported. Other types leave out more: a `graphql` request is always a `POST`, so `method` has no
meaning, and a `websocket` api opens with a `GET` and no body, so neither `method` nor `body` has one.

## Wrong

```yaml wrong V2213 title="services/catalog/catalog.api.yaml"
type: graphql
apis:
  - id: listProducts
    method: POST
    body:
      query: 'query ListProducts { products { id name } }'
```

## Right

```yaml title="services/catalog/catalog.api.yaml"
type: graphql
apis:
  - id: listProducts
    body:
      query: 'query ListProducts { products { id name } }'
```
