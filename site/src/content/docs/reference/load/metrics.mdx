Every iteration of a mix test is one sample; the metrics summarize those samples.

```console
latency p50 3.7 ms · p90 8.4 ms · p95 9.9 ms · p99 22.9 ms · max 50.9 ms
```

## Syntax

| Metric | Measures | Threshold value | Live line | Summary | `--json` field |
| --- | --- | --- | --- | --- | --- |
| `p50` | Median iteration time | duration (`lt: 200ms`) | yes | yes | `p50Ms` |
| `p90` | 90th percentile | duration | no | yes | `p90Ms` |
| `p95` | 95th percentile | duration | yes | yes | `p95Ms` |
| `p99` | 99th percentile | duration | yes | yes | `p99Ms` |
| `max` | Slowest iteration | duration | no | yes | `maxMs` |
| `errorRate` | Failed iterations ÷ iterations | rate (`lt: 1%` or `lt: 0.01`) | as an `errors` count | as an `errors` count | `errors`, with `iterations` |
| `rps` | Iterations per second | number (`gte: 100`) | yes | yes | `rps` |

The live line leaves `p90` out; the summary and the JSON have it.

## Examples

### The live line

One line a second, on stderr. `rps` is the iterations per second over the last 3 seconds, so one slow second does not make it jump; latency, over the last 10 seconds, is rounded to whole milliseconds; `breaching:` appears only when a threshold is breached on the last 10 seconds:

```console
    4s  3 users  1286 rps  p50 1 ms  p95 2 ms  p99 3 ms  0 errors  breaching: p99, sample.basics#getsCreatedUser: p95
```

## How it behaves

- **A sample is an iteration, not a request.** A test with three steps is one sample, timed over all three. `rps` is iterations per second.
- **Setup isn't sampled.** Requests from `beforeAll`, `beforeEach` and `before` are not samples. See [Lifecycle in load runs](/vc-rs/reference/load/lifecycle/).
- **Think time isn't latency.** The pause from [`thinkTime`](/vc-rs/reference/load/thinktime/) is not counted in any latency metric.
- **Errors.** An iteration fails when a check fails (which checks count depends on [`checks`](/vc-rs/reference/load/checks/)) or a request fails. An iteration that passes only on a [`retry`](/vc-rs/reference/syntax/retry/) counts as an error too, blamed on the call that failed its last failed attempt. The summary's `errors` lines group failures under the test that failed, by the api of the call that failed, the status it got and the failure's code, as `  errors sample#listUsers 200 V5101 × 10`; a `before` call or cleanup around it is never blamed. The JSON has the same groups in `errorKinds`, as `{api, test, status, code, count}`.
- **Per test.** The summary gives each test of the mix a `test` line with its own iterations, `rps`, errors and latency; the JSON has them in `tests`. A mix entry's thresholds are measured on the same numbers.
- **Scope.** Scenario thresholds use every mix test together; a mix entry's thresholds use that test's samples only.
