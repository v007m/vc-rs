`name` is a human label. The `id` is what tools and other files use; the `name` is a sentence for people. It is always optional.

```yaml title="services/tagged/flows.test.yaml"
tests:
  - id: listsUsers
    name: Lists every user
    call: tagged#list
```

## Syntax

| Where | Type | Default | Required | Notes |
| --- | --- | --- | --- | --- |
| Top of an api or test file | string | — | no | Describes the file |
| `apis` entry | string | — | no | `vc import openapi` fills it from the operation summary |
| `tests` entry | string | — | no | Used by `vc check --fix` to derive a better ID |

`name` is plain text, not a template. A `${...}` inside it is kept as written and never resolved.

## Examples

### Names on a file, an api and a test

```yaml title="services/sample/sample.api.yaml"
id: sample
name: Demo service built into Vibranium
baseUrl: ${var.sampleUrl}
apis:
  - id: listUsers
    name: List users
    path: /users
```

```yaml title="services/tagged/flows.test.yaml"
tags: [users, smoke]
tests:
  - id: listsUsers
    name: Lists every user
    call: tagged#list
  - id: listsSlowly
    call: tagged#list
    tags: [slow-network]
```

### Where the name shows up

`vc list tests` prints it after the ID. A test without a name shows just its ID and tags.

```console
$ vc list tests tagged.flows
tagged.flows#listsUsers  Lists every user  [users, smoke]
tagged.flows#listsSlowly  [users, smoke, slow-network]
tagged.flows#listsNightly  [users, smoke, nightly]
```

A run prints it after the test's label, joined by a dash:

```console
$ vc run tagged.flows#listsUsers
✓ tagged.flows#listsUsers — Lists every user                      4ms
```

`--grep` (`-g`) matches the name as well as the full ID, ignoring case:

```console
$ vc plan -g "every user"
plan  1 test in 1 file · profile default
tagged.flows
  tagged.flows#listsUsers
```

### Names written by the OpenAPI importer

`vc import openapi` turns each operation's summary into a `name`:

```yaml title="services/pets/pets.api.yaml"
apis:
  - id: listPets
    name: List pets
    path: /pets
    operationId: listPets
```

### Names help `--fix` rename a test

When a test ID is not camelCase, V4001 suggests a new ID. If the test has a `name`, the suggestion is built from it:

```yaml title="services/layer/named.test.yaml"
tests:
  - id: Lists_Twice
    name: Rejects a declined card
    call: sample#listUsers
```

```console
$ vc check services/layer
warning[V4001]: test ID `Lists_Twice` is not camelCase
 --> services/layer/named.test.yaml:5:9
  |
5 |   - id: Lists_Twice
  |         ^^^^^^^^^^^ rename it
  = help: test IDs are camelCase: `rejectsADeclinedCard`
  = fix: Rename to rejectsADeclinedCard (certain)
```

`vc check --fix` applies the rename and updates every reference.

## How it behaves

- `name` never changes what runs. Two tests can share a name; they cannot share an ID.
- Selectors, reports and history key on the ID, not the name. Renaming a test's `name` keeps its history.
- The name appears in `vc list` and is searched by `--grep`. In a run it follows the full ID; it never replaces it.
- A file's name shows in `vc list files`, the HTML report's file list (`tagged.flows — User flows`), CTRF's `extra.fileName` and a `name` property of the JUnit testsuite.
- A test's name shows after its label in the console and the HTML report, as `name` in the json reporter's `testFinished` event, as CTRF's `extra.name` and as a `name` property of the JUnit testcase.

## Common errors

`name` has no errors of its own. A value that is not text is error V2302:

```console
$ vc check
error[V2302]: expected text, found a list
 --> services/layer/named.test.yaml:9:11
  |
9 |     name: [a, b]
  |           ^^^^^^ expected text
```
