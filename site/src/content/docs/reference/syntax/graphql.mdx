A file with [`type: graphql`](/vc-rs/reference/syntax/type/) holds GraphQL apis. Each one sends its `body.query` as a JSON `POST`, and the response is read as any HTTP response is. The file's `graphql` block sets the defaults for its apis.

```yaml title="services/accounts/accounts.api.yaml"
type: graphql
baseUrl: ${var.baseUrl}
graphql:
  path: /api/graphql
apis:
  - id: getUser
    body:
      query: 'query GetUser($id: ID!) { user(id: $id) { id name } }'
      variables:
        id: ${var.userId}
```

## Syntax

On the api file:

| Field | Type | Default | Required | Notes |
| --- | --- | --- | --- | --- |
| `graphql.path` | template | `/graphql` | no | The `path` of each api in the file that sets none. Only on a `type: graphql` file; elsewhere it is V2213 |
| `graphql.schema` | `$file` | none | no | The schema the file's documents are checked against: `{$file: schema.graphql}` names an SDL file (`.graphql`, `.gql` or `.graphqls`) or an introspection result (`.json`) next to the api file |

In the `body` of a `graphql` api:

| Field | Type | Default | Required | Notes |
| --- | --- | --- | --- | --- |
| `query` | text or `$file` | — | yes | The GraphQL document, a query or a mutation, sent as written; `{$file: getUser.graphql}` reads it from a `.graphql` or `.gql` file next to the api file |
| `variables` | map of templates | `{}` | no | Sent as `variables`; this is where `${…}` values go |
| `operationName` | text | the only operation | no | Sent as `operationName`, only when set. Names an operation of the document; needed when it holds more than one. Written as is, never a template |

In the `expect` of a `graphql` api, or of a test or step that calls one:

| Field | Type | Default | Required | Notes |
| --- | --- | --- | --- | --- |
| `errors` | `none`, `any`, a list of errors, or a matcher | not checked | no | The response's GraphQL `errors`. An expected error writes `message`, `path`, `code` (its `extensions.code`) or `extensions`, each a literal or a matcher. Elsewhere it is V2213 |

A `graphql` api is always a `POST`, so it takes no `method`. A test or step that calls it takes no `body`, nor does a test whose `call` steps reach it inherit one; it changes the operation through `vars`. Any other `body` key is V2213.

## Examples

### A query with variables

The api's vars fill its `variables`, and a test sets the vars.

```yaml title="services/accounts/accounts.api.yaml"
type: graphql
baseUrl: ${var.baseUrl}
apis:
  - id: getUser
    vars:
      userId: "1"
    body:
      query: |
        query GetUser($id: ID!) {
          user(id: $id) { id name }
        }
      variables:
        id: ${var.userId}
    expect:
      body:
        match:
          data.user.id: ${var.userId}
```

```yaml title="services/accounts/users.test.yaml"
tests:
  - id: getsSecondUser
    call: accounts#getUser
    vars:
      userId: "2"
```

The request body is:

```json
{"query": "query GetUser($id: ID!) {\n  user(id: $id) { id name }\n}\n", "variables": {"id": "2"}}
```

### A document in its own file

`$file` reads the document from a `.graphql` or `.gql` file next to the api file, so an editor can highlight and check it.

```graphql title="services/accounts/getUser.graphql"
query GetUser($id: ID!) {
  user(id: $id) { id name email }
}
```

```yaml title="services/accounts/accounts.api.yaml"
type: graphql
baseUrl: ${var.baseUrl}
apis:
  - id: getUser
    body:
      query: {$file: getUser.graphql}
      variables:
        id: ${var.userId}
```

### One api on its own path

An api's own `path` wins over the file's `graphql.path`.

```yaml title="services/admin/admin.api.yaml"
type: graphql
baseUrl: ${var.baseUrl}
apis:
  - id: listAuditEvents
    path: /admin/graphql
    body:
      query: 'query ListAuditEvents { auditEvents { id at } }'
```

### Checking the errors

A GraphQL server answers `200` with partial `data` and an `errors` list when part of a query fails. Nothing checks `errors` unless `expect.errors` does, so this test pins down the one error it expects.

```yaml title="services/accounts/accounts.api.yaml"
type: graphql
baseUrl: ${var.baseUrl}
apis:
  - id: getSecretNote
    body:
      query: 'query GetSecretNote($id: ID!) { user(id: $id) { name secretNote } }'
      variables:
        id: "2"
```

```yaml title="services/accounts/privacy.test.yaml"
tests:
  - id: hidesSecretNote
    call: accounts#getSecretNote
    expect:
      status: 200
      errors:
        - code: FORBIDDEN
          path: user.secretNote
          message: {contains: not allowed}
      body:
        match:
          data.user.secretNote: null
```

`errors: none` expects no errors and `errors: any` at least one. A matcher checks the list as a whole: `{some: {code: TIMEOUT}}` passes when one error has that code, and `{length: 2}` when there are two. Only `every`, `some` and `none` look at each error, so an expected error goes under one of them or in a list; `not`, `allOf` and `anyOf` still see the whole list, as in `{not: {some: {code: TIMEOUT}}}`. An expected error written straight on the list, such as `errors: {code: FORBIDDEN}`, is V2306, and so is a value that checks nothing (`errors: null`, `false`, `0`) or anything but an expected error under `every`, `some` or `none`.

## How it behaves

- The path is the api's own `path`, else the file's `graphql.path`, else `/graphql`, after `baseUrl` as for any api.
- The `query` is literal text, never a template: a `${…}` in it is sent as written, and `vc check` reports nothing about it. Values reach the document only through `variables`, so a var's value can never change the query itself. `operationName` is literal too, so a `${…}` in it is V2302.
- `query: {$file: getUser.graphql}` reads the document from a file, relative to the api file. The path is literal and must end in `.graphql` or `.gql`, and the map takes no other key (else V2302); a file that does not exist is V2004.
- `vc check` parses the document, inline or from its file. A syntax error is V1014, underlined at the token where the parser stopped. With a `graphql.schema`, the document is checked against it too (below).
- `graphql.schema` names the service's schema, relative to the api file: SDL, or the answer to an introspection query saved as JSON (`{"data": {"__schema": …}}` or `{"__schema": …}`), read as the same schema. The path is literal and must end in `.graphql`, `.gql`, `.graphqls` or `.json`, and the map takes no other key (else V2302); a file that does not exist is V2004. An SDL file must hold only type definitions, which validate: an operation or a fragment in it, a type it uses but never defines, or no `Query` type is V1015, and a syntax error is V1014. A JSON file without `__schema`, without its `types` list, or with a type that is not what an introspection result holds (an object with no fields, a kind that is not one) is V1015, underlined at the value that is wrong. A schema file several api files name is reported once, and one under `datasets/` is not a dataset.
- With a schema, each api's document is checked against it, as a server would (V2314): a field its type does not have (the type's close field is the fix), a required argument left out, a variable passed where the argument takes another type, a selection on a field that returns a scalar. Each literal value in `variables` is checked against the type the operation declares for it (V2315), so `limit: "3"` for an `Int` is an error and `limit: 3` is not; a value with a `${…}` in it is known only at run time and is not checked.
- `operationName` must name an operation of the document, and is needed when it holds more than one (V2009). The operation must be a query or a mutation; subscriptions are not supported yet. A document with no operation (only fragments or type definitions), or with two operations of one name, is V2009 too.
- `variables` must give a value for each variable the operation declares as non-null with no default (`$id: ID!`), an error (V2108). A value for a variable the operation does not declare is a warning (V2109), since the server ignores it; the fix is the close declared name. A `variables` written as one template, such as `variables: ${var.filters}`, is not checked.
- An operation without a name is a warning (V4010): the name shows in the server's logs and traces. The fix names it after the api, so `getUser` gets `query GetUser`, when the document holds that one operation and no other api uses it. A `.graphql` file shared by several apis is reported once.
- `variables` is always sent, `{}` when unset. Its values are templates, so an unset var in it is V2101.
- `content-type: application/json` and `accept: application/graphql-response+json, application/json;q=0.9` are added only when no level (config, api file, api, test or step) sets that header. A header you set is sent as written, so a test can send a wrong `content-type` on purpose to see how the server answers.
- Auth, `headers`, `query`, `http.retry`, `timeout`, `expect`, `save`, `saveOn`, `cleanup` and request hooks work as they do on an `http` api.
- A `200` with `errors` passes unless `expect.errors` says otherwise. In the list form, the response must have as many errors as the list has entries, and each expected error is paired with its own error, in any order: `[{code: FORBIDDEN}, {code: FORBIDDEN}]` needs two such errors, and one error never fills two entries. Use `some`, `every` or `none` to match loosely. The keys an expected error leaves out are not compared. A failed list shows the errors with their `count` when the counts differ, or with the expected errors no error was left for (`unpaired`). Errors are compared with `path` dotted (`["user", "notes", 0]` reads `user.notes[0]`; a key that is not a name is quoted, `["a.b"]`, or `['say "hi"']` when it holds `"`; quoted keys have no escapes, so a key holding both quotes does not read back) and `code` read from `extensions.code`. Write an expected `path` dotted too: a list is V2306, and `vc check --fix` rewrites it when every part is text or a whole number. A key other than `message`, `path`, `code` and `extensions` is V1004, and a failed check is V5123. A body that is not a JSON object, or whose `errors` is not a list, fails the check; a body without `errors`, or with `errors: null`, has none.
- A response with `errors` holds back the api's default `save` and its `cleanup`. With no `saveOn` written, `save` runs only when the status matches and the response has no errors; an explicit `saveOn` is status only, so `saveOn: 200` saves whatever the errors. `cleanup` is registered only for a response without errors. Each such skip is warning V5129 (not one a failed check held back anyway), and when no errors check ran, the step's own or one it inherits from its api, its errors are listed in warning V5128, each as `CODE at path: message`. Under load with `checks: api`, the step's own `expect.errors` does not run, so the errors are listed. A passing `expect.errors` asserted them, so it is silent.
- A `2xx` response whose body is not a JSON object with `data` or a non-null `errors` fails the step (V5124), even without `expect.errors`, and shows with any other check that failed, in place of an `expect.errors` that cannot be judged on that body; it usually means a wrong path. Another status is left to the status check, since a GraphQL server answers `400` to a document it cannot run.
- `errors` is one check, so a test's `errors` replaces its api's, as `status` does. A test-level `errors` reaches each step, so it is V2213 when a step without its own calls an `http` api (a step whose `expect` has `replace: true` inherits nothing, so it does not count); so is `errors` in a `flow` auth step.

```yaml wrong V2213 title="services/catalog/catalog.api.yaml"
type: graphql
baseUrl: ${var.baseUrl}
apis:
  - id: listProducts
    method: POST
    body:
      query: 'query ListProducts { products { id name } }'
```

```console
$ vc check services/catalog
error[V2213]: `method` does not apply to a `graphql` api
```

## Common errors

| Code | When |
| --- | --- |
| [V1005](/vc-rs/reference/diagnostics/v1005/) | A `graphql` api has no `body.query` |
| [V2213](/vc-rs/reference/diagnostics/v2213/) | `method` on a `graphql` api; a `body` key other than `query`, `variables` and `operationName`; `body` on a test or step that calls one, or on a test whose steps call one; a `graphql` block on a file that is not `type: graphql`; `expect.errors` on an `http` api, a test-level one that reaches an `http` step, or in a `flow` auth step |
| [V1014](/vc-rs/reference/diagnostics/v1014/) | The document, or an SDL schema file, does not parse |
| [V1015](/vc-rs/reference/diagnostics/v1015/) | The `graphql.schema` file is SDL that holds an operation or a fragment or does not validate, or JSON that is not an introspection result |
| [V2314](/vc-rs/reference/diagnostics/v2314/) | The document does not fit the schema: an unknown field, a missing required argument, a variable of the wrong type, a selection on a leaf |
| [V2315](/vc-rs/reference/diagnostics/v2315/) | A literal value in `variables` does not fit its variable's type in the schema |
| [V2009](/vc-rs/reference/diagnostics/v2009/) | `operationName` names no operation of the document; several operations and no `operationName`; no operation; two operations of one name; a subscription |
| [V2108](/vc-rs/reference/diagnostics/v2108/) | A non-null variable with no default is missing from `variables` |
| [V2109](/vc-rs/reference/diagnostics/v2109/) | A value is given for a variable the operation does not declare (a warning) |
| [V4010](/vc-rs/reference/diagnostics/v4010/) | The operation has no name (a warning) |
| [V2302](/vc-rs/reference/diagnostics/v2302/) | A `query` that is neither text nor exactly a `$file` of a literal `.graphql` or `.gql` path; a `graphql.schema` that is not exactly a `$file` of a literal `.graphql`, `.gql`, `.graphqls` or `.json` path; an `operationName` that is not text or holds a `${…}`; `errors` set to a word other than `none` and `any` |
| [V2101](/vc-rs/reference/diagnostics/v2101/) | A var in `variables` that nothing sets |
| [V1004](/vc-rs/reference/diagnostics/v1004/) | An expected error writes a key other than `message`, `path`, `code` and `extensions` |
| [V2306](/vc-rs/reference/diagnostics/v2306/) | An expected error written straight on the list instead of under `every`, `some`, `none` or in a list; a value that checks nothing (`null`, `false`, `0`), or anything but an expected error under `every`, `some` or `none`; an expected `path` written as a list |
| [V5123](/vc-rs/reference/diagnostics/v5123/) | The response's errors do not match `expect.errors`, or the body is not a GraphQL response |
| [V5124](/vc-rs/reference/diagnostics/v5124/) | A 2xx response whose body is not a GraphQL response: the endpoint is likely wrong |
| [V5128](/vc-rs/reference/diagnostics/v5128/) | Warning: the response has GraphQL errors and no errors check ran, the step's own or one inherited from its api |
| [V5129](/vc-rs/reference/diagnostics/v5129/) | Warning: the errors held back the api's default `save` or its `cleanup` |
