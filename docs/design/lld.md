# Vibranium v2 — Low-Level Design (Rust)

Oct 23, 2026 · @Sarath

This is the build plan for the Vibranium v2 engine and its interfaces in Rust. It turns the Technical Design (architecture), the Syntax Reference (file formats) and the CLI and Developer Workflow doc (commands) into crates, types, algorithms and milestones precise enough for coding agents to implement one milestone at a time. Where this document and those disagree, those win on behaviour and this one wins on structure.

**Who reads it.** The coding agents that write the code, and Sarath, who reviews it without reading Rust day to day. Every section opens with what the part does in plain words; Rust appears only where the exact shape matters (types, trait signatures, schema), and each snippet is annotated.

**Rust for a TypeScript reader.** The snippets use a small set of ideas:

| Rust | Read it as (TypeScript) |
| --- | --- |
| `struct Api { id: ApiId, path: Template }` | `interface Api { id: ApiId; path: Template }` (a plain data shape) |
| `enum Body { Json(Value), Text(String), None }` | A tagged union: `{ kind: "json", value } \| { kind: "text", text } \| { kind: "none" }` |
| `Option<T>` | `T \| undefined` |
| `Result<T, E>` | A return value that is either `T` or an error `E`; no exceptions are thrown |
| `Vec<T>` / `IndexMap<K, V>` | `T[]` / a `Map` that keeps insertion order |
| `Arc<T>` | A shared, read-only reference to `T` (like passing an object around in JS, but immutable) |
| `trait Transport { async fn send(&self, r: Request) -> Result<Response> }` | `interface Transport { send(r: Request): Promise<Response> }` |
| `pub struct UserId(Sym)` (a "newtype") | A branded type: `type UserId = string & { __brand: "UserId" }` |
| `mpsc::Sender<Event>` | One end of a queue another task reads from (like posting to a worker) |
| `#[derive(Serialize)]` | Generated JSON conversion |

Versions named below were current on 23 October 2026 and are pinned in `Cargo.lock`; the Rust toolchain is installed with rustup and pinned in `rust-toolchain.toml` (1.99, edition 2024) (D98). The licence is Apache-2.0 (D35); the feasibility spike's MIT header does not carry over.

## Workspace and crates

One Cargo workspace builds one binary, `vc` (installed also as `vibranium`, a small launcher in `vc-cli` that runs the `vc` beside it), which contains the CLI, terminal UI, MCP server and local web server. Code is split into small crates so each layer can be tested alone and the dependency direction can be checked by machine. Apps sit on the outside, the `engine` facade in the middle, pure logic underneath, and adapters plug into the interfaces. Each crate's package name is `vc-<dir>` (`crates/model` is `vc-model`); adapters are `vc-adapter-<x>` (D102).

## Design rules and quality gates

The feasibility spike showed that Rust's borrow checker stays out of the way when data flows in one direction and shared data never changes. These rules make that the default, and the gates make breaking them fail CI rather than depend on review.

### Rules for the code

1. **The compiled program is read-only.** The compiler produces one `Program`; after that it is wrapped in `Arc` and never changes. Everything that varies during a run (saved values, cleanup stacks, statuses) lives in executor frames owned by one task each.
2. **Refer by ID, not by reference.** IR nodes point at each other with typed IDs (`ApiId`, `TestId`, `ActionId`) looked up in the program's tables, never with Rust references or pointers between nodes. No lifetimes appear in any public API.
3. **Talk through queues.** Long-lived parts (the history writer, the hook engine, reporters, the UI event stream) run as their own tasks and receive messages; nothing else touches their state.
4. **Locks only on the allow-list.** Exactly two files may hold a lock: the `TokenCache` (a mutex map of slots, never held across an `await`) and the `Redactor` (`arc-swap`). Shared lifecycle slots are `OnceCell`s, not locks (D113).
5. **No globals.** No `static mut`, no global registries; dependencies are passed in through constructors (the `engine` crate wires them).
6. **No panics in library code.** `unwrap`, `expect`, `panic!`, `todo!` and `dbg!` are denied by lint; errors are values (`Result`) with a diagnostic code where a user can act on them.
7. **Kinds are registries, not `match` on strings.** Matchers, pipes, auth types, reporters, importers and notifiers register by name in a table built at start-up, so adding one touches one file plus one registry line (the *Refactoring* "switch statements" and "shotgun surgery" smells).
8. **Distinct types for distinct things.** IDs, durations, sizes and file paths are newtypes, not bare strings or numbers.
9. **Small functions.** At most 40 lines, cognitive complexity at most 10, at most 3 parameters excluding `self` (group the rest into a context struct) (D109). Methods of an `impl` of a trait declared outside the workspace (std or a third-party crate, such as rquickjs's `Resolver::resolve`) are exempt from the parameter limit, since upstream fixes their signatures (D189).
10. **Small files and traits.** A source file has at most 400 lines and a trait at most 7 methods; generated and test files are exempt (D114).
11. **A facade per crate.** Library crates keep their modules private and `pub use` the public items in `lib.rs`; no `pub mod`, except in the generated `vc-contracts`.
12. **Inject trait objects.** Stored dependencies are passed as `Arc<dyn Trait>`; async methods use `async-trait`, because `async fn` in a trait is still not dyn-compatible on Rust 1.99 (checked at M0). A parameter used only during the call takes a generic or `impl Trait` (D115, D158).
13. **Errors per crate.** Each library crate has its own `thiserror` enum; `anyhow` is used only in `vc-cli`.
14. **Contract suites.** Every interface trait has one contract suite in `vc-testkit`, and every adapter or fake that implements the trait runs it (D112).
15. **Conventional commits, tidy first.** `refactor:` commits stay apart from behaviour changes and never change test assertions; CI fails one that does (D116).

CI (D119): Ubuntu runs every gate; macOS and Windows build and run the tests; a nightly job runs full mutation testing and the wall-clock budgets. `scripts/gates-selftest.sh` applies one bad patch per gate and asserts that the expected gate rejects it, so a gate cannot silently stop working (D121). Smells no tool catches (naming, speculative generality, duplicated logic written differently) are covered by a ten-line review checklist in `CONTRIBUTING.md` that every PR description answers.

## Orchestration and design patterns

The execution workflow is run by an **orchestrator**: one component decides what happens next and holds the workflow's state, while workers only carry out the step they are given and report the result. Nothing in the system chains work by calling the next part directly (choreography), so the whole flow of a run can be read in one place, tested as a state machine, and changed without touching the workers.

&#91;embedded content: orchestration · orchestrators, strategies, events, ports\]

Orchestration is hierarchical, so each level stays small. Orchestrators and workflows decide; strategies and adapters act. All of them depend on interfaces (traits in `vc-interfaces`), never on each other's concrete types.

### The orchestrators and their state machines

| Level | Owns | States | Decides |
| --- | --- | --- | --- |
| `RunOrchestrator` (one per run) | the run's state, the shared `beforeRun` slots, the root cancellation token, the run cleanup list | `Planned → Preparing → Running → Draining → CleaningUp → Reporting → Finished(Passed \| Failed \| Cancelled)` | when files start, when to stop (bail, Ctrl-C, abortOn), the final status |
| `FileOrchestrator` (one per test file) | `beforeAll` slots, the file's cleanup list, the file's instance queue | `Waiting → Preparing → Running → CleaningUp → Done` | which instance starts next (under the concurrency limit), when `afterAll` runs |
| `InstanceWorkflow` (one per test instance) | the instance frame: saved values, cleanup stack, results | `Pending → Before → Body → After → Cleanup → Done(Passed \| Failed \| Blocked \| Flaky \| Skipped)` | retries of the whole instance, stop on the first failed step, blocked when a shared action failed (D126) |

Each state machine is an `enum` of states and a single `transition(state, input) -> (state, commands)` function. It is pure: no I/O, no clock. The orchestrator task feeds it inputs (results from workers, timer ticks, cancellation) and carries out the commands it returns (start an action, start a file, emit an event). Illegal transitions cannot be written, because each state only accepts the inputs that make sense for it. The transition functions are tested exhaustively with table tests and `proptest`.

```rust
// The instance workflow, simplified. Pure: inputs in, next state and commands out.
pub enum InstanceState { Pending, Before(Cursor), Body(Cursor), After(Cursor), Cleanup(Cursor), Done(Status) } // Status includes Skipped (D126)
pub enum InstanceInput { Start, Block(Failure), ActionDone(ActionOutcome), Cancelled } // the file orchestrator sends Start or Block (from the needs analysis) once beforeRun and beforeAll have finished (D122)
pub enum Command { RunAction(ActionId, OwnerKey), RunCleanup(PendingCleanup), Emit(Event), Finish(Status) }

pub fn transition(state: InstanceState, input: InstanceInput, test: &Test) -> (InstanceState, Vec<Command>);
```

**Cleanups are compensations (saga pattern).** Every successful call that changes data registers its compensating action (the api's `cleanup`). The orchestrator owning the frame runs compensations in reverse order when the frame ends, whether the work succeeded, failed or was cancelled. That is how a run leaves nothing behind without any test mentioning deletion.

### Where each pattern is used

A pattern is used where it removes a real coupling or a real `match`/`if` chain: two or more implementations exist, or a test needs a seam (YAGNI). The table is the complete list, so a reviewer can tell an intended pattern from an accidental one.

| Pattern | Used for | Why |
| --- | --- | --- |
| **Orchestrator + state machine** | `RunOrchestrator`, `FileOrchestrator`, `InstanceWorkflow`; also the load stage controller and the HAR import wizard | One place decides and holds state; workers stay simple and testable |
| **Saga (compensation)** | Api `cleanup` as compensating actions, run in reverse | Undo without tests describing it |
| **Ports and adapters** (hexagonal) | Every outside dependency is a trait in `vc-interfaces`: `Transport`, `AuthProvider`, `SecretProvider`, `HookRunner`, `HistoryWriter`, `HistoryReader`, `CacheStore`, `Reporter`, `Notifier`, `PluginHost`, `Importer`, `Clock`, `Random`, `Environment`, `FileSystem`, `SourceProvider`, `SourceWriter`, `CompileCacheStore`, `CommandRunner`, `Vcs`, `ConfigSource`, `ActionRunner`, `FileWatcher` | The core never knows which library sits behind it |
| **Strategy** | Action executors (call, test reuse, function, command); matchers; pipes; body encoders (JSON, form, multipart, file); retry and loop policies (sequential, parallel); the load mix selector; sync merge rules | Swap behaviour by kind without branching in the caller |
| **Factory and registry** | One registry per kind of strategy or adapter, filled at start-up: `ActionExecutors` (by action kind), `AuthProviderFactory` (by auth `type`), `ReporterFactory`, `NotifierFactory`, `ImporterFactory` (by source), `TransportFactory` (by URL scheme, ready for gRPC and WebSocket), `MatcherRegistry`, `PipeRegistry`, `LintRegistry` | Adding a kind is one new file plus one registration line; nothing else changes |
| **Builder** | `EngineBuilder` (the composition root that wires adapters into the engine); `ProgramBuilder` (the compiler accumulates, then `freeze()` gives the immutable `Program`); `RequestBuilder` (renders a request from an api, scope and auth); `PlanBuilder`; `Diagnostic::new(…)` with chained `label`, `help`, `fix`; test fixtures (`ProjectBuilder`, `ProgramBuilder::for_tests`); the SDKs' fluent builders | Objects with many optional parts are assembled step by step and checked once; required parts are enforced by typed builder states |
| **Facade** | The `engine` crate: `compile`, `plan`, `run`, `call`, `sync`, `query` | Apps depend on one small surface |
| **Observer (publish/subscribe)** | The event bus and its subscribers: history writer, reporters, console, TUI, web UI, MCP | Producers never know who listens |
| **Chain of responsibility (middleware)** | The request pipeline as `tower` layers: timing → retry (`refreshOn`, `http.retry`) → auth → `beforeRequest` hooks → per-host limit → timeout (per attempt) → transport (D134, D141) | Each concern is one layer, composable and testable alone |
| **Decorator** | `CachingAuthProvider` (the token cache around any provider); `CachedExecutor` (the cross-run cache around the `call` and `test` executors); `RedactingSink` around every outward stream; `RecordingTransport` and `FaultyTransport` in tests | Add behaviour without changing the wrapped type |
| **Command** | Engine API operations; `parser::edit` changes as `EditCommand`s that produce `TextEdit`s and can be inverted (undo in the web editor) | Operations become values: logged, previewed, undone |
| **Interpreter and composite** | Templates and pipes; CEL behind `Expr`; matchers composed with `allOf`, `anyOf`, `not`, `every` | Small languages evaluated without running user code |
| **Visitor** | Walks over the `Program` for linking, lints and the planner's needs analysis (`Visit` trait with default no-op methods) | New analyses without editing the IR types |
| **Specification** | Run selection: IDs, globs, paths, tags, grep, changed and failed as composable predicates | Selectors combine freely ("or" for positional, "and" for flags) |
| **Repository** | `HistoryReader`/`HistoryWriter`, `CacheStore` with SQLite implementations (a Postgres one stays possible behind the same traits, D253) | Storage swappable; queries named by intent |
| **Null object** | `NoAuth`, `NoopReporter`, `NoHooks` | No `Option` checks scattered through callers |
| **Singleflight (memoization)** | Shared lifecycle slots and the token cache | Concurrent callers share one execution |
| **Flyweight** | Interned strings (`Sym`) for every ID and name | Small, cheap-to-copy IDs across a large program |

### Rules that keep coupling loose

- **Depend on interfaces.** Core crates take `Arc<dyn Trait>` through constructors, and generics or `impl Trait` only for call-scoped parameters (D158); only `EngineBuilder` names concrete adapter types. `arch-tests` fails if a core crate's public signature mentions an adapter type.
- **Small interfaces.** Traits are split by who uses them (`HistoryWriter` for the writer task, `HistoryReader` for queries; `Transport` knows nothing of auth), so no consumer depends on methods it doesn't call.
- **Data crosses boundaries, behaviour doesn't.** Between crates only `vc-model` types (including `Plan` and `Event`, D103) and `vc-interfaces` traits are shared; no crate reaches into another's internals (`pub(crate)` by default).
- **Tell, don't ask, and no train wrecks.** Workers receive the data they need in the command; a function that reaches through `a.b().c().d()` gets that value passed in instead (Law of Demeter, enforced in review).
- **Composition over inheritance.** Behaviour is shared by composing strategies and decorators, never by deep type hierarchies or default-method templates.
- **Refactoring before extending.** When a change needs a `match` on a kind in a second place, it becomes a strategy with a registry ("replace conditional with polymorphism"). When a function grows past the limits, extract functions or a parameter object first, then add the feature.

## Core types

The `vc-model` crate holds the compiled program, and also the `Plan` and `Event` types (D103): plain data, no behaviour beyond lookups. Every other part reads it. One of those lookups is `Names` (`names.rs`, built from the `Arc<Program>` and the `Plan`), which turns the IDs in events into the text people see: a full test ID, an instance with its example row and repeat (`users.crud#rejectsBadEmail [row 2]`; a row with a `name`, kept in `Plan::row_names`, reads `users.crud#rejectsBadEmail › missing @`, with its number too when another row of the test has the same name (`› Bob [row 3]`), so each label is unique, and `vc run` masks these names with a redactor like its events' once the secrets are loaded (`examples::mask_labels`), before any reporter, the history or a watcher sees one; every instance of a test the plan repeats, by `repeat` or `--repeat`, carries `[repeat n]`), the `name` of a test, file or profile (`test_name`, `file_name_of`, `profile_name`; `titled` joins a label and a name as `label — name`), an action (`call users#get`), a frame or a source `Location`. It also keeps the plan's instances in plan order (`Names::planned`, each a `Planned { instance, test, example_row, repeat_index }`), which the server sends as `RunPlanned`; `check_label` gives a check's `expect` key (`body.match.items[*].price`). The reporters, the TUI and the server all label a run with it, so the same run reads the same everywhere. Its types are written by hand; the `vibranium.ir.v1` protobuf messages are separate hand-written `.proto` files (checked by `buf lint` and `buf breaking`), generated into `vc-contracts` and TypeScript, with `From` conversions in `vc-contracts`, so that the SDKs, plugins and web UI see the same shapes. Each proto is written when its first consumer needs it (D101).

## Compiler

The compiler turns the project's files into a `Program` or a list of diagnostics. It is pure: the engine reads the files through the `SourceProvider` trait and hands the compiler plain `SourceFile { path, text, hash }` values (a `vc-model` type), so the compiler never depends on `vc-interfaces`; the compiler returns the program or the diagnostics, plus a `CompileCache` value that the engine persists (D132). It runs on `vc check`, at the start of every run, on every keystroke in the editors (through the engine's `Check` call) and before any command writes a file. It collects every problem in one pass instead of stopping at the first.

### Stages

| Stage | Input | Output | Notes |
| --- | --- | --- | --- |
| Discover (engine, not compiler) | project root, `paths` globs | source texts with BLAKE3 content hashes, through `SourceProvider` | `vc-adapter-system` walks with `ignore` (respects `.gitignore`); file kind from the suffix (D132, D133) |
| Parse | changed files only | a marked tree per file (`parser::Node`, every node with its span) | `parser::parse(file, syntax, text) -> (Option<Node>, Diagnostics)`, where `Syntax::of(path)` picks `Json` for a `.json` suffix and `Csv` for `.csv` (one table) and `Yaml` otherwise. Both readers feed one syntax-neutral builder: maps keep key order and key spans, scalars keep their text, style and YAML 1.2 core kind; columns count characters, offsets count bytes, and only `\n` starts a line. YAML is read from `saphyr-parser` events; a node's span starts at the value, after any `&anchor` or `!tag`. The root is `None` after a scanner error (V1001; V1002 for structure; V1007 for an alias to a missing anchor) and when nesting goes deeper than 128 (V1011); an empty file gives a null root. Problems the tree survives keep it and are reported: V1006 duplicate key, V1007 alias, V1008 tag, V1009 non-text key, V1010 second document. Scanner errors are coded from saphyr's message through one table, with a test per entry. JSON is read by a hand-written reader, strictly to RFC 8259 (D148): no comments, no trailing commas, no `True` or `+1`, and full `\u` escapes with surrogate pairs. A syntax error stops it with V1001, spanned on the offending character, escape or token, with a `help:` (a trailing comma: "remove the comma after the last item"; a lone surrogate: write both halves). Strings are double-quoted scalars whose span includes the quotes; numbers, `true`, `false` and `null` are plain. Duplicate keys (V1006), nesting (V1011), the empty file and a leading BOM behave as for YAML. `Document` edits keep to the file's syntax: in JSON, text is always written double-quoted, other kinds only as JSON literals, and `insert_entry` refuses an object (it is a flow map). CSV is read for datasets only (D173), by the `csv` crate: a header row names the columns, and each record becomes a map from column to text (a double-quoted scalar spanning the record), so the root is a list of maps. A record with another number of cells, or text that is not UTF-8, is V1001; a column named twice is V1006 and keeps its first cells |
| Shape-check | marked trees | the leaves to compile, each with its type and the roots its spot sees, and the action ids the file declares | shapes are declared once (below). An empty file is an empty map. A diagnostic on a spot the parser already reported (an alias read as null) is dropped |
| Compile parts | the leaves | a `Piece` per leaf, keyed by its span: `Template`, `Value` (a `TemplateValue`), `Duration`, `Size`, `Matcher` (statuses become `Matcher::Status`; a templated status or `saveOn` becomes `Matcher::StatusOf`, whose rendered value is read at run time with the status grammar: a code as a number or text, a class, or a list of them; anything else fails the check), `Cel` | `template` crate. Template roots and pipes are checked against the roots the spot sees (V2105, V2102, V2305, V2308); a duration or size holding a template is V2301 (`timeout: ${var.wait}`; nothing renders it at run time, and auth `expiresIn`, which is rendered, is a template key). Units V2301, statuses V2303. A map with a matcher key is `Matcher::All` of its calls, anything else `Equals`, except a scalar at a unit spot (`size: 32b`, `total: 200ms`), which is an `eq` call read in that unit; `eq` and `ne` read their argument in the spot's unit as `gt` does, and a bare `0` is zero in any unit (any other bare number is V2301, with a certain fix adding `ms` or `b`); the matcher table checks each argument (V2306, a `regex` compiled unless it holds `${`), and an unknown key beside a matcher key is V1004. A map with no matcher key whose one key (five characters or more) is close to a matcher's name, case counted, is still `Equals` but warns V3208 (D276). A status map (`expect.status`, `saveOn`) is never a literal: each key must be a matcher (V1004) and it needs at least one (V2303). Each row of the matcher table says what the matcher does with a list: a scalar one (`gt`, `between`, `in`, `notIn`, `type`, `startsWith`, `regex`, `format` and the like) under a `[*]` key is V2306, also inside `not`, `allOf` and `anyOf`, which hand the list on, since the path yields a list. A single-key `$cel` map and each `expect.cel` entry go through `CelCompiler::check` (not `prepare`) with the scope's roots plus the file's action ids as step roots; whether a step id names a step that can run first is the linker's. Each scalar's `ScalarStyle` comes from the parser's style and its exact text |
| Link | all raw items | the `Program`: ID tables, references resolved, merged `expect`, test-level step defaults, var reachability | the only stage that sees every file at once; the program is built through `ProgramBuilder` → `freeze()` only when no file and no link check has an error |
| Lint | the linked trees and the `Program` | lifecycle diagnostics (V3xxx) and naming conventions (V4xxx) | runs in `link()` only once the program is built; each lint is a `Lint` (`code`, `check`) in a file of its own under `lint/`, listed once in `LintRegistry::builtin()` (lifecycle) or `LintRegistry::conventions()` (V4001–V4007, warnings, D180). A lint error (V3102, V3103) drops the program. A camelCase ID, tag or profile is judged by `naming` (`is_camel_id`, `camel_id`), which the creators share; a bad test or api ID's certain fix renames it and every reference to it, unless the new ID is taken |

**Incremental.** The `CompileCache` keeps, per file, its `FileUnit` (kind, tree, pieces and per-file diagnostics), keyed by path, content hash and `SourceFileId`, plus the `StringTable` the units' symbols point into; the compiler takes the previous one as input and returns the new one, and the engine reads and writes it as `.vibranium/cache/compile.bin` (D132). On the next run only changed files are parsed again; linking always runs over everything but is cheap (target: 1,000 files in under 100 ms warm, under 500 ms cold). `vc watch` reads and writes it on each run, as `vc run` does; the editor will keep it in memory. The blob starts with `VCCC` and the layout version (11, a little-endian `u32`), then the length of a header (a little-endian `u32`) and the header: the compiler release that wrote it (`CARGO_PKG_VERSION`), the string table in symbol order, and per file its path, hash, number and the byte length of its stored unit. Each stored `FileUnit` (tree and pieces) follows on its own, back to back in file order, so one that does not read back costs only that file. Header and units are `postcard` (D155): a compact binary serde format, with no field names or escaping to write or read. The JSON values inside templates (`Number`, literal arguments) are self-describing, which postcard cannot read back, so a binary format stores them as their JSON text; JSON output still shows them as they are. A unit must use all of its bytes. Lengths that do not add up to the blob read as a damaged blob. `vc check` saves the cache only when it remembers other files than the one it loaded, or would store other units (so a unit that did not read back is written again). Diagnostics are never stored: a unit that has any is stored without the unit, so its file is compiled again and reports them again. Any other version or release, a damaged blob, a path `SourcePath` refuses or a string table that does not re-intern to the same symbols reads as an empty cache, which only costs a full compile. So a warm run read back from disk re-runs the per-file stages of changed files only. Two caches are equal when they remember the same files and would store the same units. The entries are in path order, so a unit is found by binary search.

**Discovery and the cache blob (ports).** Both are synchronous traits in `vc-interfaces`, each with a contract suite and an in-memory fake in `vc-testkit` (`MemorySources`, `MemoryCompileCache`):

- `SourceProvider::discover(&SourceFilter) -> Result<Discovery, SourceError>` returns the definition files (names with a `FileKind`) in path order, each read and hashed by `source_file`, the paths of the project's other files (`assets`, not read; the excludes apply, the include globs do not, so `$file` can name a JSON body or schema anywhere in the project), plus one `SourceError` per file it could not use (unreadable, not UTF-8, a name a `SourcePath` refuses, a link out of the project); only a root that cannot be searched fails the call. `SourceFilter` holds the `paths.include` and `paths.exclude` globs (`globset`, `*` stays within one folder, an exclude that matches a folder drops everything in it); `.vibranium/` and `.git/` are always left out, and `node_modules/` unless the config writes its own excludes; include globs never leave out the root `vibranium.config.yaml`. `SourceProvider::read_bytes(&SourcePath)` returns one file's bytes, text or not, with the same checks as `read` (a link out of the project, a hidden file); before a run the engine reads with it, in `spawn_blocking` and each path once, the paths `vc_compiler::body_files` lists for the actions the run can reach (`body_files::reached`: `vc_planner::bodies` over the plan and, when any action has `cache:`, `bodies_from` every api's cleanup, which the sweep of an expired entry can run; `bodies_from` for one `vc call` or the cleanups `vc cache clear` runs), and passes the bytes as `Bytes`, or why not (`Unread::Templated` for a path holding `${…}`, `Unread::Refused` for a path the compile refused, `Unread::Failed` for a read that failed), in `RunInputs::bodies` (D272), so `check` and `plan` read none. The engine discovers with the default filter, reads the config's globs with the pure `vc_compiler::SourceGlobs::of`, and discovers again with `SourceFilter::written` only when the config writes `paths`; a glob that does not parse fails the check (`EngineError::Sources`).
- `SourceProvider::ignores(&SourcePath) -> bool` says whether the project's ignore files keep discovery from a path, there or not yet: `FsSources` walks only the folders on the way to it with discovery's walk, leaves out every path under a link to a folder (discovery never follows one, so a save cannot write through it into a left-out folder), and matches a path not there yet against the `.ignore` and `.gitignore` files above it (the nearest that matches decides; `.git/info/exclude` and global git excludes are not applied to a path not there yet). The default, for providers with no ignore files, leaves nothing out. The web UI's editor asks it before it opens or writes a file.
- `SourceProvider::read(&[SourcePath]) -> Result<Discovery, SourceError>` reads the files at the given paths, whatever their kind, in path order and each once, with the same problems per file (a missing file is `SourceError::Missing`, a file that is there but cannot be read a `Read` problem) and no assets; only a root that cannot be read fails the call. The engine reads with it the data and hook files a compile wants (`data_wanted`, `hooks_wanted`), which `discover` only lists.
- `CompileCacheStore::load() -> Result<Option<Vec<u8>>, _>` and `save(&[u8])` hold the opaque `CompileCache` blob. The engine treats a failed load or save as a notice (`warning:` on stderr), never as a failed check.
- `vc-adapter-system` implements them as `FsSources` (the `ignore` walker: `.gitignore` and `.ignore` respected even outside a repository, the user's global excludes not; links to folders not followed; a linked file read only when its resolved path is inside the root, otherwise `OutsideRoot`) and `FsCompileCache` (temp file, `sync_all`, rename; refuses to go through a link at `.vibranium`, `.vibranium/cache` or the blob). `find_project_root` walks up from the start folder to the first `vibranium.config.yaml`.
- The engine turns each discovery problem into a V1001 error on an empty placeholder file at that path, so it renders like any other diagnostic and the check fails.

**One declaration per file shape.** Each file kind's keys are declared once in Rust, with type, default, description and an example:

```rust
shape! {
    test = Shape::new("testEntry", "One test: a call or steps, with checks", &[
        key("id", Ty::Id).required().doc("Third-person verb, such as `rejectsDeclinedCard`").example("getsCreatedUser"),
        key("call", Ty::Ref).doc("The api to call").example("users#get"),
        key("steps", ACTIONS).doc("Several actions in order"),
        key("repeat", Ty::Int).default("1").doc("Run the whole test this many times"),
        // … one line per key in the Syntax Reference
    ])
    .mixins(&[request])
    .one_of(&["call", "steps"], Code::V2201)
    .scopes(&[("examples", Scope::EXAMPLES), ("repeat", Scope::LOOP)])
}
```

The tables are `const` data in `vc-compiler` (`shapes/`): a `Shape` has a title, a description, its keys, shared key sets it mixes in, an optional one-of group with its code and the roots its keys add for siblings (`examples`, `repeat`, `forEach`); a `Key` has a name, a `Ty`, `required`, a default, a description, an example and the scope it opens. `Ty` covers text, IDs, references, templates, integers, flags, durations, sizes, statuses, matchers, CEL, enums, lists, maps of a type, nested shapes and either-of. `shapes::reachable(root)` lists every shape a file reaches, breadth first.

The same declarations generate the shape-check stage, the JSON Schemas shipped for editors (`vc schema export`) and the keys tables of the docs (`key_tables(kind)`: one `| Key | Type | Default | Purpose |` table per reachable shape), so the docs, the editors and the checker cannot drift apart. Each schema is draft 2020-12 with `$id` `https://v007m.github.io/vc-rs/schema/<kind>.schema.json` (D258: the docs site publishes the repo-root `schema/`, and a compiler test fails when it differs from the export); the root is a closed object (`additionalProperties: false`, `required`, a one-of group as `oneOf` of `required`), nested shapes are `$defs` reached by `$ref`, and every property carries its description, its example under `examples`, and its default only when the declared default is a value of the key's type (a default such as "defaults.timeout" stays in the description).

### Linking in detail

1. **Symbol tables.** Every file ID, api ID, test ID, auth ID, profile, dataset and generator goes into a table. Each file has one ID namespace across kinds, so two items in one file with the same ID are V2001 with both locations, whatever their kinds; a reserved ID is V2006. Another file's items are referenced by full ID, `fileId#id`; a bare dotted word is always a file ID (D128, D138). File IDs are derived from paths; an explicit `id:` that differs is V2007, and two files with the same ID are V2001 (D139). The `CompileCache` keeps each file's content hash and last ID, so a moved file is recognised and V2003 can offer its new ID as a certain fix.
2. **References.** `call`, `test`, `cleanup.call`, `auth`, `$file`, `function`, `forEach` datasets and load `mix` entries are resolved; unknown ones are V2003 with "did you mean" from Damerau–Levenshtein distance (`strsim`) over the IDs of the right kind, ranked with same-file IDs first; the file ID and the item ID are measured apart: in the file the reference names, or else in the file IDs close to it, looked up across the whole project, only the item IDs are compared (so `people#nah` is not close to `people#echo`, `peolpe#getPerson` is close only to `people#getPerson`, and in `users.crud`, `users.admin#getsUser` is close to `users.admin#getsUsers`, not `users.crud#getsUser`); when none of those items is close, the item IDs of every file are compared (`users.crud#deletesUser` finds `users.admin#deletesUser`); only when no file ID is close (a bare ID that resolved to its own file) are whole IDs compared. A certain fix needs exactly one close ID, found in the named file or by whole ID for a bare ID; one found in another file is only a `help:`, as taking it would change the service called, and several give only a `help:`.
3. **Expect merge.** Checks are keyed by check kind plus leaf path. Levels merge api → test → step (the step wins), and the more specific level replaces a check with the same key; `custom` and CEL checks append instead. `expect: { replace: true }` drops the inherited checks. Every check carries its origin and source line (D123).
4. **Test-level step defaults.** A test's `auth`, `headers`, `query`, `body`, `poll` and `expect` are defaults for every `call` step, and the step's own value wins; a `test:` step takes none and runs the reused test as written, so those keys written on it are V3207 (D270). A body default that reaches a GET or HEAD step is V3205; a default no step uses is V3206. A test-level `save` reads the last step's response (D124).
5. **Var reachability.** For each template, the linker walks the levels that can supply a var at that spot (call vars, earlier saves in the same test, beforeAll saves under their action id, file vars, beforeRun saves, the api's defaults, the api file, config), separately for every profile. A `function:` or `test:` action may declare `provides: [x]`, and the linker trusts that declaration (D128). A var that no level provides for some profile is V2101, naming the profiles where it is missing and the places it could be set. A template root that is not available at that spot (D125) is V2105.
6. **Lifecycle graph.** `test:` reuse forms a graph; cycles are V2205 with the whole chain. Shared actions without an `id` are V2210.
7. **Types.** Pipes are checked against what each reference can hold (a `| number` on a value the api's schema says is an object is V2304). CEL is not type-checked until the interpreter has a checker (see Open questions).

The link stage (`link/` in `vc-compiler`) runs over every file's unit on each compile, cached or not. It reads the units' trees and pieces through a `Project` (the files with a tree, their path-derived file IDs, and tables of apis and tests by full ID) and runs in two tiers:

- **Always:** the ID tables (V2001, V2006, V2007), references (V2003 for `call`, `cleanup.call` and `test`; V2002 for `auth` and a file's `profiles` entries, against the config), `$file` paths (V2004, below), example columns (V2103: a `${example.x}` in a test whose `examples` is an inline list of maps, where no row has `x`; rows from a `$file` or a dataset are known only at run time), the keys each config `auth` entry's type needs (`link/auth_keys`: V1005 at its `type`, from `vc_model::AUTH_NEEDS`, the one table that `vc new auth` and the auth adapters' required keys also follow, with a test on each side), and V3101 when the config defines no profile. References into a file the per-file stages could not read cleanly are not reported, since its items may be missing.
- **Only when no file has an error of its own:** var reachability, `test:` cycles and shared actions without an `id`. The var walk follows run order: config vars, `beforeRun` (each action's saves shared under its `id`), then per test file its vars and `profiles`, `beforeAll` (shared the same way), `beforeEach`, and per test its vars, `before`, its call or steps, `after`. Every action's templates are checked with what ran before it plus its own vars; its `cache.check` is checked as an action that runs after it, so it also sees the action's saves, by name and under the action's `id` (`${var.admin.userId}`); an api's templates (and its file's) are checked at each call site with the api's and its file's vars added, and a diagnostic in them points back at the `call:` that reached them. A config `auth` entry of `type: flow` is walked as its `steps` (a block whose saves are plain names), then its `apply` and `expiresIn`, which see those saves. A level is a set of names for every profile plus names per profile; a var is V2101 for each configured profile no level sets it for, unless its first pipe takes a missing value (`default`, `PipeDef::takes_missing`). A name's type is known when every definition of it is a literal of one type, and only then are its pipes checked (V2304). A step root is V2105 unless an action with that `id` ran earlier in the same test or block: "not available here" when an action in the file or the config has that `id`, else "not a root or a step id" (`Roots::undeclared`), whose help lists the roots, with a note naming the steps that ran earlier and the one close name as a certain fix. Apis no test calls are not walked yet, and neither are load files.

The lint stage (`lint/` in `vc-compiler`) then runs over the same trees and the built program. M1 checks V3102 (a second `default: true` profile, with the first as a secondary label), V3103 (a blank `skip` reason, or `true` or `false` in its place, on a file or a test), V3201 (a `PUT`, `PATCH` or `DELETE` call, outside `beforeAll`, whose `vars`, `auth`, `headers`, `query` or `body` read `var.<id>` of a `beforeRun` or `beforeAll` action), V3202 (`cache` on an action in `beforeEach`, `afterEach`, `before`, the steps or `after`), V3203 (a `call`, step or `cleanup.call` to a `deprecated` api), V3205 (a test `body` reaching a GET or HEAD `call` step without its own `body`) V3206 (a test's `auth`, `body` or `poll` that every `call` step sets itself, a `headers` or `query` name every such step sets, or a test-level check no step's merged checks kept; a test whose steps are all `test:`, `function` or `command` uses none) and V3207 (`auth`, `headers`, `query`, `body`, `poll` or `expect` written on a `test:` action, which runs the reused test as written (D270); the certain fix removes the key when nothing else shares its first line). It also checks V2211 (`parallel` on an action without `repeat` or `forEach`; an `abortOn` metric that neither the scenario's nor a mix test's `thresholds` names), V2310 (a `headers` key on an api, its file, an action, the config's `defaults`, an auth flow's `steps` or `apply`, or in an `expect`, that is not an RFC 9110 token, a `${…}` template included), V2311 (a `redact.rules` `regex` that does not compile, with the regex engine's reason), V2302 for load values that do not fit together (`stages: []`, a `thinkTime.min` longer than its `max`) and V3104 (a `skip` whose `until` date is before today, on a file or a test; the certain fix removes the skip when it is written in block style on its own lines). The compiler stays pure: the engine reads today's date in UTC from the `Clock` port (`SystemClock`, or `FixedClock` in tests) and passes it in `CompileInput::today`; without one, V3104 is not checked. `until` is a `Ty::Date` (`YYYY-MM-DD`), so a malformed date is V2302. V3101 stays in the link stage and V3204 is the parser's. Apart from V3104 and V3207, none of these has a certain fix.

Each reference is reported once, at its first spot. A `$file` path (the value of a map whose only key is `$file`) is resolved against the folder of the file that holds it, after dropping a `#/pointer`, and must name a definition file or one of the discovery's `assets` (`CompileInput::assets`; `None` skips the check); a path that leads out of the project or names no file is V2004, with the close paths (written relative to that folder) as "did you mean", and a certain fix when exactly one is close. A path holding a template is known only at run time and is not checked. An api file's `source.openapi` path (`link/spec_files.rs`), relative to the project root, is checked the same way; a URL or a templated path is not. Generators are linked in `link/fakes` against the `FakeRegistry` of `vc-template` (D174): each config generator has exactly one kind (`fromRegExp`, `oneOf`, `int`, `lorem`; none is V1005, several or settings of the wrong shape V2302, a pattern the generator cannot follow V2309) and an ID that is not a Faker module (`person`; V2006). Every `${fake.…}` in a template is then either a built-in, whose literal arguments are checked (V2302, V2309), or a named generator, which takes none (V2302); any other name is V2002 with the close names as "did you mean" and the list of generators as a note, and a pipe on a generator's output type is checked as for any value (V2304). Datasets are linked in `link/data` (D173). A dataset is every `.csv`, `.json`, `.yaml` or `.yml` file under `datasets/` among the definition files and `assets`, named by its path below the folder with dots for slashes, no suffix and each word in camelCase (`datasets/users/seed.yml` is `users.seed`, `datasets/world-cities.csv` is `worldCities`), and every entry of the config's `datasets.files`, which wins over a folder file with the same ID. A `datasets.files` path is relative to the project root; one that leads out of it must be under one of `datasets.allowRoots`, compared after `.` and `..` are resolved (`SourcePath::data`), else V1012, as is a path that is not relative. The compiler does no I/O, so `Compiled::data_wanted` lists each data file it names but was not given (a dataset's file, with the allowed root it is under, and each literal `$file` an `examples` or `forEach` reads): the engine reads an outside file through `SourceProvider::read_outside`, which canonicalises the file and its root and reads the file only while it stays under the root, in no hidden folder below it and outside the project (a project file is read by its own path; else V1012, named by its path), passes it in `CompileInput::files` (a file of no kind is parsed and kept as data) and compiles again; the cache makes the second pass cheap. A given file that is not a list is V1002. Once the files are given, `${example.x}` in a test whose `examples` is a bare `${dataset.<id>}` or `$file` is checked against the rows' columns (V2103), and when `assets` lists the project, every `${dataset.…}` outside CEL must start with a dataset ID (V2002, with the close IDs as "did you mean"). A piped dataset (`${dataset.cities | take(3)}`) is read at run time. The moved-file fix for V2003 and the `function` references are not linked yet; V2005 (hook export) is linked with hooks in M4, and its golden case lands then.

When nothing is an error, `link/build` fills a `ProgramBuilder` (in `vc-model`: `new(strings, files)`, `intern`, one adder per table, `action(…) -> ActionId`, `freeze() -> Arc<Program>`) from the same trees and pieces. Every api's own checks are read first, by `ApiId`; then the config (its `defaults`, `vars`, `reports`, `redact`), its profiles and `beforeRun`/`afterRun` (owner `Run`), every api file (its group, its apis in file order, each `cleanup` as an action), and every test file (`beforeAll`/`afterAll` owned by the file, `beforeEach`/`afterEach`, `before`, `after` and steps by the instance). Checks are keyed as follows: `status`, `size` and body `equals` by kind alone; `headers` by the lower-cased name; `body.match` by its path (`items[*].price`); `timing` by phase; `cel` by label and `custom` by `path#export` (these two always append). A call action's checks are the api's, then (for a step) the test's, then its own, merged as in item 3; a `function` or `command` action keeps only its own, and a `test:` action builds no request, checks or poll at all, since it runs the reused test as written; V3207 reports any it writes. Test-level defaults reach `call` steps only, never `test:`, `function` or `command` steps (D124, D270). Headers and query merge by name over the test's; `auth`, `body` and `poll` replace. A test with `call` becomes one action whose checks carry the test's origin, while its vars and `retry` stay on the `Test`. The test-level `save` is added to the last step's saves, the step's own names winning. A body that is text is `Text`; a single-key `$file` or `$base64` map is `File` or `Base64`; anything else is `Json`. A literal `$file` path, the whole body's or one inside a map or list (a multipart part), is resolved from the folder of the file that names it, so the program holds its project path (`body_files::resolved`); `vc_compiler::body_files(program, actions)` lists, for each given action, each `$file` its body writes with its project path, or why it is not read (`Unreadable::Templated` for a path holding `${…}`, `Unreadable::Refused` for one that leads out of the project): the whole body's at the pointer `""`, and a map part's at `/name` or `/name/index` (`vc_model::file_parts` and `part_pointer`, the index counted before nulls are left out) whatever the `content-type`, since only the rendered header says whether the body is multipart; a `$file` map inside a JSON body is sent as written (D272). `poll` has no defaults: `until`, `every` and `timeout` are all required, so a missing one is V1005 (D156). A flag that is not written takes the default its shape declares, so a test is `standalone` unless it says `false`. `examples` becomes `Rows` for an inline list, and for a bare `${dataset.<id>}` or a `$file` map whose data file the compile was given; otherwise it is `File` for a single-key `$file` map and `Template` for a template such as `${dataset.capitals | take(3)}`. A template row source is read before the run starts, so it reads only `var`, `env` and `dataset` (`Scope::ROWS`, `Roots::only`; any other root is V2105, D125), and so must each var it reads: `link/examples` follows each as rendering looks it up (the `Scope::of_test` order: the test's vars, its file's, then the config's; a definition reading its own name continues at the next level out), through the definitions written without a profile, and a var only a save sets, or one that reads another root, is V2105 at `examples`, its help naming the var and the root (`vc_template::row_var_unread`). A save counts only at a level the lookup still reaches, so a config var reading its own name looks past the config, where no save is. A read whose first pipe takes a missing value (`default`) needs nothing when it is of a var only a save sets, or, inside a followed definition, of a `secret` (`vc_template::row_readable`, which the compiler and the executor both call), since before the run neither has a value and the render then gives the default. Every other root (an action's response, `run`, `item`, `iteration`, `example`) has no value at all before the run, which `default` does not stand in for, so it stays V2105. A defined var read with `default` is still followed, and `examples: ${secret.X | default(…)}` written directly stays V2105. The compiler, the executor and the engine find the reads with one walker, `TemplateValue::references` and `Template::references` in `vc-model`, each keeping its own policy on top. A profile's definitions are left to the engine, which runs `vc_executor::unread_var` under the run's active profiles before it renders and gives the same V2105 at the `${var.…}` in `examples`, so a profile-only read breaks only the runs that use that profile. A `$file` path holding a template is V2105 at `examples`; any key a `$file` of `examples` holds besides its path is V1004, since such a map is no row source. When some test's rows are a template, the engine asks the planner, in one pass, which selected tests it does not skip have template rows not yet counted (`vc_planner::rows_wanted`), so a test that is not selected or is skipped is never rendered; a `$file` the compile was not given is not rendered but refused when planned ("the example rows of `…` were not loaded"); renders those once (`vc_executor::example_rows`, against the test's, the file's and the config's vars under the run's profiles and `--set`, each test drawing from its own source, `ports::random_for(seed, full ID)`, so `--seed` gives a test the same rows whatever else the run selects and the run's fakes never shift them); plans once with the row counts (D132); and passes the rows to the executor (`RunInputs::with_examples`), which binds each row as data and never renders it again. Rows that do not render, or are not a list of maps, stop the run before it starts with V5111 (V5112 for a missing column). A test whose rows number zero, inline or loaded, is planned as skipped with the reason `NO_ROWS` ("examples gave no rows") in every plan, so `vc list` and the catalog show it as skipped; only a run adds a notice for it. An explicit `:n` on it stays `NoSuchInstance`. `vc list` renders no rows: it counts a test whose rows come from a template or file as one instance. Inline rows stay templates, rendered per instance, and may read every root a test's vars may. A `forEach` over a given dataset or `$file` becomes the literal list of its rows, so the loop runs over them. Each given dataset becomes a `Dataset { id, file, rows }`, its rows as JSON, which the executor binds as the `dataset` root. `repeat` and `forEach` on an action or step become its `Loop` (`parallel` is 1 when not written, and `forEach` wins when both are written); a test with `call` keeps its `repeat` on the `Test`, so its action gets no loop. The config's `http.retry` keys are laid over the D143 defaults into `Config::http_retry`; an api that writes `http.retry` gets `Api::http_retry`, its keys over the config's, and one that writes none gets `None`. Each config generator becomes a `GeneratorDef { id, fake, args }`: the built-in its kind calls and that call's arguments (`int: {min: 1, max: 5}` is `number.int(1, 5)`, `lorem: {words: 500}` is `lorem.words(500)`). The config's `auth` entries become `AuthDef`s and `secrets` and `redact.rules` go into `Config` (see Auth). A `body.schema` under an `expect` or `poll.until` is a `Schema` check whose matcher is the literal key of its schema in `Program::schemas` (D201): one written inline is held by `<file>:<line>:<column>`; a file (a bare string or a single-key `$file` map, relative to the file holding it) by its project path, with a `#/pointer` after it when one is written (`schemas/user.json#/definitions/user`). A named file the project lists is wanted like a data file, and once given its whole document is held by its path; a file not given, or whose path holds a template, is missing from the table. Not built yet: load files and `cache`.

### Diagnostics and fixes

```rust
pub struct Diagnostic {
    pub code: Code,                       // V2003
    pub severity: Severity,               // Info < Warning < Error; worst = max()
    pub message: String,                  // unknown api "orders#plcae"
    pub primary: Label,                   // span + short label under the caret
    pub secondary: Vec<Label>,            // other places involved (e.g. the earlier duplicate)
    pub notes: Vec<String>,               // = note: …
    pub help: Vec<String>,                // = help: …
    pub fixes: Vec<Fix>,
}

pub struct Fix {
    pub title: String,                    // Replace with orders#place
    pub certain: bool,                    // true: vc check --fix may apply it without asking per fix
    pub edits: Vec<TextEdit>,             // byte-range replacements, possibly across several files
}

pub struct TextEdit { pub file: SourceFileId, pub range: Range<usize>, pub new_text: String }
```

`Code` is a registry of associated consts (`Code::V2003`), each with its number, default severity and title, and a category (V1 to V5) derived from the number's first digit; `Code::ALL` lists them in numeric order and `"V2003".parse::<Code>()` looks one up. The table is the one under [Diagnostic codes](#diagnostic-codes); a failure or blocked result there has severity `Error`. Diagnostics are built step by step, taking the severity from the code:

```rust
Diagnostic::new(Code::V2003, span, "unknown api \"orders#plcae\"")
    .label("not defined").help("did you mean orders#place?")
    .fix(Fix::certain("Replace with orders#place", vec![TextEdit::replace(span, "orders#place")]))
```

A `Diagnostics` collection gathers them (`push`, `extend`, `has_errors`) and `sort()`s them for display by file-table order (the compiler adds files in path order), then position, then code. These types serialize with serde (camelCase keys, codes as `"V2003"`, severities in lowercase), but that is not the `vc check --json` shape: spans hold a `SourceFileId` index, which the JSON renderer replaces with the file path.

Diagnostics render through the `Render` trait (`render(&Diagnostics, &SourceFiles) -> Result<String, DiagnosticsError>`), in the order given, so callers `sort()` first. `TextRenderer` writes the rustc-style text shown in the CLI doc: `error[V2003]: message`, `--> path:line:col`, the excerpt with the primary span underlined `^^^` and its label, secondary labels underlined `---`, then `= note:`, `= help:` and `= fix: <title>`, with ` (certain)` after a certain fix. Excerpts are grouped by file, the primary's file first and the others in the order their first label appears: each file gets one location line (`-->` for the first, `::: path:line:col` for the rest) and its excerpts in line order, with `...` between disjoint ones. Labels in one file whose lines overlap, touch or are one line apart share one excerpt (a single line between them is shown, not elided), each underlined on its own row under the line, primary first. A span over more than four lines shows its first two lines, `...` and its last; a span ending at column 1 of a line (just past a newline) ends on the line before. Control characters and bidi controls in messages, labels, notes, help, fix titles, paths and source lines print as one column-wide control picture each (C0 as its own such as `␛`, DEL as `␡`, C1 and U+202A–202E, U+2066–2069, U+200E, U+200F, U+061C as the substitute picture `␚`), so a file cannot drive the terminal; `SourcePath` already rejects them, so this is defence in depth. Fix edits into a file missing from the table fail with `UnknownFile`, as in the JSON renderer. Colour is off unless `.color(true)` turns it on; the CLI decides (a terminal and no `NO_COLOR`). `JsonRenderer` writes the stable shape for `vc check --json`, editors and agents:

```json
{
  "summary": { "errors": 1, "warnings": 0, "infos": 0 },
  "diagnostics": [{
    "code": "V2003", "severity": "error", "message": "unknown api \"orders#plcae\"",
    "primary": { "span": { "path": "services/orders/checkout.test.yaml", "line": 4, "column": 11, "endLine": 4, "endColumn": 23 }, "text": "not defined" },
    "secondary": [], "notes": [], "help": ["did you mean orders#place?"],
    "fixes": [{ "title": "Replace with orders#place", "certain": true,
                "edits": [{ "path": "services/orders/checkout.test.yaml", "range": { "start": 57, "end": 69 }, "newText": "orders#place" }] }]
  }]
}
```

Lines are 1-based, columns 1-based in characters, and `endLine`/`endColumn` point just past the span; edit ranges are 0-based byte offsets. A span or edit naming a file not in `SourceFiles` is `DiagnosticsError::UnknownFile`, an internal error. The engine API carries the same data to the editors and the web UI, which show the same code, text and fixes.

### Editing files without reformatting them

Everything that changes a definition file (`vc new`, `vc rename`, `--fix`, `vc sync`, `vc skip`, HAR import, the web editor's form view, agents' `write_definition`) goes through one module, `parser::edit`. It takes the original text and its marked tree and turns structural changes (set a key, insert a list item, remove an item, rename a reference) into minimal `TextEdit`s on the original text, keeping comments, quoting and spacing everywhere else, and checks that the result parses again. New text is written in the house style (`vc fmt`): block YAML, two-space indent, keys in the documented order, templates unquoted unless YAML needs quotes. The guard lives in the engine: it compiles before and after every edit and refuses the edit if it would add an error (D107). Engine calls that change files return `Changes` (each `FileChange` with its path, text before and after, and a unified `diff()`); the engine compiles the project with them in place and refuses with `EngineError::Edit` when an error appears whose code and message the project did not already have. Apps show the changes, ask when they should, and hand them back to `Engine::write`, which writes through the `SourceWriter` port (`FsSources` in `vc-adapter-system`, which refuses a path that leads through a link out of the project). `Engine::fix` gathers the first certain fix of each selected diagnostic, skipping one whose edits overlap a fix already taken, for `vc check --fix`. `Engine::skip` and `Engine::unskip` add or remove the `skip` of a test (its last key) or of a test file (its first key, short form `skip: <reason>` or the `reason`/`until` map); an unknown ID is refused with the close ones (the planner's `closest`). `Engine::rename` renames an api or test ID (it keeps its file, and must be camelCase and free in the file's one namespace) or a file ID (lower-case dotted words), with `rename_refs` in every file that refers to it; a new file ID moves the file to the path the ID derives, under the same root folder and keeping an api file named like its folder, as a `FileChange` with `moved_from`, which `Engine::write` writes at the new path before `SourceWriter::remove` takes away the old one. A var, auth or dataset is named with its kind (`var.userId`, `auth.partnerToken`, `dataset.capitals`; that prefix wins over a file ID), each a `NameKind` entry in `rename_name.rs`: the new name keeps the kind's convention and is not in use anywhere, and every definition file gets the kind's `parser::edit` rename plus, for an auth or a dataset, the `id` of its entry in the config's `auth` or `datasets.files` list (`none` is never an auth's new name). `rename_var` renames the keys of every `vars` and `save` map and every `var.<name>` in a `${…}` reference (a path after it too) or in CEL (`expect.cel`, `$cel`), matching on the source text, where a name is spelled the same in any quote or block style, and never in a literal `$${…}`; `rename_dataset` renames `dataset.<id>` there but not `dataset.<id>.<more>`, another dataset; `rename_auth` renames each `auth: <id>` and `auth: {id: <id>}`. A dataset named by its path under `datasets/` is refused, since that means moving the file. `Engine::new_api`, `new_test`, `new_auth` and `new_file` (`vc new`) append an item, with one brief comment line above it, to the file its ID derives (`services/<words>/…`, a one-word api ID in a folder of its own), or create that file starting with `vc_compiler::schema_line` and a one-line description; an ID that breaks the convention is refused with the one `camel_id`/`file_id` suggests, a taken ID or an existing file is refused, and `new_file` never overwrites; a new load file also gets a `mix` of the project's first test by ID and one stage (`30s`, 1 user) from `create_load.rs`, and is refused in a project with no test. `new_api` writes the ID as a sentence as its `name`, `{name}` path parameters as `${var.name}` and the method only when it is not GET; a new file from `--path` gets `baseUrl: ${var.<last word>Url}`, that var added to the config as `http://localhost` (with a note) when neither the config's root nor a profile sets it, never reusing another var that holds `http://localhost`; an existing file with no `baseUrl` refuses a `--url` or curl api, help: add one; with a full URL (D177) the origin becomes a config var ending in `Url` (reused when a var already holds it, unless that is the `http://localhost` placeholder; refused when the config or a profile already sets the name to something else), added through `insert_flow_entry` or `insert_entry`, and the new file's `baseUrl`. `Engine::new_api_from_curl` (`--from-curl`, D176) reads the one curl command through the registry's `curl` importer (more than one command is refused, help: `vc import curl <file>`) and writes its `DraftApi` with `import_write::api_fields` under the given ID, its origin through the same `base_var`; the importer's notes follow `Add <id>` in `Changes.titles`, and the CLI prints one line each. `new_test` writes `id`, `name` (the ID as a sentence) and `call`, then `vars:` with each `${var.…}` in the api's path that the config, the api file and the test file leave unset, at their root or in a profile (D262, `create_vars.rs`): the api's own value as written (the spec's sample, for an imported api), else `replace-me`, each with a `# replace` comment, so the file checks; `--negative` is refused while apis have no body schema (D176); `--auth` adds a second test after it, `rejectsAnonymous<ApiId>` ("<Api id> needs a signed-in caller"; the verb first, so V4001 passes it), calling with `auth: none` and expecting `401`; the `before:` call that creates a needed resource is not built yet. `new_auth` refuses a credential field (`token`, `password`, `value`, `clientSecret`, `refreshToken`) that is not a template; the CLI asks for the type and fields only when stdin is a terminal and `--json` is off. `Engine::fmt` (`vc fmt`) rewrites each YAML definition file at or under the paths given with `Document::format`: block style with a two-space indent, the keys of every map the shapes declare in their declared order (`vc_compiler::key_order`, passed in through the parser's `FormatRules` trait, since the parser cannot see the compiler) and data maps (`vars`, `body`, `expect`, ...) in the order written, text plain unless YAML needs quotes, other scalars and block scalars as written, empty `[]` and `{}` kept. Comment lines move with the entry or item below them, a line written deeper than it as much deeper (the commented-out end of a block); a same-line comment keeps its gap, and one in or after a `[..]` or `{..}` goes with its key (after the `[` or `{`, else after the `]` or `}`) or with the entry or item it follows; `--strip-comments` drops the one-line comments `vc new` wrote above its items (`… · keys: <docs>#…`). It parses the result again and refuses, writing nothing, when the tree would differ or a comment would be lost (a comment line just before a `]` or `}`); a file that does not parse is refused too. Formatting a formatted file changes nothing. `Engine::init` (`vc init`) returns the new config and, unless `--no-sample`, the sample api and test files (kept as YAML under `crates/engine/src/init/`, each written after its schema line, with the folder name as `project`), passed by the guard; then `.env.schema` when there is none and `.vibranium/` added to `.gitignore` when missing. It refuses, naming it, a definition file it would write that exists; the CLI creates the empty `INIT_FOLDERS` after writing. `Engine::save_call_as_test` (`vc call --save-as-test`) appends a `CallAsTest` the way `new_test` does: its `call`, the `--var`s given, `expect.status` as it came back and, for each `--expect-field body.<path>` (dotted keys and `[n]`), a `body.match` entry with the value the JSON body held there, a `${` in text escaped as `$${`; a field that is missing, holds a list or an object, or is not under `body.` is refused. No schema is inferred (D176). M1 ships the shape: `parser::Document` holds the text and its tree, `set_scalar`, `set_typed` and `insert_entry` each return one `TextEdit`, and `apply` splices edits (refusing ranges that overlap or fall outside the text) and parses the result again. Each edit first finds its node in the document's own tree and refuses a node from another or an older document. `set_scalar` keeps the value's kind (`status: 200` set to `201` stays a number; a number given text is refused) and its quote style (`'old'` stays single-quoted), quoting plain text only when YAML would misread it, which inside `[..]` or `{..}` includes `,[]{}`. A null takes the kind of what replaces it, and an empty value (`key:` with nothing after it) is filled in after its colon; an empty document or list item is refused. A change of kind is explicit: `set_typed(node, value, kind)`. `insert_entry` refuses a key the map already has, adds the line after the last entry (after a block scalar's last line, not past the next key) and uses the file's line ending. M5 adds the rest. `insert_yaml` adds an entry whose value is a YAML fragment (a collection goes on the lines below, two spaces deeper), and `insert_first` adds one before the map's first key (a file-level `skip`). `insert_item` adds a list item: in a block list after the last item, lined up with its dashes and before any blank or comment lines that follow; in a flow list of scalars after the last one (`[a, b]` becomes `[a, b, c]`); an empty flow list that is a key's value and gets a collection becomes a block list. `insert_flow_entry` adds a `key: value` pair after the last one of a flow map (`{a: 1}` becomes `{a: 1, b: 2}`). `remove` takes out an entry from its key's line to the end of its value's line, comment included, or a list item with the comment lines directly above it at its dash's indent, up to a blank line; anything in a flow collection, or sharing its line with what comes before, is refused. `rename_refs(file_id, from, to)` renames every `call` and `test` reference to the full ID `from`, keeping quote style and keeping a short reference short when `to` is in the same file; it leaves definitions (`id:`) alone and does not look into data (`vars`, `body`, `expect`, ...). `EditCommand` applies a set of edits as one step and returns the command that undoes it, which gives back the original bytes. The round-trip cases in `crates/parser/tests/edits/` pin every operation byte for byte.

## Planner

The planner decides what a run will do before anything is sent: which test instances, in which files, needing which lifecycle actions. `vc plan` prints this; `vc run` prints its first line. It is a pure function, so it is tested with property tests rather than against servers.

```rust
// vc-planner. Pure: `$file`/template example row counts arrive preloaded in `options` (D132).
pub fn plan(program: &Program, selection: &Selection, options: &PlanOptions) -> Result<Plan, PlanError>;

pub struct Selection {
    pub ids: Vec<String>,                   // test ID, instance (`users.crud#getsUser:2`, D140), file ID, glob; a path is read as a path
    pub paths: Vec<String>,                 // folders or test files, relative to the project root
    pub tags: Vec<String>,                  // one expression per `-t`, all must hold: `smoke,checkout & !slow`
    pub grep: Option<String>,               // substring of the full ID or name, ignoring case
    pub changed: Option<BTreeSet<String>>,  // file IDs, resolved by the engine through the `Vcs` trait before planning
    pub include_skipped: bool,
}
// `failed_in` (rerun the failures of a run) arrives in M3 with the history store (D130).
```

`changed` comes from `Vcs::changed(base) -> Result<Vec<SourcePath>, VcsError>` (in `vc-interfaces`): the files that differ from `base` (committed since it, staged, in the working tree only, or deleted) and the untracked files that are not ignored, relative to the project root and sorted. The engine maps each path to its file ID with `SourcePath::file_id` (the config and files of no kind give none). Every implementation first checks the ref with `checked_ref` (letters, digits and `/ . _ - + ~ ^ @ { }`, no leading `-`, no `..`), else `VcsError::InvalidRef`. `GitVcs` in `vc-adapter-system` runs `git -C <root> rev-parse --verify <base>^{commit}` (so it never falls into `diff --no-index` outside a repository), then `git diff --name-only -z --no-renames --relative --end-of-options <base> --` and `git ls-files --others --exclude-standard -z`, each argument passed on its own with no shell and `core.fsmonitor` off; a `git` that cannot be started is `Unavailable`, and one that fails (no repository, unknown ref) is `Failed` with git's message. `vc-testkit` has `FakeVcs` and `vcs_suite`.

```rust
pub struct PlanOptions {
    pub repeat: Option<u32>,                     // `--repeat N`: replaces each test's own `repeat`
    pub today: Option<String>,                   // YYYY-MM-DD for `skip.until`; None keeps every skip in force
    pub example_rows: BTreeMap<TestId, u32>,     // row counts of `$file`/template examples, preloaded by the engine
}

pub enum PlanError {
    Diagnostics(Vec<Diagnostic>),
    UnknownSelector { selector: String, suggestions: Vec<String> },  // did-you-mean over test and file IDs (strsim)
    NoSuchInstance { selector: String, count: u32 },
    ReuseOnly { selector: String, test: String },  // every test the selector picks has `standalone: false`
    BadTagExpr { expr: String, reason: String },
    BadGlob { pattern: String, reason: String },
    RowsNotLoaded { test: String },               // the engine did not preload a test's example rows
    NotSupportedYet { kind: &'static str, action: ActionId },  // `function:` until M4
}
// `PlanError::help()` gives the `help:` line. An empty result is `Ok` with no instances; the engine maps it to exit 2.

// vc-model (D103). The active profile is the engine's choice, not part of the plan.
pub struct Plan {
    pub before_run: Vec<PlannedAction>,  // planned only when the run has an instance (D122)
    pub files: Vec<PlannedFile>,         // in project order, only files with an instance
    pub after_run: Vec<ActionId>,
    pub skipped: Vec<SkippedTest>,       // test and reason; reported with the `Skipped` state, never run (D126); also in its `PlannedFile::skipped`, reported as that file starts and counted in its totals
}

pub struct PlannedAction { pub action: ActionId, pub needs: Needs }  // a shared action, and the earlier ones it reads

pub struct PlannedFile {
    pub id: FileId,
    pub before_all: Vec<PlannedAction>,
    pub instances: Vec<Instance>,
    pub after_all: Vec<ActionId>,
}

pub struct Instance {
    pub id: InstanceId,              // numbered in plan order
    pub test: TestId,
    pub example_row: Option<u32>,    // 0-based
    pub repeat_index: u32,           // 0-based
    pub needs: Needs,                // shared actions this instance reads: decides which are blocked by a failure
}
```

How it works:

1. **Select.** Each positional selector is read by the first entry of a registry of selector kinds that claims it: a path (has `/` or ends in `.yaml`), a glob (has `*?[{`, matched against full test IDs and file IDs), an instance (`<testId>:<n>`), a test ID (has `#`), and otherwise a file ID. Each kind, tag term, `--grep` and `--changed` is a Specification; positional selectors are joined with "or", flags filter with "and". Tag expressions bind `!` tightest, then `&`, then `,`, so `smoke,checkout & !slow` is `smoke` or (`checkout` and not `slow`); a test's tags include its file's. `--changed` holds when the test's file changed or an api file it calls did. A selector that matches no test and names no test file is `UnknownSelector` with up to three suggestions. Tests with `standalone: false` are never planned on their own, and a positional selector that picks only such tests is `ReuseOnly`, naming the first, so selecting one says it runs only when a `test:` action reuses it. Skipped tests and files go to `skipped` unless `include_skipped`; a file's skip wins over the test's; a skip whose `until` is before `today` is ignored, so the test runs, and the lint already warned.
2. **Expand instances.** For each selected test, create one instance per example row × repeat, rows outermost; `--repeat` replaces the test's `repeat`. Inline rows are counted from the program; `$file` and template rows come counted in `PlanOptions` (D132). `:n` picks the nth instance in that order, from 1; a selector without `:n` for the same test picks all of them.
3. **Plan lifecycle and find what each instance needs.** `beforeRun` is planned when the run has an instance, and a file's `beforeAll` when that file has one; both run eagerly and finish before any instance starts (D122). A Visitor (`Walker` + `Visit`) walks each instance's scope (config and profile vars, default headers, file vars, `beforeEach`/`afterEach`) and its test, following the calls it makes (api, api file, auth and cleanup) and the tests it reuses with `test:`. Every `${var.<id>.…}` whose `<id>` names a shared action in scope is a need; a file's `beforeAll` names shadow `beforeRun` names. `vc_planner::bodies(program, &Plan)` walks the same way, collecting each action through `Visit::action`, to give every action the plan can run (lifecycle blocks, instances, the tests they reuse, api cleanups, auth steps), so the engine reads the `$file` bodies of those alone; `bodies_from(program, &[ActionId])` starts from given actions. Laziness remains only in the token cache and in cache-store hits.
4. **Order.** Files keep project order; instances keep file order. The linker already guarantees the action graph is acyclic (V2205). Concurrency is decided at run time by the scheduler, not by the plan.
5. **Refuse what cannot run yet.** A registry of unsupported kinds (`function:` until M4) is checked over every planned action, in run order; the first one found is `NotSupportedYet`.
6. **Explain.** `plan_line` gives the line `vc run` prints first (`6 tests in 2 files · lifecycle: beforeRun warm, cold · beforeAll prime, seed · beforeEach ×4 · 2 skipped`, where tests counts instances); `tree` the `vc plan` listing with each instance's needs; `json` the `vc plan --json` value; `dot` a DOT graph for `vc plan --dot` with one cluster per file, a node per lifecycle action (named by its block) and instance, a dashed edge from each node to those that run after it and a solid edge per need; `explain` each planned test's requests with their checks and where each came from: api, test or step (D123).

Tests: table tests per selector kind, expansion, skips and lifecycle over compiled YAML; insta snapshots of every render; property tests (`proptest` over generated projects): every instance's needs are planned; no lifecycle block is planned for a run or file without an instance; selecting the selected tests again selects them; selecting a file equals selecting its test IDs.

## Executor

The executor runs a `Plan`. It is where concurrency, lifecycle blocks, shared values, cleanup and cancellation come together, so it is designed to need no locks beyond the redactor's `arc-swap` (D113): every piece of changing state has exactly one owner task, and shared values are slots created up front and filled once.

### Tasks and who owns what

| Task | One per | Owns | Talks to |
| --- | --- | --- | --- |
| Run orchestrator | run | the run frame: shared `beforeRun` slots, the run's cleanup list, the run status | file orchestrators (spawns them), the event bus |
| File orchestrator | test file in the plan | the file frame: `beforeAll` slots, the file's cleanup list | instance workflows (spawns them under the concurrency limit) |
| Instance workflow | test instance | the instance frame: saved values, its cleanup stack, check results | transport, auth, hooks (all through interface traits) |
| Event writer tasks | subscriber | their own buffers | history store, reporters, console, UI stream |
| Hook thread | process | the QuickJS runtime | instance workflows, via a request queue |

This section details the workers and frames under the orchestrators described in Orchestration and design patterns. The run orchestrator runs the planned `beforeRun` actions to completion, and each file orchestrator runs its `beforeAll` before any of its instances start (D122); file orchestrators start in plan order; instances from different files run side by side, limited by `defaults.concurrency` (a semaphore) and by `defaults.perHost` (a semaphore per host in the request pipeline).

### Shared values without locks

The planner lists every shared action, so each frame creates its slots up front and fills them before any instance starts (D122):

```rust
/// What a shared action left behind: its saved values, or its failure.
pub type SharedResult = Result<Arc<Saved>, Arc<Failure>>;

/// One frame's shared actions (beforeRun, or a file's beforeAll): a slot per planned action,
/// created up front, filled once by the worker that ran the action, read by every instance.
pub struct SharedSlots {
    slots: BTreeMap<ActionId, tokio::sync::OnceCell<SharedResult>>,
}
```

`OnceCell` makes each slot write-once, so it needs no lock. The slots live in a read-only map shared by `Arc` (each action's `Frame` carries the run's and the file's slots); the worker fills the slot before it reports the action done, so the machine starts instances only after their shared values are readable. Cleanups the action registered travel back in its `ActionReport` to the frame's machine, which runs them newest first when the frame closes; a failed action stores its failure, and every instance whose needs include it is marked **blocked** with that failure attached; blocked instances are never retried (D126). Cleanups are returned as data and run by the frame's owner when it closes, so no task ever writes into another task's state.

### One test instance

```text
run_instance(instance):                           # repeated per attempt when the test has retry (D126)
  frame = InstanceFrame::new(instance, scope = run saves + file saves (read-only) + file vars + …)
  for action in file.beforeEach ++ test.before:    run_action(action, frame)   # on failure: blocked, skip to after
  if test is Call: run_action(call, frame)
  else for step in test.steps:                     run_action(step, frame)     # test-level keys are step defaults (D124); stop at the first failure
  apply test-level save to the last step's response (D124)
  for action in test.after ++ file.afterEach:      run_action(action, frame)   # always runs
  run frame.cleanups newest first                                              # always runs, own timeout, also between attempts
  emit TestFinished(status, checks, timings)                                   # passed after a failed attempt = flaky
```

`run_action` dispatches on the action kind:

- **Call.** Resolve the effective auth (step, then api, then api file) and put its stages into the pipeline (see Auth); render the request (method, URL from the api file's `baseUrl`, headers, query, body) against the scope, the `baseUrl` as written and the `path` by `action/path.rs` (D278): its literal text as written, and each `${…}` value percent-encoded as one segment (RFC 3986 `pchar`, so `/`, `?`, `#`, `%` and a space are encoded, and a lone `.` or `..` is `%2E` or `%2E%2E`), a value after a literal `?` as a query value, one before the path's first `/` as written only when it is an absolute `http(s)://` URL (a templated URL), and one whose last pipe is `urlEncode` as the pipe left it (V4007); run `beforeRequest` hooks; send through the transport, within the action's own `timeout` (D192), else the api's, else `defaults.timeout`, else 30 s (V5104); run `afterResponse` hooks; if `poll` is set, send again every `every` until its `until` checks hold, failing with V5104 ("`poll.until` did not hold within …") once the next send would pass its `timeout`, with the last exchange still in the report (`flight::Halted`), so the events show what the server last answered; a poll reports only its last exchange; evaluate the merged checks; apply `save` (the api's when the status matches its `saveOn`, then the action's) only if every check held, `Api::save_on` being the compiled `saveOn`, else the api's `expect.status` matcher, else `2xx` (D191); if the status is 2xx, the api has `cleanup` and the action isn't `keep`, render the cleanup's vars against this response and push it onto the owner's cleanup stack, whatever the checks said. A call run as a cleanup registers none. A save that fails fails the action but keeps its cleanup, since the server already created what it cleans up; a cleanup var that fails to render fails the action with no cleanup. The merged checks are the compiled `Action::expect` (D123, D124) with the api's default `status: 2xx` (origin `Api`, the api's span) in front unless any of them checks the status. Each check is evaluated on its own by the `MatcherRegistry` (`check/`: one entry per matcher name, `standard()` plus `with(name, fn)`; `Equals` renders its value and compares, `Status` matches codes and classes, `All` needs every call to hold) into a `CheckResult` with the rendered `expected`, the `actual` read at its target (`None` when absent), a `similar` unified diff of the pretty JSON for a failed `equals` on an object or list, and its code; the first failed check fails the action (V5101, V5102 for CEL, V5103 for `custom`). A `schema` check (D201) validates the body against the schema its key names in `Program::schemas`: `ActionCx::new` compiles each check's schema once per run (`check/schema.rs`, `jsonschema` with its default features off, so no remote or file `$ref` is fetched), by its `$schema` draft (draft-04 to 2020-12, 2020-12 when none is named); a `#/pointer` key compiles that part of the file with the file's own `$ref`s kept. It fails with V5101 listing up to five breaks as `<instance path>: <reason>`, the body's values left out; a schema that was not loaded or is not valid also fails with V5101, at run time. A `custom` check fails (V5103) until the hook bridge in M4. The results pass through the redactor before they leave the call, so neither a result nor a failure built from one shows a masked header, and the action's `ActionReport::checks` carries them in order. Header, query and body levels merge config defaults < api file < api < action, a null value removing a header or query key and a list repeating a query key; a JSON or `$extend` body defaults to `application/json`, text to `text/plain; charset=utf-8` and `$base64` to `application/octet-stream`. A map body (JSON or `$extend`) whose `content-type` media type, without parameters or case, has an encoder in `action/encode.rs` is sent in that encoding instead (D273): `application/x-www-form-urlencoded` is WHATWG form encoding, a space as `+`, a list repeating its key, a null left out and a nested object or list V5111; the header is sent as written. A `$file` body (D272) is the bytes the engine read before the run (`RunInputs::bodies`, a `BodyFiles` side table keyed by `(ActionId, JSON pointer)`, so a JSON body that holds a `$file` map is sent as written), with the `content-type` its extension names in the data table of `action/media.rs`, else `application/octet-stream`; a path holding a template, or one not read, is V5111, as is a file that was refused or could not be read, each with its own message and the reason. A map body whose media type is `multipart/form-data` (D274, `action/multipart.rs`) is sent as RFC 7578 parts: text with no part type, a `{$file: path}` value as a file part (its basename as `filename`, the media table's type, the bytes `RunInputs::bodies` holds at its pointer), another map or a list as `application/json`; a list repeats the part and a null is left out. A part's `$file` path must be written in the body, literally: one holding `${…}`, or a `$file` map that arrives in a `${…}` value, is V5111. A written `boundary=` must be 1 to 70 RFC 2046 characters not ending in a space, and appear in no part (V5111): each part's head and bytes are scanned for its delimiter as the part is written straight into the body; a drawn one is not checked. Each part's bytes are the `Bytes` the side table holds, cloned by reference. An encoder is given an `Encoding` (the body files, the run's `Random`, the written header) and may return a header to send in its place: the boundary is the written `boundary=` parameter, else `vc-` plus 24 hex characters from two draws of the seeded `Random`, appended to the written header. Names are quoted with `"`, CR and LF percent-encoded.
- **Inline** (a `flow` auth's steps). `InlineExecutor` renders the step's own `url` with its `query`, method, headers (over the config defaults) and body, sends it through the pipeline with no auth and the default retry, within the step's own `timeout` (D192; the `flowStep` shape does not take one yet), else `defaults.timeout`, else 30 s, judges its `expect` with the default `status: 2xx`, and applies its `save` when every check holds.
- **Test** (`test:` reuse). Run the reused test's calls in order inside a copy of the current frame, with each api's checks; the steps see the reused test's vars and the reusing action's vars (which win) as call levels, the reused test's own file vars in place of the caller's (`Frame::test_file`), and each step's saves and step id; the reused test's own test-level checks apply, since the linker merged them into its calls, and the reusing test's step defaults do not reach them (D270). The reusing action's own `timeout` limits all the steps together (D192): the step in flight when it passes is dropped and fails with V5104, and the earlier steps keep their cleanups. Each step hands its cleanups to the reuse's `CleanupCollector` as it finishes (see Cancellation and timeouts), so a dropped step loses none its finished parts registered, and a reuse dropped by its caller's deadline loses none of its own.
- **Function / command.** Send the call to the hook thread or spawn the process through the `CommandRunner` trait (with a timeout and the run's environment); a non-zero exit (V5110) or a thrown error fails the action; a returned object becomes saved values; a `function:` action's own `timeout` is its hook budget's time (`HookBridge::within`, D192), else the default 200 ms. A dynamically saved value that a later template uses without a `provides:` declaration is V5108; a declared one the action did not return is V5109 (D128). The `command:` executor (`CommandExecutor`, D181) renders the line with each value quoted as one shell word (POSIX single quotes; on Windows a value `cmd` would act on is V5111), runs it through the `CommandRunner` port in the project root with a 64 KiB tail cap per stream and the action's own `timeout`, else `defaults.timeout` (D192), and fails a non-zero exit with V5110 carrying the exit code and the last 20 lines. `ProcessRunner` streams each pipe keeping its tail, ends the run when the child exits (reading what the pipes still hold for 200 ms more, so a process it left in the background never holds the run open; after that a detached task, spawned only for a pipe not yet at its end, reads it to its end and discards what comes, so that process lives on while vc runs instead of dying of a closed pipe; once vc exits it dies of `SIGPIPE` at its next write. A clean exit never kills its group), and on unix starts the child in its own process group and kills the group on timeout or cancellation. It appends the folder of the running executable (links resolved) to the end of the child's `PATH` when that `PATH` lacks it, so a line calling `vc` (the sample's `vc demo start`) works when vc was started by its path or through a `vibranium` link, and a `vc` the user already has on `PATH` still wins. The `function:` executor is registered in M4. Until then `function:` has no entry in the `ActionExecutors` registry, and `Executor::start` walks every action the plan can reach (through api cleanups and `test:` reuse, via `ActionExecutor::follows`) and refuses the plan with `ExecutorError::NoExecutor` before anything runs.
- **Loops.** `repeat` and `forEach` (`Action::repeat`) wrap whichever executor runs the action (`action/looping.rs`). The iterations run in a `JoinSet` that holds at most `parallel` (at least 1) at once: a new one starts only when one finishes, which bounds them as a semaphore would and lets the loop stop starting new ones after a failure. Each iteration runs in a copy of the frame with `${iteration.index}` (from 1), `${iteration.count}` and, for `forEach`, `${item}` bound, and its own fake-data memo, so fakes are drawn once per iteration. Its report lands in slot `i` of a pre-sized list, so each saved name becomes a list in iteration order however the iterations finish; the saves are kept only if every iteration passed. On failure, no further iteration starts, the action waits for the ones already running, keeps every finished iteration's cleanups and checks, and reports the first failure in slot order, prefixed `iteration n:`. A `forEach` whose items do not render to a list is V5111; until the engine passes the data files, a `forEach` over a `$file` map is one.
- **Retry.** A test's `retry` (else `defaults.retry`, which `InstanceScript::retry` resolves when the run's scripts are built) re-runs the whole instance after `delay`, running its cleanups between attempts; a pass after a failure marks it **flaky** with every attempt recorded. The console shows a failed retried instance once (`✕ id (3 attempts)`), with each different failure listed once under the attempts it happened in (`attempts 1, 2 and 3 of 3:`, `failure.rs`). A blocked instance is never retried. An action's own `retry` (a step, or an entry of a lifecycle block; `defaults.retry` does not reach actions) is a strategy around whichever executor runs it (`action/retrying.rs`, wrapping the loop when there is one): after a failed attempt its cleanups run newest first, then `delay` passes and the action runs again, and the last attempt's report stands, so a `beforeAll` action blocks its tests only once its retries are spent. Transport-level retries are `http.retry`, in the request pipeline (D126).
- **Cache.** `CachedExecutor` (`action/cached.rs`) wraps the `call` and `test` executors when the run has a `CacheStore` (`ActionCx::with_cache`); an action with `cache` looks in the store first (see Cache store). On a live entry, `cache.check` runs with the cached saves bound by name and under the action's `id`; when it passes (or there is none) the hit returns the saves only, with no request, check or cleanup of the action's own; the check's exchanges go in front of the report's, hit or miss, so its call is an `exchanged` event like any other. A miss or a failed check runs the action; a result that passed, whose every cleanup is its api's `cleanup`, is stored with those cleanups and reports none to the frame. `CacheStore::put` keeps the entry it replaced (a failed check's, or one that expired since the run began) as a tombstone, in the same transaction: a row under a key of its own, expired when the fresh entry was made. It gives the tombstone back, and the tombstone goes down the `RunCache`'s channel instead of being cleaned up then, since another instance may still use what it made. The engine holds the other end (in its `Sweep`) and, once the run is over (also when it ends in an error), runs each tombstone's cleanups the way it runs expired ones, so one that fails is a warning and never fails the run, then removes it (`CacheStore::remove`). A third Ctrl-C during that sweep abandons it; a tombstone left behind, by that or by a killed run, is an expired entry, so the next run's start cleans it up. A store that fails reads as a miss and never fails the action. Entries are made and expire by the `Clock` port the engine passes to `RunCache::new`, read as each cached action runs, so an entry that expires during a long run is not used past its `for`.

### Cancellation and timeouts

A tree of `CancellationToken`s mirrors the frames (run → file → instance); each frame's `CancelTree` holds its own `work` token (a child of its parent's) plus two run-wide tokens, `hurry` and `abort`. Ctrl-C, `--bail` or a test timeout cancels the relevant subtree: no new instances start, and the action in flight gets a grace period (`RunOptions::grace`, default 5 s) before it is cut. Cleanups run outside the `work` token, so they are not cancelled with the work. A second Ctrl-C (`hurry`) ends the grace period but still runs cleanups; a third (`abort`) stops everything, and each frame emits `CleanupsAbandoned` with the cleanups that did not run. The run machine counts the interrupts (`RunHandle::interrupt`); the shells only carry out its `Cancel`, `SkipGrace` and `Abort` commands. A cut instance with no failure is reported skipped (reason `cancelled`); the run ends `Cancelled` and exits 130 (D127).

A test's `timeout` is enforced per attempt, not through the cancel tree: each attempt's actions carry the attempt's deadline (`Job::deadline`, restarted after a retry's `delay`), and an action still running at the deadline is dropped and fails with V5104 ("the test ran past its `timeout`"), so the attempt fails, may be retried, and its cleanups run as for any failure. The `after` and `afterEach` actions always run, so they do not carry the attempt's deadline: one with its own `timeout` (D192) gets that as a whole-action limit from when it starts, past which it fails with V5104 ("the `after` or `afterEach` action ran past its own `timeout`"); one without has no whole-action limit, and only its requests' own timeouts bound it. For a `call:` that limit equals its per-attempt one, so it also bounds the call's `http.retry`. Cleanups have no deadline. Dropping an action must not lose the cleanups its finished parts registered, so they are handed over as each part finishes rather than held in a report that is dropped with it: `Frame::sink` is a `CleanupSink`, the sending end of an unbounded channel (lock-free, a send never waits), and whoever can drop or must intercept nested work owns a `CleanupCollector` and gives its frame that sink. `Crew::act` (around the cancel guard and the job's deadline), a `test:` reuse (its steps, its own `timeout`), a `retry` attempt (so a failed attempt undoes them all) and a cache miss (so all of them are stored) each own one; a loop turn hands its report's cleanups to the frame's sink the moment it finishes, inside its task. A collector's `take` gives what was handed over, oldest first, then the report's own; a collector dropped first hands what it holds to the sink it was made under. A cut by cancellation drops the in-flight action's report but not those cleanups: `ActionCut` carries them to the frame's machine, which runs them with the rest. There is no grace period and no default whole-test timeout yet; a request's own limit is its `timeout` (see Call).

### Events

Everything observable is an `Event`, numbered with a run-wide sequence number by the `EventBus`:

```rust
pub enum Event {
    RunStarted { files: usize, instances: usize }, FileStarted { file: FileId },
    FileFinished { file: FileId, totals: Totals },
    ActionStarted { action: ActionId, owner: OwnerKey },
    Exchanged { action: ActionId, owner: OwnerKey, exchange: Box<Exchange> }, // a call's request and response, whole, then redacted (history, reports and the web UI's run feed cut bodies at history.maxBodySize afterwards with `cut_body`, and the feed sets `body_truncated`; the feed sends bodies only with `history.bodies: all`, since with `failures` a failure is known only when the action or test ends, so those bodies come from `GetRun` once the report arrives); before its checks
    CheckEvaluated { action: ActionId, owner: OwnerKey, check: Box<CheckResult> }, // each, in order, before ActionFinished
    ActionFinished { action: ActionId, owner: OwnerKey, outcome: ActionOutcome },
    CleanupFinished { cleanup: CleanupRecord },
    CleanupsAbandoned { owner: OwnerKey, cleanups: Vec<ActionId> }, // after a third Ctrl-C
    TestFinished { result: TestResult },               // passed | failed | blocked | skipped | flaky; duration by the executor's clock
    RunFinished { status: RunStatus, totals: Totals },
}
pub struct Sequenced { pub seq: u64, pub event: Event }
pub enum Feed { Event(Sequenced), Missed { count: u64 } }
```

The bus is one fan-out task that owns the sequence number and the subscribers; `publish` never waits. Each subscriber (history writer, reporters, console, TUI, web UI, MCP) gets its own bounded `Feed` channel (`EventBus::subscribe(capacity)`), so a slow subscriber cannot slow the run: when its buffer is full the event is dropped for that subscriber only and counted, and once there is room it receives `Feed::Missed { count }` before the next event, then reloads from the history store. The run flushes the bus before `RunFinished` is reported. Every event passes through the redactor before it leaves the executor; the redactor is executor logic, and the secrets adapter only supplies values (D106). `Event` is a `vc-model` type (D103).

Apps outside the engine watch a run through `RunRequest::watch`, a `RunWatch` holding the sending half of the app's `mpsc` channel of `RunFeed` (`run_feed.rs`). There is one feed for every watcher: the TUI's Run tab and the server's `Run` stream both read it. `RunFeed` is `Started(Names)`, `Event(Sequenced)`, `Missed { count }` or `Done(RunReport)`. `Engine::run` subscribes a relay task to the bus before the executor starts. The relay first sends `Started` with the run's `Names` (from its program and plan), so the watcher can label every event without the program; it waits for room, as `Done` does, and the bus buffers the events meanwhile. `vc_engine` re-exports `Names` and the model types a feed carries (`Sequenced`, `TestResult`, `TestStatus`, `Totals`, `RunStatus`, `OwnerKey`, `Exchange`, `CheckResult`, `Failure`, `Location`, `check_label`). The relay then passes each event on with `try_send`, so watching never holds up or fails the run, and it applies the bus's rule to the watcher's channel: a full channel drops the event and counts it, and the next send that finds room delivers `Missed { count }` first. A closed channel ends the relay. Once the reporters have finished (the history and report files are written), the run hands its report to the relay. The relay then passes on the events still queued, then any count still missed, then `Done`, and nothing follows it. Apart from `Started`, only these last sends wait for room, because nothing waits on the relay by then. A run that fails before it executes ends the feed without `Done`; one that fails as it executes, or after (its gate settling), has sent `Done` already (an executor error among its notices); either way the error is `run`'s result. A watched run prints nothing to stdout, as an agent's run does, because its watcher shows it; its report files and history are written as usual.

### Determinism

The executor reaches time, randomness, the environment, the file system and processes only through the `Clock`, `Random`, `Environment`, `FileSystem` and `CommandRunner` traits (implemented in `vc-adapter-system`, D133: `SeededRandom` is a lock-free SplitMix64 on an `AtomicU64`, and `SystemEnvironment` is one snapshot of the process environment taken at run start). `--seed` seeds `Random` (fake data, `random`/`shuffle` pipes, dataset picks), so a run can be repeated exactly; with more than one task drawing, the order of the draws may vary; the seed is printed on failure (D131), and tests use the `vc-testkit` fakes.

## Vars, templates and CEL at run time

Templates were parsed at compile time; at run time they are only rendered against a scope. Rendering never runs arbitrary code: references are looked up, pipes are applied from a registry, and `$cel` values are evaluated by the sandboxed CEL interpreter.

### The scope

```rust
/// The levels a ${var.x} lookup walks, closest first, built per action from its frame.
pub struct Scope {
    levels: SmallVec<[Level; 10]>,
}
pub enum Level {
    Call(Arc<Defined>),         // vars on the call: the action's, then each reusing action's and
                                // reused test's (innermost first), then the instance's test
    Given(Arc<Saved>),          // a cleanup's vars, rendered when registered; replace its own
    Saved(Arc<Saved>),          // saved earlier in this test instance (beforeEach, before, steps)
    File(Arc<SharedSlots>),     // beforeAll saves, published under action ids
    TestFile(Arc<Defined>),     // the test file's vars
    Run(Arc<SharedSlots>),      // beforeRun saves, under action ids
    Api(Arc<Defined>),          // the api's vars
    ApiFile(Arc<Defined>),      // the api file's vars
    Config(Arc<Defined>),       // config vars with active profiles applied in order
}
```

What an action reads comes from its `Frame` (`vc-executor`): the run's and file's `SharedSlots`, the instance being run, its saved values, step-id values (`created.body.id`) and drawn fakes, the callers' vars (`test:` reuse), and a cleanup's given vars. The task that owns the frame absorbs each `ActionReport` into it (`Frame::absorb`); a retry starts from a fresh frame (`Frame::restart`). Every run-wide input is in `ActionCx::new(program, executors, RunInputs)`: `RunInputs` carries the `Random` and `Environment` ports and the chosen profiles, and `RunValues` is built from them once per run: each level's var definitions with the active profiles' values layered over the base values (by-profile config values, then each profile's own vars, in the order given; with no profiles chosen, the profiles marked `default`), the `PipeRegistry` and the `FakeRegistry` (`vc-template`, D174), and `started_ms`, the run's start (`RunInputs::with_started_at`, which the engine sets from the `Clock` port), which `date.past`, `date.future` and `date.recent` count back or forward from so a seeded run is repeatable. A `${fake.<id>}` naming a config generator calls its `GeneratorDef`'s built-in with its arguments; every generator draws from the frame's `Chance`, through an adapter that gives the `fake` crate its random source. `Executor::new(cx, options)` takes the same `Arc<ActionCx>`.

Config values are layered once, lowest first: built-in defaults < user config < `vibranium.config.yaml` < profiles in the order given < `.env` < `VIB_*` variables < `--set`. Each layer is a `ConfigSource` whose `ConfigEntry`s carry their origin (the file path, `.env`, the variable's name or `--set`), so `vc config explain` can say where a value came from (D129); the per-key store that command reads lands with it. The engine stacks them in `ports::layered`: `UserConfig` (`vc-adapter-system`, wrapped in `UnderProject`, which drops a key the project's config or a default profile already sets) < `DotEnv` < `VibEnvironment` < `--set`. The `.env` file is read from the project root even when the `Environment` port is injected, and its non-`VIB_*` lines fill `env.X` only where the environment is silent. Profile overrides are applied when the program is loaded for a run, not on every lookup. A lookup walks the levels and returns the first hit. A var defined from itself (`greeting: ${var.greeting} there`) reads the next level out, and a chain deeper than 16 vars fails, so vars that refer to each other cannot loop. A miss renders as a V5111 failure of the action (``var.userId` is not set``) that the `default` pipe may stand in for; until the linker checks references against the levels an action can see, a miss is a user error, not an internal one. `env.X` reads the `Environment` port; `run.profiles`, `iteration` and `example` (an inline row, rendered per instance, or a compiled or pre-rendered row, bound as data) are bound from the inputs and the instance. `dataset` is every built dataset's rows, nested by the dots of its ID (`users.seed` is `{users: {seed: [...]}}`), built once per run in `RunValues`. An `example` or `item` that is a map without the column a template reads is V5112 rather than V5111 (`RenderError::code`); `default` still stands in for it.

### Rendering

- **Type preservation.** A value that is exactly one template keeps its type (number, list, object); a template inside other text renders to a string. This is decided at compile time from the parsed parts (`Template::preserves_type`).
- **Fake data memo.** A var defined as `${fake.…}` is drawn when it is first rendered and then kept in the frame's memo by var name for the rest of the instance (or loop iteration), so one value can appear in several places and an unused fake var draws nothing, leaving the random sequence independent of unused vars; an inline `${fake.…}` is fresh each time it is rendered (D131).
- **Paths.** After the namespace, paths walk JSON with `.key`, `[n]` (negative from the end), `[*]` (map over a list) and quoted keys; a missing path is a run-time render failure of that action (V5111), with the path and the actual value shown.
- **Pipes.** Registered functions `PipeFn = fn(&Value, &PipeArgs) -> Result<Value, String>` (`PipeArgs` holds the literal arguments and a `Chance`, the random source), held with each signature in one `PipeDef` in the `PipeRegistry`: `number`, `int`, `bool`, `string`, `json`, `jsonString`, `base64`, `fromBase64`, `lower`, `upper`, `trim`, `urlEncode`, `default`, `random`, `shuffle`, `take`. A plugin registers more under its prefix (`acme.mask`); `PipeRegistry::register` returns `TemplateError::UnprefixedPipe` or `DuplicatePipe` otherwise. The `PipeRegistry` holds each pipe's signature (argument types, input and output type) so `vc check` reports an unknown pipe or wrong arguments (V2308) and a pipe given the wrong type (V2304) before the run. Messages name types in the Syntax Reference's words (`a list`, `a whole number ≥ 0`). A pipe gives the reason it failed and the renderer adds the pipe and the value: ``pipe `number` cannot take "abc": the text is not a number`` (V5111). Only a pipe marked `taking_missing` (`default`) runs on a missing value, given as `null`.
- **The renderer.** `vc_template::Renderer::new(&PipeRegistry, &dyn Resolve)` renders a `Template` (`template`, `text`) or a `TemplateValue` (`value`) and stays pure: a `Resolve` gives each reference's value (its root followed along its path, usually with `vc_template::select`), evaluates `$cel` values and supplies the `Chance`. Failures are `RenderError { message, missing }`; `missing` marks an absent value, which `default` may stand in for. Inside text a string renders as it is and anything else as compact JSON (`to_text`).
- **Parsing.** `vc_template::parse(text, ScalarSource, &mut StringTable) -> Result<Template, TemplateError>`; `TemplateError::Syntax` carries a V2305 diagnostic naming what the innermost rule expected, and `TemplateError::Internal` wraps a `ModelError` such as a full string table. The parser reports each scalar's style, so spans are exact only for one-line plain scalars and quoted scalars without escapes; for block scalars, folded lines and escaped quoted scalars the span is the whole scalar and no diagnostic offers a fix. Literal arguments are JSON numbers, `true`, `false` and single-quoted strings; `null` and double-quoted strings are V2305, with a certain fix that swaps the quotes when the text has no `'` or `\` and the scalar is not single-quoted (D151). A bare `status`, `headers` or `body` parses as a step id; `Roots::check` reports it as V2105 unless that step is available, with a certain fix that inserts `response.` when the root span is exact (D150).
- **`$extend` and `$remove`.** The base must be a template (V2302 at compile time otherwise); it is rendered and must give an object, else the action fails with V5111 ("`$extend` needs an object to start from, but its base is …"). The changes are deep-merged into it (maps merge, lists and scalars replace, `null` sets null), then the `$remove` paths are deleted. A `$remove` in a map without `$extend` is V2211.
- **Secrets.** `${secret.X}` renders the real value into the request, and the value is registered with the redactor the moment it is first resolved, so it is masked in every event and output.

### CEL

The `cel` crate is private to `vc-template`, behind a small trait so it can be replaced. Checking and evaluating are split so that `vc-model` stays plain data and the compiler stays pure:

```rust
impl CelCompiler {
    /// Pure, used by the compiler: parses the source and checks every root it reads.
    pub fn check(&self, source: &CelSource, roots: &Roots, strings: &mut StringTable) -> Result<CelProgram, TemplateError>;
    /// Used by the executor at run start: turns a checked program into an evaluator.
    pub fn prepare(&self, program: &CelProgram) -> Result<Arc<dyn Expr>, TemplateError>;
}
pub trait Expr: Send + Sync + Debug {
    fn eval(&self, activation: &Activation) -> Result<serde_json::Value, ExprError>;
}
/// One evaluation's roots (D125): response (status, headers, body, timing), request, var (D53), env,
/// item, iteration, example and each step id, as JSON; plus the step limit (default 1,000,000).
pub struct Activation { /* roots: HashMap<Namespace, Arc<Value>>, step_limit */ }
pub enum ExprError { Eval(String), StepLimit(u64), MissingRoot(String), Unrepresentable(String) }
```

- **Check (compile time).** `check` parses the expression and walks it for roots: an identifier followed by fields and literal indexes becomes a `Reference` with its path and exact span, and comprehension variables and type names are skipped. Each reference goes through the same `Roots::check` as templates, so an unavailable root is V2105 or V2102, and a bare `status`, `headers` or `body` is V2105 with the certain `response.` fix (D150). `secret`, `fake`, `dataset` and `run` are V2105 "not available in CEL": CEL's activation has no such roots (D125), so the help says to set a var from a template and read `var.<name>`. A parse error is V2305 at the parser's position, with the parser's internal "Incomplete …" errors dropped. `timestamp(string)` and `duration(string)` are our own registered functions (`cel_time.rs`, built without `cel`'s `chrono` feature; D153): a timestamp is RFC 3339 (`2024-05-01T12:30:00Z`, an offset or a fraction allowed) in years 1 to 9999, a duration is Go-style (`1h30m`, `1.5s`, `-300ms`) and fits an `i64` of nanoseconds, and both compare, add and subtract as CEL specifies (`timestamp - timestamp` is a duration; overflow is an error) and convert with `string()`. A time value that is the whole result becomes its `string()` in JSON; one inside a list or map has no JSON form, so wrap it in `string()`. A literal pattern given to `matches()` that does not compile is V2306, as for the `regex` matcher. `cel-rust` has no type checker, so a call to an unknown function or a type mismatch is only found at run time.
- **Prepare (run start).** The executor (M2) prepares every `CelProgram` once per run into its own table keyed by the program's position in the `Program`; the `Program` itself holds only data. `prepare` re-parses the source, binds each root the program reads to its `Namespace`, and wraps every comprehension's range in a counting call (below). For now the executor prepares a `$cel` value each time it is evaluated; the per-run table comes when profiling shows the cost.
- **Evaluate.** Each evaluation builds a fresh CEL context from the activation: only the roots the program reads are converted from JSON, every integer that fits becomes an `int` (CEL has no arithmetic across `int`, `uint` and `double`), and the result is converted back to JSON with map keys as sorted strings. Bytes, NaN and infinities have no JSON form (`ExprError::Unrepresentable`).
- **Standard library additions.** `sum()` on a list of numbers is an `int` when every element is one (overflow is an error) and a `double` otherwise; `[]` sums to 0. `matches()` is the interpreter's own, built on the same `regex` crate as the `regex` matcher.
- **Step limit.** CEL's only loops are comprehensions (`all`, `exists`, `map`, `filter`). Every comprehension's range is passed through a hidden `@steps` function that adds the range's size to a counter local to that evaluation and fails with `ExprError::StepLimit` past the activation's limit, so a nested pathological expression fails instead of hanging. List and string building outside comprehensions is not counted.
- **The word `var`.** CEL reserves `var`, which is one of our roots. Before parsing, every `var` outside strings and comments and not after a `.` is renamed in place to `_v_`, a word of the same length, so every offset still matches the source. Writing `_v_` yourself is V2305.

### Transport

```rust
#[async_trait]
pub trait Transport: Send + Sync {
    async fn send(&self, request: RenderedRequest, ctx: &SendContext) -> Result<Exchange, TransportError>;
}

pub struct SendContext { pub body_limit: Size }   // in-memory cap on the decoded body, default 64 MiB

pub struct Exchange {
    pub request: RenderedRequest,          // method, uri, headers, body: as sent, after hooks and auth
    pub response: HttpResponse,            // status, headers, decoded body (capped), wire_size
    pub timing: Timing,                    // dns, connect, tls (None on a reused connection), first_byte, download, total
    pub connection: ConnectionInfo,        // reused or new, protocol (Http1, Http2), remote address
}
```

The wire types live in `vc-model` (`exchange.rs`) and use `http` and `bytes` types (D111); their `Debug` output shows header names but never values. `TransportError` (in `vc-interfaces`) is `InvalidRequest`, `Dns`, `Connect`, `Tls`, `Timeout` (V5104), `Protocol`, `BodyTooLarge` or `Decode`; all but `Timeout` are V5105. A status code is never an error.

The HTTP adapter (`HttpTransport::new(&HttpOptions)`, the only public constructor, called by `EngineBuilder`) is built on `hyper` 1 with `hyper-util`'s pooled client and a custom connector that times each phase: DNS through `tokio::net::lookup_host` (the system resolver; skipped for an IP literal), TCP connect, the proxy tunnel, and the `rustls` handshake (`ring` provider, roots from the OS store through `rustls-native-certs` plus `HttpOptions::extra_roots`, webpki verification always on; D152), then first byte and download measured around the body stream. HTTP/2 is negotiated by ALPN (`h2`, then `http/1.1`). The connector attaches a connect record to each new connection; the first response on it claims the record and reports the connect phases, and later responses on a pooled connection report `reused`. The `response.timing` root, which timing checks read, gives a phase that did not happen as 0 ms (D275); the exchange keeps `None`, so reports and history still tell it from a measured 0. Response bodies are read up to `SendContext::body_limit` on the wire and again after decoding (gzip, x-gzip, deflate, br, zstd; stacked encodings are undone last first), so a small compressed body cannot expand without bound; `accept-encoding: gzip, br, zstd, deflate` is sent unless the request sets its own. Proxies come from `ProxyConfig::from_env`, which the engine calls with its environment source (`HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, upper case first): plain HTTP goes to the proxy in absolute form, HTTPS through a `CONNECT` tunnel, both with `Proxy-Authorization` from the proxy URL's credentials; only `http://` proxies are supported. Client certificates and per-profile CA bundles come later as per-profile config.

Around the transport, each request passes through `tower` services in this order (D134, D141), built by `pipeline(PipelineParts)` in `vc-executor`: timing → retry (on `refreshOn` and per `http.retry`, D143) → auth → `beforeRequest` hooks → per-host limit → timeout → transport. Auth sits inside retry, so a retried request gets fresh credentials. The timeout (`Call::timeout`) sits inside retry and inside the per-host limit, so it limits each attempt, waiting for a permit does not count, and a timed-out attempt can be retried. Retry asks a `RetryPolicy` (`NoRetry`, or `HttpRetryPolicy` for `http.retry`: idempotent methods, connect failures, timeouts and listed statuses, exponential backoff capped at `max`). The call executor builds the policy for each call from the api's `http.retry`, else the config's (`action/http_retry.rs`): `NoRetry` when `attempts` is 0, and with `jitter` the policy is wrapped in `Jittered`, which draws each wait evenly between half of it and all of it from the run's `Random` ("equal jitter"), so `--seed` repeats the waits. `PipelineParts::retry` is therefore replaced on every call. Auth and hooks are `RequestStage`s: auth is the `AuthStage` of the call's definition (see Auth) or the `Unchanged` null object when the call has none; hooks are `Unchanged` until M4. The per-host limit (`defaults.perHost`) is a `HostLimits` actor task that owns the map from `host:port` to an `Arc<Semaphore>`, created on first use and handed out on each request; the permit is acquired outside the actor and held for the attempt. The map lives for one run, so it is bounded by the distinct hosts the run talks to. The timing service returns a `Delivery`: the last attempt's result, the attempt count and the wall time of the whole call.

### Auth

```rust
#[async_trait]
pub trait AuthProvider: Send + Sync {
    /// The credentials for one identity: headers, query params and cookies, with how long they hold.
    async fn credentials(&self, request: &AuthRequest) -> Result<Credentials, AuthError>;
}
pub struct AuthRequest { pub auth: String, pub kind: String, pub settings: Map<String, Value>, pub flow: Option<Arc<dyn ActionRunner>> }
pub struct Credentials { pub headers, pub query, pub cookies: Vec<(String, Secret)>, pub expires_in: Option<Duration> }
#[async_trait]
pub trait ActionRunner: Send + Sync { async fn run(&self) -> Result<Credentials, AuthError>; }  // a `flow`'s steps
```

The compiler turns each `auth` entry into an `AuthDef` (`link/build/auth.rs`): its `type`, `vars`, `refreshBefore` (default 60 s), `refreshOn` (default `[401]`), `expiresIn` (a template rendered after a `flow`), and every other key as a compiled setting. A `flow`'s steps become run-owned inline actions (`ActionKind::Inline`: `url` with its method, headers, body, `expect` and `save`); a `call:` step is not supported yet. `AuthDef::steps` lists them so the start-up check reaches them.

The executor owns the cache (`action/auth/`). For a call, `auth::prepare` picks the first of the action's, the api's and the api file's `auth` that does not inherit; renders the vars in the call's own `Render` through `Render::scoped`, which puts levels around the scope (an `Around`: vars and given values in front, a fallback behind every other level), runs, and takes them away: a use-site var renders with its sibling use-site vars found first, then the caller's levels, then the definition's vars as the lowest fallback (so `token: ${var.token}-v2` reads the definition's `token` when the caller has none), a definition default the use site does not override renders with the use site's values found over the definition's, and the settings render with all of them found first. A `${fake.*}` drawn by the call keeps its value across them, a `${fake.*}` an auth var draws gets a slot of its own that is set aside afterwards (a definition fake the use site reads is drawn once, for both), and a saved value read undeclared is still V5108 (D186); and keys the identity with an `AuthKey`, a keyed BLAKE3 hash of the definition, its rendered vars and settings under a per-run random key (D168), so no secret is recoverable from a key. `auth::added` puts two pieces into the call's `PipelineParts`: an `AuthStage` (the auth `RequestStage`) that asks the `TokenCache` and attaches the credentials (headers set, query params appended through the same encoder as the request, cookies joined into `cookie`), and a `RefreshOn` retry policy around the call's own that invalidates the call's `Lease` and retries once when a response has a `refreshOn` status. The two share one `Lease`, which holds the slot the call last took credentials from. Every credential value is handed to the redactor as it arrives, with the token after a scheme (`Bearer x` also hides `x`, which the issuing response shows on its own), and the header it went in is masked too. A failure is `TransportError::Credentials` (V5114), whose message names the definition and the cause but never a value or a token body.

`TokenCache` (`token_cache.rs`, one of the two files allowed a lock) is a mutex over a map from `AuthKey` to a `OnceCell` slot, never held across an `await` (D113): concurrent requests for one identity wait for one fetch, a slot is fetched again by the first caller after `expires_in - min(refreshBefore, expires_in / 2)` (D193), the request that fetched credentials always uses them, and `invalidate(lease)` drops the slot only if it is still the one the lease holds (compare-and-invalidate), so N requests rejected together cause one fetch, not N. A failed fetch is shared with the requests already waiting on it. A failure that may pass (`AuthError::may_pass`: the endpoint unreachable or timed out, or a 408, 429 or 5xx answer) is then dropped, so the next request fetches again; any other failure, such as a refusal (`AuthError::refused`: 400, 401 or 403) or a failed `flow` step, which carries no status, is kept for the run, so requests do not each retry a login and lock the account. Credentials live in memory only; `cache: true` (across runs, through the cache store) is not built yet.

The types are entries of the `AuthTypes` registry in `vc-adapter-auth`, which is itself an `AuthProvider` that hands each request to the entry for its `kind` (an unknown kind is V5114): `basic`, `bearer`, `apiKey` (pure functions of their settings); `oauth2ClientCredentials`, `oauth2Password` and `oauth2Refresh` (form posts to `tokenUrl` through the injected `Transport`, the client in Basic auth when it has a `clientSecret` and as `client_id` otherwise); `oauth2AuthorizationCode` (PKCE: opens the `Browser` port once, listens on `redirectPort`, and keeps the refresh token through the `Keychain` port; a refresh the server refuses (`AuthError::refused`: 400, 401 or 403) forgets the token and signs in again, while any other failure keeps it and fails the request); and `flow`, which runs the request's `ActionRunner`. The executor's `FlowRunner` runs a flow's steps in a frame of their own that starts with the definition's vars as saved values, each step through the action registry (`InlineExecutor`), and then renders `apply` (`headers`, `query`, `cookies`) and `expiresIn` against the last step. A failed step is reported by its `id` and code only. The engine composes the registry once for each `ActionCx` it makes (`Engine::action_cx`, the start of every run with its `beforeRun` and shared blocks, every `vc call` and every `vc cache clear` cleanup): `AuthTypes::standard` over the same `Transport` the run's requests use, the `SystemBrowser` over the command runner and the keychain, injected with `ActionCx::with_auth`. `EngineBuilder::auth` replaces the whole registry and `EngineBuilder::browser` only the browser, for tests. `NoAuth`, which knows no type, is only the executor's default for a context made without the engine.

### Secrets and redaction

```rust
#[async_trait]
pub trait SecretProvider: Send + Sync {
    /// The values of the names `query` asks for; a missing name is an error naming it, never a value.
    async fn load(&self, query: &SecretQuery) -> Result<Secrets, SecretError>;
}
```

`secrets.provider` picks an entry of the `SecretProviders` registry in `vc-adapter-secrets` (D163): `env` (the default) reads the run's environment snapshot, `.env` under the process environment; `varlock` runs `varlock load --format json` once per run through the `CommandRunner` port, never through a shell, and output past the command's output cap is an error rather than a partial read. Both keep values in memory for the run only. A failure is a `SecretError` (V5114), with its own help per cause, never showing a value. `Secret` holds its value in a `Zeroizing<String>`; its `Debug` shows only a placeholder and it has no `Serialize`. `.env.schema` at the project root declares the names (`NAME=` lines; `#` lines are Varlock decorators): when discovery lists it, the engine reads it through `SourceProvider::read` and passes it as `CompileInput::secret_schema` (a schema it cannot read is a V1012 error, not a missing schema), and the linker reports `${secret.X}` of an undeclared name (V2106) and `${env.X}` of a declared one (V2107). Not built yet: a `secrets.schema` other than `.env.schema`; the engine reads only the default path. When the schema declares names, `vc run` builds `SecretProviders::standard` over the run's environment snapshot, the command runner and the project root (in `ports.rs`, next to the other adapters the engine names), loads the declared names from the configured provider before the history row is opened, and hands them to the executor with `RunInputs::with_secrets`; `${secret.X}` renders from them. A provider that fails stops the run with a `secrets` setting error, which never holds a value. So does a declared name the provider leaves out or gives a blank value (`Engine::secrets`: `V5114: the declared secret \`X\` has no value`, naming only those names), for `vc run`, `vc call`, `vc load`, a cache cleanup and an alert sample, before any request; `vc config explain` loads them without that check (`Engine::loaded_secrets`), since it needs the values only to mask them. The executor reads `${secret.X}` by name (`values/lookup.rs`): a name that did not load is V5114 and a path inside a secret is an error, and neither message shows the `secret` root. The `Keychain` port's adapter is `OsKeychain` in the same crate, over `keyring-core` and one native store per system, each a target-specific dependency (D187): `OsKeychain::platform()` opens Keychain Services on macOS, the Credential Manager on Windows and the kernel keyutils session keyring on Linux, and fails on any other system, so its user goes without. On Linux a key in the session keyring lasts only for the login session. `OsKeychain::new` takes any `keyring-core` credential store, and its tests use `keyring-core`'s mock store. Its errors never hold a secret.

The redactor (`redactor.rs`, the other file allowed a lock) is core logic in `vc-executor`; providers only supply values (D106). Its masks sit behind an `ArcSwap` and are swapped whole, so readers never wait (D113): the lower-cased masked headers (always `authorization`, `cookie` and `set-cookie`, plus `redact.headers`), the hidden JSON fields (`redact.fields`, any case), and one `aho-corasick` automaton over every value it was told to hide (values under four characters are left alone). `Redactor::for_config` builds it from the config, including `redact.rules` (D171) as `MaskRule`s applied after the built-in masking: a `regex` masks every match in any text, a `cel` rule masks a JSON field whose `name` and `value` make it true; a `regex` that does not compile masks every text and a `cel` rule that fails masks the field (fail closed); a `cel` rule sees `item = {name, value}`. `MaskRule` is async (`text` and `value`, each given one piece of output whole, so a rule that calls a hook does so once per piece; D185), and rules see output only after the built-in masking, so never a secret value (a `cel` rule's `item.value` is already masked). Each rule is made through the `MaskRules` registry, keyed by `RedactRuleKind`: `MaskRules::standard()` holds the `regex` and `cel` makers, and an entry no maker makes masks everything (fail closed). A `function:` rule is a `HookMaskRule` (`action/hooks/redact.rs`): `MaskRules::with_hooks(runner, program)` registers its maker under `RedactRuleKind::Function`, and the engine hands that registry to `ActionCx::with_mask_rules`, which rebuilds the redactor with those rules and every value hidden so far (`Redactor::with_rules`). The hook is called through the `HookBridge`, within the hook budget, once per piece: a text as `{text}`, which must come back a string, and a JSON value whole as `{json}`, which comes back as any JSON; a hook that throws, overruns, is missing or has no runner masks the whole piece. Which paths get which masking: `Redactor::event`, and so `RedactingSink::publish` and everything downstream of the bus (history, run snapshot, reports, console), is async and applies the built-in masking and then the rules in config order; `Redactor::text`, `Redactor::value` and `Redactor::check` stay synchronous and apply the built-in masking only, for what cannot wait: `Debug` output, error text and a call's own check results (whose events get the rules when they are published). `ActionCx::new` hides every loaded secret before the run starts, and the auth stage hides each credential as it arrives. A masked value reads as `MASKED` (`••••`). `Redactor::check` masks a check on a masked header whole and drops its diff; any other check has its `expected`, `actual` and `error` masked and its diff made again from the masked values. `Redactor::event` masks `CheckEvaluated`, the failure of `ActionFinished`, `Warned` and `CleanupFinished`, the failure and skip reason of `TestFinished`, and an `Exchanged` call (`exchange_mask.rs`): masked headers whole in the request and the response, and every secret value, hidden field and rule match in the URL (a URL that no longer parses keeps only its scheme and host), the other headers and both bodies (a JSON body field by field, then as text; bytes that are not text replaced whole when they hold a secret). Values are also hidden as a URL's query encodes them. The redactor never cuts a body; whatever keeps one cuts it after masking, so a cut never splits a secret out of reach. The match names every variant, with no catch-all, so a new event has to decide what it masks. A call masks its check results before building a failure from them, and the shells publish through a `RedactingSink` as a second line. Plugin responses and MCP results go through it when those land.

## Hook bridge: TypeScript in QuickJS

Hooks, lifecycle `function:` actions and custom checks are TypeScript or JavaScript functions in the project's `hooks/` folder. They run inside the `vc` binary in an embedded QuickJS engine, sandboxed, with no Node or Bun needed. Other languages run through the plugin protocol instead.

### Loading

1. **Type checking is the user's editor's and CI's job.** `@vibranium/sdk` is a types-only npm package (`BeforeRequestHook`, `AfterResponseHook`, `CustomCheck`, `LifecycleFunction`, the request and response shapes), so `tsc --noEmit` in the project checks hooks. Vibranium itself never type-checks.
2. **Strip and bundle at compile time.** For each referenced file, `oxc` parses it, strips types (including `import type`), resolves relative imports between hook files into one module per entry, and produces JavaScript plus a source map. The result is cached by content hash in `.vibranium/cache/hooks/`.
3. **Allowed imports.** Relative hook files, `@vibranium/sdk` (types only, removed by stripping) and a small built-in module `vibranium:std` (crypto HMAC and hashes, base64, URL and query helpers, time formatting). Anything else, including Node built-ins such as `node:crypto`, is a compile error with a suggestion; npm packages can be used by bundling them into the hooks folder with the user's own bundler.

### Running

```rust
/// Owned by one dedicated OS thread; everything else sends it requests through a queue.
pub struct HookEngine { requests: mpsc::Sender<HookRequest> }

pub struct HookRequest {
    pub hook: HookRef,                     // module + export name
    pub input: serde_json::Value,          // the request, response, vars … as JSON
    pub budget: Budget,                    // time (default 200 ms), memory (default 64 MB)
    pub reply: oneshot::Sender<Result<serde_json::Value, HookError>>,
}
```

The hook thread owns one QuickJS runtime with a context per hook module, created on first use. Each call converts the input JSON into a JS value, calls the export, awaits it if it returns a promise (the QuickJS job queue is drained on the same thread), and converts the result back. An interrupt handler stops a call that runs past its time budget; the memory limit is enforced by the runtime, and a thrown `null` or `undefined` counts as running out of memory, since that is what QuickJS throws when it cannot allocate the out-of-memory error either. There is no file, network, process or environment access, and no `console` yet (a call to it throws `console is not defined`, V5115; D267's run log for it is not built): the only capabilities are the `vibranium:std` functions and a `secret(name)` function that returns secrets declared in .env.schema (each use is logged, and the value is redacted from everything the hook returns). Errors are mapped back through the source map, so a thrown error points to the TypeScript line. QuickJS stops a loop at its jump back and names the line of the code just before the jump's target, which is the code before the loop. So the compiler puts a call to a no-op global, `__vcTick` (`HookModule::LOOP_TICK`), just before each loop (a labelled loop keeps its label), mapped to the loop's line: a call stopped in a loop names that loop.

Measured in the spike: 4.2 MB added to the binary, 3.2 ms to the first call, about 20 µs for a `beforeRequest` call and 36 µs for a custom check. JSON conversion is most of that cost, so inputs are kept small (bodies are passed lazily through a `body()` accessor). One thread serves all hooks; under load, `hooks.threads` can start more (each with its own runtime) and requests are spread across them.

Known limit from the spike: a single long built-in call, such as a pathological regular expression, can run past the time budget before the interrupt is checked. The budget is enforced again from outside by a watchdog that, if a call overruns by more than 1 second, marks the hook thread unusable, fails the call, and starts a fresh thread.

## Results, history store, cache store and reports

### History store (`.vibranium/history.db`)

SQLite in WAL mode through `rusqlite` (bundled, no system library). One writer task owns the connection, receives events, and commits in batches (every 200 ms or 500 events); readers (`vc history`, TUI, web UI, MCP, report generation) open their own read-only connections, which WAL lets run alongside the writer. The ports are `HistoryWriter` (`begin`, `record`, `finish`, `prune`) and `HistoryReader` (`runs`, `run`, `tests`, `snapshot`, `trends`) in `vc-interfaces`; `vc-adapter-store` implements them as `SqliteHistory` (the writer thread, fed by a channel) and `SqliteHistoryReader` (a read-only connection per query; a missing file is an empty history), and `vc-testkit` has `MemoryHistory` with `history_writer_suite` and `history_reader_suite`. Rows reach the writer already redacted and cut; the writer never masks. A failed batch commit does not stop the run: the next `finish` reports it once. Foreign keys are on, so pruning a run deletes its tests, checks, exchanges and snapshot. `trends(window)` sums up each test over the newest `window` runs of kind `run` (G15), in test ID order, as a `TestTrend`: its results that ran (every `examples` row and repeat; skipped results are left out), how many failed or were blocked, how many were flaky, and their mean wall time. `Engine::trends(window)` serves it to the History screens of the TUI and the web UI, which take the runs' pass rates and durations from `runs(limit)`.

In the engine, `Engine::run` begins a run (`kind`, start time, profiles, selectors as typed, seed, `vc` version) before the executor starts and binds its number to `${run.id}` (0 when the history cannot be opened: the run then goes unrecorded with a notice, and its report files go straight into `reports.dir`). The reporter fan-out hands each event to a `Recorder`, which gives back the rows it completes for `Recording::record`; when the run ends the engine renders the report formats from the recorder's `RunSnapshot` into `<reports.dir>/<run>/` (or `--out` as is), first marking the folder as a run's with an empty `.vc-run` file (`mark_run_folder`, as `vc report` does too), then `finish`es the run with the snapshot and prunes on a blocking thread: `Recording::pruning` names the run's report folder root, and once the rows are pruned `prune_run_folders` (`vc-adapter-reporters`) removes each marked `<reports.dir>/<n>/` folder older than the oldest run kept and the run that just ended, leaving anything not named by a plain run number or not marked, and nothing when no run is stored and none just ended; `Engine::prune_history` does the same for `vc history prune`. `Engine::history`, `Engine::stored` and `Engine::prune_history` serve `vc history`; the TUI and the web UI read the same rows through `HistoryReport::runs()`, `StoredRun::run()` and `StoredRun::tests()` (`RunRow`, `RunStart`, `TestRow` and `RunId` are re-exported from `vc_engine`, with `started`, which prints a start time as `vc history` does); `Engine::report` reads a snapshot back and renders it again through the same `FormatRegistry`. `vc run --failed` reads the last run's failed and blocked rows and selects them (`RunRef::Last`, here and for `vc history show` and `vc report`, is the newest run whose kind is not `adhoc`, so a `vc call` never hides the run before it), as `<test>:<n>` instances for an `examples` row (n counted as the planner counts row × repeat), under the last run's profiles.

Bodies are stored per `history.bodies` (default: failures only), cut at `history.maxBodySize` and compressed with zstd. Retention (`history.keep`, default 50 runs, D170) deletes the oldest runs, and their report folders, when a run ends. Schema changes go through numbered migrations stored in the file. The self-hosted server uses the same SQLite `HistoryStore` and migrations, with one writer task (D253); a Postgres adapter stays possible behind the trait.

SQLite, one table:

`SqliteCache` implements the `CacheStore` port (`get`, `put`, which keeps the entry it replaced as an expired tombstone and gives that back, `remove`, `take_expired`, `list`, `clear`; `MemoryCacheStore` and a contract suite in `vc-testkit`). The engine (`cache.rs`) opens it only when the program has a `cache` action and `--no-cache` is not given. The key (`CacheSecret`, zeroed on drop) is `VIB_CACHE_KEY` (64 hex digits) when it is set; else the one the `Keychain` port holds (`OsKeychain::platform()`, D187; `EngineBuilder::keychain` swaps it in tests), generated and stored there on first use. On Linux that is the kernel keyutils session keyring, so the key lasts only for the login session. With neither, the cache is off for the run: `cache` actions run every time and the run prints V5113 as a warning (D166). A lost or different key, or an entry changed on disk, fails to open and reads as a miss, never a failure; a cache that cannot be opened is a warning. Values from `${fake.*}` are left out of the key so a cached admin user is found again. At run start the engine takes the entries expired at `started_ms` and runs their cleanups, oldest entry first and each entry's newest cleanup first, under the profiles the entry was made with; a failed cleanup, or an api that no longer has one, is a warning. The tombstones of the entries fresh results replace during the run are cleaned up the same way at its end, after `afterRun` and the run's own cleanups, and then removed. A tombstone's key is a keyed blake3 tag of the replaced entry's key, time and contents, so it reveals nothing without the cache key. `vc cache clear [id]` removes every entry (or one label's) and runs their cleanups the same way; `vc cache list` reads only the labels, profiles and times, never the sealed values.

### Results and reports

CTRF is the canonical result: the CTRF reporter writes `ctrf.json` from the event stream, with Vibranium-specific fields (lifecycle, blocked-by, checks with source lines) under CTRF's `extra`. JUnit and console reporters derive from the same events. All reporters implement one trait and are chosen by name:

```rust
#[async_trait]
pub trait Reporter: Send {
    async fn on_event(&mut self, event: &Event) -> Result<(), ReportError>;
    async fn finish(&mut self, run: &RunSummary) -> Result<Vec<Artifact>, ReportError>;
}
```

`RunSummary` carries the run's status, totals, start (Unix milliseconds), duration, profiles and the artifacts already written; an `Artifact` names its reporter and the file's path. `vc-adapter-reporters` holds the built-ins in a `ReporterRegistry` (`spec`, `json`, `ctrf`, `junit`; `ReporterRegistry::builtin().create(name, &context)`, an unknown name is `ReportError::Unknown` listing the known ones). Each reporter is built from one `ReporterContext`: the `Arc<Program>`, the `Arc<Plan>` (example rows and repeats for instance labels), a `Destination` (`print` for the console, `save(name, bytes)` for report files; `FsDestination` writes stdout and the report folder), the `Color` (`Color::detect` honours `NO_COLOR` and a terminal), a `Stopwatch` (events carry no times, so in M2 an instance lasts from its first `ActionStarted` to its `TestFinished` as the reporter receives them) and an optional headline, the planner's plan line. The engine finishes the file reporters first and passes their artifacts to the console reporter's `finish`, which prints the `reports` line. CTRF maps `blocked` to `failed` and `flaky` to `passed` (with `flaky: true`), keeping Vibranium's status in `rawStatus`; `specVersion` is `0.2.0`, the version of the CTRF specification and JSON schema (`ctrf-io/ctrf`, `schema/ctrf.schema.json`) the reporter is checked against. The config's `project` (kept in the run's snapshot; `vibranium` when it is not set) names the run: CTRF's `environment.appName`, while `tool.name` stays `vibranium`, and JUnit's `<testsuites name>`. A test, file or profile `name` never replaces its ID: the spec reporter prints `label — name` and `profile dev "Local dev"`, the json reporter adds `name` to `testFinished` and `profileNames` to the summary, CTRF puts `name` and `fileName` in a test's `extra` and the run's `seed` (D131) and `profileNames` in `results.extra`, JUnit writes them as `<properties>` (`seed` and the file's `name` on each testsuite, the test's `name` on its testcase), and the HTML report shows them beside the IDs (`TestView::titled`, `RunSnapshot::profile_names`). There is no `dots` console format in M2. JUnit writes blocked tests as `<error>`. `NoopReporter` reports nothing.

The HTML reporter writes the folder layout from the Technical Design: `index.html` plus `data/summary.js`, `data/index.js`, `data/tests/<shard>.js` and `data/bodies/<hash>.js`, each data file a single `VIB.load(key, json)` call so it loads from `file://`. Test details are sharded by test (one file per test, or per 50 instances for very repetitive tests); bodies are deduplicated by BLAKE3 hash. The single-file layout embeds the same data as gzip and base64 per test and inflates it lazily. The report's front end is a separate small Svelte bundle: its source is `web/src/report/` (a `DataStore` over `VIB.load` or the inflated bundle, the `Report` state class and the page) and it reuses `#lib/results/` (`TestList`, `CheckList`, `ExchangeView`, `RunProgress`) from the web UI's run view. `pnpm build:report` (`vite.report.config.ts`, one IIFE that defines `VIB`) writes `web/report/report.js` and `report.css`, which are committed with a "generated; do not edit" banner so the Rust build needs no Node; `mise run report:check` fails when they are stale. The build refuses output containing `</script` or `<!--`, since `vc-adapter-reporters` inlines it. `report.html` carries a CSP that allows only inline and local scripts and no network. Data is rendered as text only. Budgets at 10,000 tests: first paint under 1 s and opening a test under 100 ms (`web/tests/report.spec.ts`).

### Alerts

The config's `alerts` lower to `Config.alerts`, a list of `Alert { on, profiles, tags, notify }` (vc-model). `on` holds `AlertTrigger`s and defaults to `[failure]`; empty `profiles` or `tags` match every run or test. `notify` holds `AlertChannel { kind, settings }`, one per key of each entry, in written order. The settings stay a `TemplateValue` until the run ends, so `${secret.X}` is rendered only then. `plugins` lower to `Config.plugins`, a list of `PluginRef { id, source, config }`.

When a run ends, `engine/src/alerts.rs` decides which rules fire. It is pure: `decide(rules, &Finished, previous)` returns one `Fired { rule, notice }` per rule that fires.
- `Finished` holds the project, the `RunSummary`, each test's `Ended { test, tags, status, message }`, the load breaches, whether anything ran (a test that was not skipped, or a load iteration) and the report path.
- `previous` is the status of the previous run.
- A rule whose `profiles` share none of the run's is skipped. Otherwise the rule sees only the tests its `tags` pick.
- It fires for the first trigger in `on` that happened, tried in this order:
  - `failure`: a test it sees failed or was blocked;
  - `blocked`: a test it sees was blocked; a rule listing only `blocked` pages when a setup it needs is broken (D256);
  - `threshold`: a load threshold was breached, whatever the tags;
  - `flaky`: a test it sees passed on a retry;
  - `recovery`: the previous run failed, this one ran something and was not cancelled, nothing breached, and none of its tests failed. A run where nothing ran never recovers.
- The `Notice` lists the failures that rule sees (blocked tests included, each `blocked by <id>`), the breaches and the report.

`vc-adapter-notifiers` sends a notice. `NotifierRegistry` maps each channel kind to a `Payload`: the URL from the channel's settings, and the JSON it posts there through the run's `Transport`.
- `webhook {url}` posts the run's CTRF summary, with the notice under `results.extra`.
- `slack {webhook, channel}` posts a Block Kit message.
- `teams {webhook}` posts an Adaptive Card 1.4.
- `pagerduty {routingKey, severity, url}` posts an Events API v2 event:
  - `dedup_key` is `<project>#<profiles>`;
  - a `recovery` resolves the event; any other trigger raises it;
  - `severity` defaults to `error`, and `url` to `https://events.pagerduty.com/v2/enqueue`.
- A message lists at most ten failures, each cut to 200 characters, and counts the rest.
- Errors are V5117:
  - a settings error names the key, never its value;
  - a refused post gives `HTTP <status>`;
  - a transport error has the URL's path, which often holds the hook's secret, replaced with `/…`.

`vc run` sends the alerts once the reporters finish (`engine/src/notify.rs`):
- `Reporters` hands each recorded row to a `Watch`. A `Watch` notes each test's result, with its own tags and its file's.
  - An example row is named `<test>:<n>`, counting from 1.
  - A blocked test's message is `blocked by <id>`.
- `finish` returns an `Ending`: the results and the first report file, which the notice gives relative to the project root.
- `previous` is the status of the last finished run of the same kind (`run` or `load`) in the history under the same profiles, searching the last 50 runs. A `vc run` in which no test ran (exit 2) is passed over, so it never replaces the previous run.
- `vc run` has no load breaches, so `threshold` never fires there.
- A run the executor fails still finishes its reporters and gives a watcher `Done` (exit 70 for an internal error, else 2) before returning the error; it sends no alerts. Its reports and history row say `Cancelled` with no totals, since it has no result, rather than a failed run of zero tests.
- `vc load` sends its alerts once its history run is closed (`Engine::load_alerts`): no tests, each breach as `metric` or `metric of <test>`, and "ran" when it recorded an iteration.
- The notice's `project` is the config's `project`, else the root folder's name.
- Each channel's settings are rendered when the run ends.
  - Only `${secret.X}` and `${env.X}` are read.
  - Reading a declared secret through `env` is refused, so the secret stays masked.
- The channels come from `EngineBuilder::notifiers`, else `NotifierRegistry::standard` over the run's transport.
- Every channel that cannot be built or sent to adds a `V5117: <reason>` line to `RunReport.notices`; the exit code is unchanged.

`vc alerts test` sends a sample instead of a run's notice (`Engine::test_alerts`, `engine/src/alert_samples.rs`; D257).
- The settings and profiles load as for `vc call`; nothing is planned, run or recorded.
- The rules are those whose `profiles` match, ignoring `tags` and `on`; none gives an empty list (exit 2).
- The notice is a `failure` with `Notice.test` set: one passed and one failed test, the failure `<project>#sampleTest`. Every channel's headline starts `[test] `.
- `Payload::then` gives a second body to post once the first was taken; `pagerduty` uses it for a test notice, which it raises as `info` under `dedup_key` `<project>#test` and then resolves.
- Each channel gives an `AlertSent { rule, channel, error }`, the rule counted from 1; `error` is the V5117 reason.

`vc check` warns V5117 at each `alerts[].notify[]` key that names no channel the engine knows, and at each whose settings, written with no `${…}` template, the channel's notifier refuses to build from (`engine/src/check_alerts.rs`). It also reports V3101 when the config has profiles but none is `default: true` and no settings layer (user config, `.env`, `VIB_PROFILE`) names one, since the compiler cannot read those layers (`engine/src/check_profiles.rs`).
- The engine knows the builder's notifier channels, else `NotifierRegistry::standard_channels()`.
- The help gives the close names, else the full list.
- The compiler stays pure: it does not know the channel kinds.

## Import and sync: OpenAPI and HAR

All importers produce the same intermediate form and hand it to `parser::edit` (with the engine's compile guard, D107), so every import respects the naming conventions, writes the documentation header and never reformats existing text.

```rust
#[async_trait]
pub trait Importer: Send + Sync {
    async fn read(&self, source: &ImportSource, opts: &ImportOptions) -> Result<ImportDraft, ImportError>;
    fn source_help(&self) -> Option<&'static str> { None }   // help when the source cannot be fetched
    fn read_help(&self) -> Option<&'static str> { None }     // help when the source cannot be read as this kind
    fn reads_folders(&self) -> bool { false }                 // Bruno: a folder source is read file by file
    fn keeps_snapshot(&self) -> bool { false }                // OpenAPI: the draft has a snapshot, so the engine
                                                              // guards openapi/<fileId>.yaml before the fetch and the write
}

pub struct ImportDraft {
    pub groups: Vec<DraftGroup>,          // one per target api file (existing or new)
    pub flow: Option<DraftFlow>,          // HAR: the recorded order as steps with chained saves
    pub secrets: Vec<SecretFinding>,      // removed values and where they map to
    pub notes: Vec<ImportNote>,           // things the user should know (skipped entries, guesses)
    pub summary: Option<String>,          // HAR: what was read and filtered, one line
    pub snapshot: Option<Value>,          // OpenAPI: the bundled 3.1 document for openapi/<fileId>.yaml
}
pub struct DraftApi { pub id: String, pub name: Option<String>, pub method: Method, pub path: String,
                      pub vars: IndexMap<String, Value>, pub query: IndexMap<String, String>,
                      pub body: Option<Value>, pub content_type: Option<String>,
                      pub operation_id: Option<String>, pub matches: Option<String> }
```

The draft types live in `vc-interfaces` (`import.rs`). They hold text and JSON values, not the program's `Sym`, `Template` or `ApiId`: an importer has no string table, and the engine renders the draft into YAML that the compiler then checks like any other edit. Template text such as `${var.userId}` stays text until then. A `DraftGroup` is one api file (`file_id`, `name`, `base_url`, the `config_vars` it needs, its `apis` and the `tests` that `--tests`, `--negative` and `--auth` ask for); a `DraftFlow` is HAR's recorded order as `DraftStep`s with `save`s. An `ImportNote` is an `at` (an operation or a JSON pointer) and a `message`; it has no code or span, because it points into the foreign file, not a definition file. `ImportError` is `UnknownKind`, `Invalid` (with the location), `Cycle` (the `$ref` chain) or `Fetch`.

Importers get the documents a file refers to through the `SpecFetcher` port (`fetch(location) -> bytes`, `list(folder) -> Vec<String>`, the files under a folder by relative path in path order, none for a URL, a file or a hidden path, and `decode(location, bytes) -> serde_json::Value`, which the engine does with vc-parser because an adapter may not depend on it; `FetchError::Failed`, `NotAllowed` or `Undecodable`); `resolve_reference(base, ref)` joins a relative `$ref` to its base and refuses one that climbs above the base's root. The engine implements the port over `Transport` for URLs and over `SourceProvider` for files, so nothing outside the project is read, nor a hidden file or folder inside it (a `$ref` to `.env` or `.vibranium/` is `FetchError::NotAllowed`). `vc-adapter-importers` holds the `ImporterRegistry` (`ImporterRegistry::builtin().create(kind, fetcher)`, an unknown kind is `ImportError::UnknownKind` listing the known ones); every importer runs `vc_testkit::importer_suite`, and `vc_testkit::FakeImporter` reads a made-up `METHOD /path` format for engine tests. The engine's `import(&ImportRequest) -> Changes` reads the spec once through its `ProjectFetcher` (`fetch.rs`), or takes it from `ImportRequest.text` when the web UI sends the text itself (`source` then only names it), has the registry's importer draft it and writes the draft: a spec's (one with a snapshot) as new files (`import_write.rs`, below), a recording's (HAR, curl) merged into the project (`import_recorded.rs`, under HAR). `Engine::importers()` lists the registry's names in name order, for `vc import`'s refusal and the TUI's Import tab. `Engine::spec_location(base, source)` gives `ImportRequest.source` for both apps: a URL as given, a path from `base` when relative, canonicalised and made project-relative by `Engine::project_path`, which canonicalises the root as well, so a root reached through a link (macOS `/tmp`) or with `..` in it still holds its files (refused with `EngineError::Edit` when it is not in the project). `ImportRequest` carries a recording's `flow` and `keep` (`Keep { hosts, assets }`, from `--include-host` and `--keep-static`), and the engine fills `ImportOptions.recording.hosts` with the hosts the profiles' base URLs render to. `sync(&SyncRequest) -> SyncReport` (`changes`, `drift`, `conflicts`; `SyncMode` is `Write`, `DryRun` or `Check`; `settle` holds the `--take`/`--resolved` answers as `(apiId, SyncSide)`) runs the three-way merge below. `load(&LoadRequest, LoadWatch) -> LoadReport` runs one load scenario (see "Load engine").

### OpenAPI

- **Reading.** Fetch the URL (`source.headers`, rendered against the active profile, are not sent yet) or read the file from the project; detect JSON or YAML by content; detect the version from `openapi`/`swagger`. Swagger 2.0 is converted to 3.1 first (a mechanical mapping of `definitions`, `parameters`, `consumes`/`produces`), and 3.0 is up-converted to 3.1 the same way (`nullable`, `exclusiveMinimum`/`exclusiveMaximum`, `example`); everything is then read with `oas3` (D199). YAML goes through vc-parser to `serde_json::Value` first. External `$ref`s are fetched and bundled.
- **Snapshot.** The bundled 3.1 document is written to `openapi/<fileId>.yaml` in a canonical form (keys sorted, YAML block style, two comment lines naming the source), so it diffs well. It is not a definition file: the compile guard sees it as a file of no kind, which it only parses, so a generated test's schema `$file` into it resolves. Import and sync check the snapshot with `SnapshotGuard` (`snapshot_guard.rs`) before the fetch and again after it, and are refused when writing it would change a spec: the spec is read from a snapshot path `openapi/<id>.yaml` or a file that leads to one, the snapshot path leads to another file (`SourceProvider::real`: a link, or another case on a file system that ignores case), or it is the spec another api file's `source.openapi` names. `FileChange::before` holds the snapshot as it is (an import reads it too, so `--dry-run` shows an overwrite as a diff), and `Engine::write` writes a snapshot with `SourceWriter::write_unchanged` against that text's hash: it renames over the file rather than writing into it, so a hard link there leaves the spec as it was, and a file or link put there after the check is refused.
- **Mapping.** One api per operation (filtered by `--include` tags or path prefixes, matched by whole segments so `/user` keeps `/user/{id}` but not `/users`, and `--only` operation or draft IDs); ID from `operationId` in camelCase or from method and path, with `2`, `3`… added to a clash in spec order over every operation, so a filter never changes an ID; path parameters become `${var.name}`; query parameters become vars with the spec's defaults; required body fields become vars with generators matched to type and format. An api that creates what another's path names (the `POST` on the collection above a `{param}`) gets the `save` of that param and a `cleanup` calling the item's `DELETE` (`openapi/creators.rs`). What cannot be carried over (a TRACE operation, an unresolved `$ref`, a body field named like a parameter) is an `ImportNote`.
- **Writing.** The engine renders each `DraftGroup` with `yaml_out.rs` (block YAML in the house key order): the api file at its derived path with `id`, `name`, `baseUrl`, `source` (`openapi`, `include`, `only`; D277) and the apis; the tests, when asked for, in the test file `<fileId>.openapi` (`openapi/cases.rs`: the creators in `before`, the last one `keep: true` for a `DELETE`, or a `skip` reason when nothing creates the item; the first 2xx and the success schema as a `$file` into the snapshot; `--negative`'s `examples` rows from `openapi/negative.rs`, a body missing, mistyped or outside its enum per field, expecting 400 or 422); the base-URL var through the same `base_var` as `vc new api`, reusing a config var that holds the origin. An api or test file that exists is refused (help: `vc sync <fileId>`). Notes go into `Changes.titles` as `at: message`. With no `--id`, the file ID is the spec's file name up to its first dot.
- **Three-way sync.** `sync.rs` picks the api files (the ones named, else every one with a `source`), fetches each `source.openapi` and reads its snapshot `openapi/<fileId>.yaml`, both drafted by the openapi importer with the file's `source.include` and `source.only`. For each operation, matched by `operationId`, `sync_rules.rs` decides from whether base (the old snapshot), theirs (the new spec) and mine (the api file) have it: add it, mark it `deprecated: true`, merge it, or leave it (one the user removed stays removed). A merge compares, field by field, what sync owns: `method`, `path`, each `query` entry and the `content-type` header; each row of the CLI doc's rule table is one arm of `field`. A value taken from the spec brings the `${var.x}` it reads, with the spec's default, when the api has no such var. `sync_plan.rs` turns this into `Step`s (set, put, remove, deprecate, append) and a line each for the user (`↑` taken, `+` added, `-` deprecated, `=` kept, `!` conflict, `~` listed only: an optional query param the spec added that the file does not send, from the importer's `DraftApi.optional_query`, or one it dropped that the file still sends); `sync_apply.rs` makes the steps one at a time with `parser::edit`, re-reading the file after each, and refuses (help: make it by hand) one the file's layout does not allow, such as removing from a `{..}` map. A conflict, where both sides changed a field differently, or a new operation whose ID the file already uses, leaves the api as it is and is listed with its `--take spec`, `--take mine` and `--resolved` answers; `--take spec` takes the spec's values, `--take mine` and `--resolved` keep the file's. The api files pass the compile guard; the new snapshot (`sync_snapshot.rs`) is the spec, except that a conflicted operation keeps its old snapshot entry, so the next sync sees the same conflict; after putting one back it also keeps the old components the new snapshot lacks, which that entry may refer to. Drift is a spec whose bundled document differs from its snapshot's (or has none); drift with no line for the file gets `~ <fileId> the spec changed outside what sync takes into the file: only the snapshot is updated`, so `--check` never exits 4 silently. `--dry-run` shows the lines and diffs and writes nothing; `--check` shows the lines and exits 4 on drift.

### HAR

- **Reading** with the `har` crate (HAR 1.2 and 1.3), into private serde structs that keep only what drafting needs (method, URL, header names, the request body, the response type); none derives `Debug`, so a recorded value cannot reach a log. `HarImporter` is the registry's `har` entry (`importers/src/har/`).
- **Filtering.** Static assets are found by MIME type and extension (and any scheme other than http and https), third-party hosts by comparison with the hosts the active profile's base-URL vars resolve to, and preflights by method. The engine passes those hosts in `ImportOptions.recording` (a `RecordingFilter`); a project with no base-URL var compares with the site of the recording's first entry. A host given with `--include-host` is kept whatever its site, and `--keep-static` keeps static files. A site is a host's last two labels (an IP address or `localhost` whole); public suffixes such as `co.uk` are not handled, since there is no public-suffix list. The draft's `summary` counts them: `read 12 entries · filtered 3 static, 1 third-party, 1 OPTIONS → 7 requests`. When nothing is kept, the error appends an `--include-host <host>` for each third-party host it dropped. An importer's `read_help` gives the help for a file it cannot read (the `OpenAPI` one names `--include` and `--only`, the HAR one `--include-host`); the engine's generic help is for the rest.
- **Host mapping.** The importer drafts one group per origin. The engine (`import_homes.rs`, `import_recorded.rs`) renders each api file's `baseUrl` under the request's profiles to an origin and base path (`Home`), and merges a group into the file with its origin whose base path every api's path is under, the longest winning; an unknown origin becomes a new api file, named by the conventions, with a base-URL var added to the config (`base_var_in`), and one whose file ID is taken by a file pointing elsewhere is refused (help: the `--profile` that points it there, or `vc rename`). Its file ID is the host's first label other than `www` and `api` (`api.shop.test` → `shop`, `pay.shop.test` → `pay`), with `2`, `3`… added when taken; its var is `<fileId>Url`. A user and password in the URL are dropped with a note.
- **Path templating.** Path segments that look like identifiers (UUIDs, numeric IDs, prefixed IDs such as `ord_8Kq2Tz`, long hex) become vars named after the preceding segment (`/orders/{x}` → `orderId`). Requests that differ only in those segments are merged into one api, noted `recorded 2 times, merged into one api`. An api's ID says what the call does: `getCart`, `listOrders`, `createOrder`, `addItem` (`POST /carts/{id}/items`), `cancelOrder` (`POST /orders/{id}/cancel`); another method or shape is named by its route.
- **Matching.** A request whose method and path shape (each `${…}` or `{…}` as `{}`, after the base path is taken off) equal an existing api is reused, not duplicated, and the flow's steps send its vars under that api's names (positionally); the rest are appended to the file with one comment line each, under a free ID (`addItem2` when taken). Edits to one file chain through `Staged`, so each sees the last.
- **Body vars.** Body fields become api vars, with the recorded values as defaults.
- **Chaining.** Values that appear in a response and later in a request (an ID returned by one call and used in a later URL or body) become `save` entries and `${var.…}` references in the flow, which is how the recorded session replays with fresh data. With `--flow <fileId>#<testId>` (`ImportOptions.flow`) the draft's `DraftFlow` has a step per kept request in recorded order (`importers/src/har/flow.rs`). A JSON response's values that look like IDs (the path rule, or a number under a key `id`, `…Id` or `…_id`; up to six levels deep and ten items of a list) are remembered with the template that reads them; a later request's path or top-level body var holding one is sent as `${var.<var>}`, and the step that first got the value saves it under that var's name (`cartId: ${response.body.id}`, `2`, `3`… added when the name is taken). A step sends only the vars that are chained or differ from its api's defaults, so a repeated call keeps its own values. A query value is not chained. Only templates over a response are written, never a value it held.
- **Secrets.** `Authorization` and cookies are dropped and mapped to the file's auth, with a note per header and no value. Query or body fields with secret-like names (the shared `secrets::credential` rule), or high-entropy values in a path, query or body (24 or more characters with lower case, upper case and digits, at least 16 of them different, and not shaped like an ID; or 32 or more letters and digits, both present, with letters of one case only, hex among them, and at least 10 of them different), become `${secret.NAME}` references, named `<FILE>_<FIELD>` in upper snake case (`PAY_API_KEY`), each listed in the draft's `secrets` with where it was found, which is the entry proposed for `.env.schema`. The engine appends the undeclared ones to `.env.schema` when the project has one (the guard compiles with that change, so V2106 sees them), and otherwise says in a line what to add. The flow becomes a test in its file (`<fileId>#<testId>`, refused when taken), its calls pointed at the apis reused or added. `Changes.titles` are `Import <n> apis from <source>`, the summary, a line per host (`api.shop.test → shop (existing)  1 matched, 4 new · auth shopToken`, or `no auth yet: vc new auth …` when a credential header was dropped and the file has none), the secrets line, the `.env.schema` line, the flow line and the remaining notes grouped by message (`import_titles.rs`). `vc import har` prints them after the change, or with `--dry-run` before the diffs, writing nothing. A recorded value never reaches a written file, a note, the dry-run diff or `Debug` output; a test greps them all for the sample's recorded values.

### cURL

- **Reading.** The file is read as bash reads a command line: words split at blanks, `'…'`, `"…"` and `$'…'` quotes, backslash escapes, line continuations and `#` comments. Each unquoted `curl` word starts a command, which ends at the next `curl` or at an operator (`|`, `;`, `&`, `>`, an unescaped line break), so a `$` prompt or a `| jq .` is read past. Each option is an entry of one table (`--long`, `-s` with bundles such as `-sXPOST`); one with no api form (output, timeouts, TLS, verbosity) is read past, an unknown one is noted.
- **Mapping.** The method is `-X`, else HEAD for `-I`, POST when data is sent in a body, GET otherwise. The first command's origin becomes the base-URL var `<fileId>Url`; a command calling another origin is skipped with a note. Path segments that look like IDs become vars by the HAR rule (`/users/u_7f3k` → `${var.userId}`, in `path_vars.rs`, shared with HAR). The query, and `-G` data, become the api's query, decoded. JSON data keeps its shape, each top-level field a var with the command's value as its default; form data and `-F` fields become body maps with their content type; other data is text. A second command with the same method and templated path is noted, not drafted again. There is no spec to sync, so the api file has no `source` and no snapshot is written.
- **Credentials.** `authorization`, cookies and other secret-named headers, `-u`, `-b`, `--oauth2-bearer`, a URL's user and password, and secret-named query and body fields (`secrets.rs`) are never written: a body field is written empty, the rest left out, and a note names each one, never its value. `-d @file` and `-F name=@file` files are not read.

### Postman

- **Reading.** `PostmanImporter` (`importers/src/postman/`, the registry's `postman` entry) reads a collection whose `info.schema` names v2.1 into private serde structs that derive no `Debug`; any other file is `Invalid` with the help to export Collection v2.1. Requests are walked in order through their folders, each inheriting the auth of the request, else the nearest folder, else the collection (`noauth` sends none, `inherit` looks further up). A request written as a bare URL is a `GET` of it.
- **Variables.** A URL's leading `{{name}}`s are looked up in the collection's variables (up to eight deep) to find its origin; requests are then grouped by origin as for HAR (`origin.rs`, shared), and the engine merges them into the project the same way (`import_recorded.rs`). An origin that stays unknown is the importer's fallback file with its base-URL var set to `http://localhost`, noted. Elsewhere `{{name}}` becomes `${var.<camel>}`, with the collection's value, scrubbed, as the api's default (empty, noted, when it has none and no script saves it); a credential-named one is a `${secret.…}` reference; a dynamic one is the generator from one table (`{{$guid}}` → `${fake.string.uuid}`), else left as written, noted. In a JSON body an unquoted `{{qty}}` is quoted so the text stays JSON. `:name` path variables take their default from the URL's `variable` list.
- **Mapping.** One api per request: ID the request's name in camelCase (else by method and path, as for HAR), `free` adding `2`, `3`… when taken; `name` the request's name. The path goes through the HAR path rule; the enabled query parameters become the query; the body by mode from one table (`raw` by the `Content-Type` header, else its language; `urlencoded` as a form; `graphql` as JSON), read by the shared `body.rs`, while `formdata` and `file` bodies are left out, noted. Other headers are noted, not imported.
- **Secrets.** The auth block is never written: an `apikey` in the query becomes a `${secret.<FILE>_<KEY>}` query entry, any other auth a note that it maps to the file's auth, as do credential headers (D3, the HAR rules). Secret-named and high-entropy values in paths, queries, bodies and variables become references through the shared `secret.rs`, listed in the draft's `secrets`. A collection's values never reach a written file, a note or `Debug` output; a test greps them all.
- **Scripts.** Scripts are not imported, noted, apart from a test script's `pm.environment.set("cartId", pm.response.json().id)` (and the `collectionVariables`, `globals`, `variables` and `postman.set…` forms, directly or through `var data = pm.response.json()`), which `script.rs` reads into a `save` of `cartId: ${response.body.id}`. With `--flow`, the `DraftFlow` has a step per request in collection order; a step sends `${var.x}` for an api var an earlier step saved. The summary reads `collection Shop · 8 requests in 2 folders`.

The variables, mapping, secrets and `--flow` rules above live in `importers/src/collected/`, shared by the collection importers: each reads its own file into neutral `Call`s (URL text, path values, enabled query and headers, where its auth sends a credential, a `Payload`, notes) and its variables into `Values`; `postman/` keeps only its serde structs, the mode and language tables, and `script.rs`. The Bruno importer reads into the same form.

### .http

- **Reading.** A `.http` file (the VS Code REST Client and JetBrains HTTP Client format, D130) is read by `http/parse.rs`: requests are separated by `###` lines, whose text is the request's title; `#` and `//` lines are comments, `# @name x` names a request and `@x = value` defines a file variable. The request line is `METHOD url [HTTP/x]` (GET when the method is left out), its URL full, a path or starting with a `{{variable}}` (anything else makes the file `Invalid`), continued by lines starting with `?` or `&`; headers follow until a blank line, then the body. A response handler (`> …`) ends the body and is noted; a body read from a file (`< path`) is not read.
- **Mapping.** `http/templates.rs` resolves `{{…}}`: a file variable is its value (each resolved with those defined before it); `{{$guid}}`, `{{$uuid}}` and `{{$random.uuid}}` are `${fake.string.uuid}`, `{{$randomInt a b}}` is `${fake.number.int(a, b)}`, and another dynamic variable is sent as written with a note; a request variable (`{{login.response.body.$.id}}`) is the var `loginId`, with a note; anything else is `${var.<camel>}`. Each request then becomes a curl `Request` and is drafted by the curl rules (one origin, IDs in paths as vars, JSON fields as vars, duplicates noted, `draft(requests, opts, "request")`), its title (else its `@name`) the api's name. A body with no content type is JSON when it parses, else `text/plain`. A URL that starts with an undefined variable is sent to `http://localhost` with a note; a bare path goes to its `Host` header. A var an api reads that nothing defines, or a body field set to a var of its own name, is written `""` with a note.
- **Credentials.** A file variable named like a credential (`secrets.rs`) is never substituted, so its references stay vars and the draft never holds its value; credential headers and body fields follow the curl rules.

### Bruno

- **Reading.** `bruno/collection.rs` reads a collection exported from Bruno as JSON (D209), and `bruno/folder.rs` builds the same `Collection` from a collection folder (D254), so both draft the same: `name`, `items` (folders and requests by `type`, sorted by `seq`), `environments` and `root`. `http` and `graphql` items (and the older `http-request`, `graphql-request`) are requests; a `grpc` or `ws` item is noted, not imported. A file without `items` is `Invalid` with "export the collection as JSON from Bruno". A request inherits the auth of the nearest folder or collection `root` that sets one (`inherit` defers, `none` sends none) and their headers before its own.
- **Mapping.** `bruno/calls.rs` turns each request into a `collected::Call`: the URL as written, `params` of type `path` as path values and of type `query` as the query, the enabled headers, the body by a mode table (`json`, `text`, `xml`, `sparql` as text with their content type, `formUrlEncoded` as a form, `graphql`; `multipartForm` and `file` noted), and an api key placed in `queryparams` as a query secret. The vars are the collection's `root` vars with the first environment's values over them; its other environments are noted. An environment variable marked `secret` (`Values::with_secrets`) and `{{process.env.NAME}}` are `${secret.<FILE>_NAME}` references whose values are never looked up.
- **Saves.** A post-response var whose value reads the body (`res.body.id`, `res.getBody().items[0].id`) is the step's `save` (`${response.body.id}`); any other is dropped. Scripts, tests, assertions and request vars are noted.
- **A folder (D254).** `BrunoImporter::reads_folders()` is true, so when `SpecFetcher::list(source)` names files the engine hands the importer an `ImportSource` with no bytes, and the importer fetches `bruno.json` and each `.bru` file itself (other files are not read). `bruno/bru.rs` parses the `.bru` blocks: a dictionary (`name: value`, split at the first colon, `~` off), a list (`vars:secret [a, b]`) or text (`body:json`, `script:*`, `tests`), outdented by two spaces; an unclosed block is `Invalid` with the file's path and the block's name, never its text. `bruno/folder.rs` maps the folder: `bruno.json` names the collection and its `ignore` paths are not read; `collection.bru` is the `root`; `environments/<Name>.bru` is environment `Name`, its `vars:secret` names secret variables without values; each subfolder is a folder item named and ordered by its `folder.bru` `meta` (else its own name), which is also its `root`; each other `.bru` file is an item by its `meta` (`name`, else the file stem; `type`; `seq`), whose request is its method block (`get` … `trace`: `url`, `body` mode, `auth` mode) with `params:query`, `params:path`, `headers`, `body:<mode>`, `auth:apikey`, `script:*`, `vars:*`, `tests` and `assert`. A folder without `bruno.json` is `Invalid` with "it is not a Bruno collection: the folder has no bruno.json". A source that cannot be fetched carries `Importer::source_help`, for Bruno "give the Bruno collection's folder (the one with its bruno.json) or the collection exported as JSON".

`vc migrate v1` (D200) is not an importer: `importers::migrate_v1` (module `v1/`) takes the JSON files of a v1 project by path (`config.json`, and the `scenarios`, `payloads` and `schemas` under its `tests_directory`) and returns a `V1Migration`: whole files as `serde_json::Value`s (the config, an api file per collection, a test file per scenario at `services/<collection>/<area>.test.yaml`), the secret names the auth reads, and notes. A test is the endpoint's api called after its dependencies: a cached one is a `beforeAll` call with `save`, read through `${var.<call>.<name>}`, any other a `before` call; `repeat-until` is a `poll`, `ignore` a `skip`, and expect asserts of the common shapes `body.match` entries; a `schema` reference is inlined as `body.schema`. What has no v2 form (scripts, other asserts, a var only a script set, which the api gets as `""`) is a TODO on the file's item; `delay`, `async`, `timing.wait` and a repeat's delay are notes. `Engine::migrate_v1(folder)` reads the `.json` files under the folder, renders each file with its header in the house style (`format::house_style`), puts `# TODO(vc migrate): <text>` above the item's `- id:` (above `tests:` for the file), passes the files through the compile guard and adds the missing names to `.env.schema`; it refuses a project that has a config.

## Load engine

The load engine reuses the executor's action runner, so a test behaves the same in a load run as in a functional run; only scheduling and recording differ. The executor exposes that runner to it as the `Iterations` trait: `iterate(test, user)` runs one instance of a test, from `beforeEach` to its cleanups, against the shared slots the run's `beforeRun` and `beforeAll` filled, and returns an `IterationReport` (passed, each call's api, status and elapsed time, and the first failure as an `IterationFailure`: the api of the action that failed, the status of that action's last call, the diagnostic code and the message). A failure is a report the load engine counts, not an error.

- **Model.** A closed model of virtual users. A stage controller adjusts the number of user tasks once per second toward the stage target (linear ramp from the previous stage's count). Each user task loops: pick a test from the mix by weight (a precomputed alias table), run one instance of it with `checks: api` or `full`, then sleep the think time.
- **Run loop.** `run_load(scenario, LoadParts, matching)` is the shell around the pure parts. `Matching` pairs the matcher registry with a `Sync` renderer of literal arguments, so the run's future stays `Send`; each judgement builds its `Judge` from it. The stage loop runs on a one-second tick. Each tick closes the second before it and sends a `Second` (users, the closed rows, the rolling window's totals and the thresholds breaching in it) to the caller's channel, then moves the stages on. Each user is a tokio task whose retire frame is a child of the run's frame. A retired user finishes the iteration it is in first, and an iteration that ends after the run is cancelled is not recorded. When the run ends, the loop waits for the users still running, sends the open seconds as one last `Second` and judges the whole run. Its `LoadOutcome` says how the run ended (`Finished`, `Aborted` or `Cancelled`).
- **Lifecycle.** `beforeRun` and each mixed file's `beforeAll` run once before the first stage, through the same shared slots as a functional run; `beforeEach`, `before` and cleanups run inside every iteration and are counted separately from the mix. The executor's `ProgramIterations` is the `Iterations` the engine hands the load run. The order is pure: `LoadLifecycle::new(&Plan)` (in `machine/`) lists the `prepare` actions with their owners and the `finish` steps (`Act` or `Clean` per owner), and the shell only carries the list out through `Crew::act`, which fills the shared slots as in a functional run. `prepare` runs the shared actions in order; if one fails or is cut, `unwind` runs the cleanups registered so far and the load run does not start (`SharedFailed`, which the engine reports as V5106 naming the action). Each iteration runs the test's first planned instance under a child of `users()`, the load run's frame, so an `abortOn` breach cuts the iterations but not the root. With `checks: api`, a call judges only its api's own `expect`, plus the default `status: 2xx` when that `expect` checks no status. `finish` runs each file's `afterAll` and its cleanups, newest first, then `afterRun` and the run's cleanups. Once the root is cancelled, `afterAll` and `afterRun` are skipped (`LifecycleStep::runs`); an abort stops the cleanups.
- **Measuring.** Each iteration records latency from its scheduled start, not from when the request was actually sent, so a tool that falls behind cannot hide a slow server (coordinated omission). User tasks send each iteration to a recorder task as a `Sample` (test, second, latency, failed); the recorder keeps one `hdrhistogram` per test and per api per second (1 µs to 60 s, 3 significant digits) and writes one row per test per second. A histogram is about 140 KB, so users send samples, not histograms. Errors are counted by kind: each failed iteration the run keeps (one that ends after a cancel or an abort is in neither the errors nor a kind; `LoadParts::failed` gets it only once its `Sample` is sent) under the api of the action that failed, the status of that action's last call and the failure's code (`V5101` for a check, `V5105` for a transport error, `V5111` for a template). A `before` call or cleanup around it is never blamed for it. An iteration that passes only on a retry counts as an error (only a `Passed` verdict passes), blamed as its verdict is: on the call that failed its last failed attempt, which is also the blame when the last attempt is cut short; the shell keeps that attempt's failing calls (`earlier_failing`) for it. A failure with no api (a `function` or `command` action, or a test not in the plan) is counted under the test instead. The report shows each kind as `errors users#list 200 V5101 × 12`, and its JSON as `{api, test, status, code, count}` (not yet: the first five exchanges per error kind). `Engine::load` writes the history run with kind `load`, its totals counting iterations (passed is iterations less errors, failed is errors; `vc history` lists it as `load · 40 iterations · 3 errors`), and one `Row::Interval` (test, second, count, errors, encoded histogram) per test per second into `load_intervals`; threshold values are literals, since a load run has no call for a reference to read.
- **Thresholds.** Thresholds are evaluated every second on a rolling window and at the end: rolling thresholds use the last 10 s (`WINDOW_SECONDS`); the final verdict uses the whole run. Each `Breach` carries its metric's `Unit` (`ms` for the latencies, `share` for `errorRate`, `perSecond` for `rps`) and its limit, the matcher's arguments as `Judge::expected` renders them (a duration in ms, `1%` as 0.01). The report shows a breach as `breached p99 at 45.471 ms (lt 30 ms)`, the actual and the limit with the same decimals (`Unit::breach`): three, or up to six where fewer would round a number of the limit or show the actual as one, or as 0 when it is not (`at 30.0004 ms (lte 30 ms)`, `at 1.0006 ms (lte 1.0005 ms)`), and past six both exactly, so a breach never reads as a pass. Its JSON is `{metric, test, actual, unit, limit}`, with `actual` not rounded and `limit` as the matcher gives it; the report's other values are rounded to their unit's places. A rolling breach of an `abortOn` metric cancels the run through the same cancellation tree; cleanups still run. Exit code 3 comes only from the final evaluation.
- **Capacity.** The target is 5,000 users on one 8-core machine at under 70% tool CPU. Users are lightweight tokio tasks; connection reuse comes from the transport's pool; event detail drops to aggregates (no per-exchange events) above 50 users unless `--trace` asks otherwise (not yet: `--trace`; a load run sends no per-exchange events at any size).
- **Live view.** The CLI, TUI and web UI subscribe to a once-per-second summary event, `Event::LoadTick` (second, users, whole rps over the last 3 s (`RATE_SECONDS`, fewer in the first seconds) so a second that closed with few iterations does not make it jump, p50, p95 and p99 as durations, and errors over the rolling window, and the names of the thresholds breaching in it). `Engine::load(request, LoadWatch)` sends it to `LoadWatch.ticks` with `try_send`, so a slow view drops ticks instead of slowing the run; each value of `LoadWatch.interrupts` is one Ctrl-C (cancel, skip the grace period, abandon the cleanups). The `LoadReport` holds the scenario's `name` (its summary line reads `checkout.peak — Peak checkout · finished after …`), the whole run's numbers (rps, p50, p90, p95, p99 and max), breaches, error kinds and exit code (0, 1 blocked by a shared action, 3 breached, 130 cancelled).

## Interfaces

Every interface is a thin adapter over the `engine` facade, so a capability added to the engine appears in all of them. The facade's methods are also the `vibranium.engine.v1` service that the web UI, SDKs and remote agents call.

### CLI (`apps/cli`)

`clap` derive commands as listed in the CLI and Developer Workflow doc; the global flag `--project <dir>` (the others are per command). Console output is written by the console reporter (spec, dots, json) and the diagnostics `TextRenderer`; colour and progress bars switch off when stdout is not a terminal. Exit codes follow that doc (0 pass, 1 failed or blocked, 2 nothing ran, 3 load threshold, 4 sync drift), plus 130 when cancelled and 70 for an internal error, which prints a report hint and writes a redacted debug bundle (D127). `vc-cli` owns `main` and dispatches `vc tui`, `vc mcp` and `vc ui` to their app crates (D110). `vc completion <shell>` generates static completion plus a dynamic hook (`vc __complete`) that lists project IDs.

So far (M2) the CLI has `vc check [--json] [paths…]`, `vc schema export [--out <dir>]`, `vc plan`, `vc run` and `vc list`. `vc check` finds the project from the working folder (`EngineBuilder::for_project`), calls `Engine::check(CheckRequest { paths })` and prints the report with `TextRenderer` (colour only on a terminal without `NO_COLOR`) followed by a summary line, or with `JsonRenderer` under `--json`. Paths are resolved against the working folder, or the project root under `--project`, and must lie in the project. `vc schema export` needs no project: `Engine::schema_bundle()` prints one object keyed by kind, `Engine::schema_export()` gives the `<kind>.schema.json` files for `--out`. `vc plan`, `vc run` and `vc list` take the selectors of cli-workflow's "Selecting what to run" (a selector naming an existing file or folder is a project path, anything else an ID) and build a `PlanRequest` (`--profile`, `--set`, `--repeat`) or `ListRequest`. `Engine::plan` resolves the settings in layers (D129: built-in < user config < config < profiles < `.env` < `VIB_*` < `--set`, each value keeping its origin; `EngineBuilder::user_config(path)` replaces the default user-config path for tests), asks the `Vcs` port for `--changed` (D179), compiles and plans. `Engine::run` runs that plan on a Tokio runtime the CLI owns, fans the event stream out to the console reporter (`spec`, `json`) and the file reporters (`--report` over `reports.formats`, into `--out` over `reports.dir`), lets the file reporters finish first so the console can print their paths, and returns the exit code; Ctrl-C reaches the executor through the `Interrupter` from `vc_engine::interrupts()` (exit 130). `command:` actions run through the `CommandRunner` port (`EngineBuilder::commands`, `ProcessRunner` by default, D181). `vc list apis` and `vc list files` take the same selectors as `vc list tests` (`select_apis`, `select_files` in `vc-planner`); apis have no tags, so `-t` with `list apis` is a selection error. The end-to-end suite (`crates/apps/cli/tests/e2e`) runs the real binary against `vc-mock-server`. A failing run prints its seed. Everything a user can fix (no project, a missing `--project` folder, an unknown profile, `--set` key or reporter, an empty selection, a path outside it or with no definition files, an unwritable `--out`) prints `error: …` and exits 2; any other error or a panic exits 70 with the "please report" hint.

M5 stream B adds these commands:

- **`vc explain <code>`** prints `Code::explain()`, the page from `crates/diagnostics/explain/<code>.md`, which is built into the binary with `include_str!`. Headings lose their `#`s and example lines are indented without their fences. It needs no project. A code with no page yet prints its title alone.
- **`vc explain <id>`** calls `Engine::explain(target, &ExplainRequest { profiles, sets })`. It resolves the settings as `vc plan` does, then shows the api or test for the active profile: the request line with the final URL, vars with their level, auth, the merged `expect`, steps, and lifecycle and cleanup.
- **`vc config explain <key>`** calls `Engine::config_explain`, which is `Engine::config_values` for one key printed as text, so its values are masked the same way (D232). It lists the layer that set the value, then each value it replaced (`  over 30s  (built-in)`). An unknown key is an `EngineError::Selection` with the closest key.
- **`vc completion <shell>`** writes the `clap_complete` script for bash, zsh, fish or PowerShell, plus a short hook. The hook calls the hidden `vc __complete <command|flag> <word>`, which prints `Engine::complete(CompleteKind, prefix)`, one candidate per line:
  - `Tests`: file and test IDs, after `run`, `plan` and `list`.
  - `Apis`: api file and api IDs, after `call`.
  - `Ids`: both, after `explain`.
  - `Profiles` and `Tags`: completed after the last comma.
  - Outside a project, or in one with errors, it prints nothing.
- **`vc demo start|stop`** spawns the `vc-demo` binary, looked up next to `vc` first and then on `PATH`; when neither has it, `start` exits 2 naming the folder of `vc` and PATH, with the install command as help. `--detach` waits until the demo it launched answers (its `/echo` names the pid in `x-vc-demo-pid`), then writes `<port>.pid` in `vibranium-demo-<uid>`, a folder in the temp folder made with mode 0700 and refused when it is a link or not the user's. Joins are files `<pid>.<n>` in `<port>.users` beside it; one counts while that pid lives or for an hour after it was made. A `start` whose demo ended because another took the port joins that one. The demo runs with null stdio in a process group of its own; on Windows it is also created with `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`. It still inherits `vc`'s inheritable handles there, because std has no stable `inherit_handles` and `unsafe` is forbidden. So a caller that reads `vc`'s pipes to their end waits until `stop`; the `command:` action stops reading shortly after `vc` exits. `stop` sends SIGTERM (taskkill on Windows) and removes the pidfile. When no demo is running, it exits 0 and names the port.
- **`vc call <apiId>`** calls `Engine::call(&CallRequest { api, vars, keep, profiles, sets })`:
  - The engine layers the settings, but it builds no plan, so `beforeRun` and `beforeAll` never run.
  - It appends one run-owned `Call` action, which carries the api's own `expect`, to a copy of the program.
  - It runs that action through the executor with the `--var` values in the frame's saved scope.
  - It then runs the cleanups the action registered unless `--keep`, last first. A cleanup failure becomes a notice.
  - It records a history run of kind `adhoc`, with the api ID as its selector and one passed or failed instance.
  - It returns a `CallReport`: `exit` (0 or 1), `text` (status line, masked body, `✗` failure), `notices`, and `response`. `response` is the masked response value that `--save-as-test` reads. It also carries what the web UI's Client shows as tabs (D245 P1), each masked by the run's redactor, rules included, as the matching event would be: `exchange` (the last request as sent and its response, bodies whole; `None` when no response came back), `checks` (in the order they ran) and `saved` (`SavedValue`: the var, its template as written such as `${response.body.id}`, and the value). A saved value whose template reads a part of the response the redactor masks (a `redact.fields` field, a masked header) is masked whole, since it may be that part. The server's `CallResponse` sends the exchange with both bodies whole, whatever `history.bodies` says, as `results.v1.Exchange` with `body_truncated` false.

`vc watch` (D180, D190) takes `vc run`'s flags and prints what `vc run` prints:
  - Its port is `FileWatcher` in `vc-interfaces`. `watch(filter)` returns a channel of batches of saved `SourcePath`s that the filter lets through. `EngineBuilder` fills it with `NotifyWatcher` (`vc-adapter-system`, `notify` 8.2.1); `Engine::watch` passes it the filter discovery uses (the config's `paths` globs, else the default `SourceFilter`, read when the watch starts) and hands the channel on.
  - `NotifyWatcher` reports the definition files the filter lets through and the root `.env` and `.env.schema`. Other files, and the folders the filter skips (`.vibranium/`, `.git/`, `node_modules/`), are never reported, so a run's own reports and caches do not start another. Access events are not saves. A thread owns the OS watcher and sends a batch once the files have been quiet for 200 ms, in path order and each path once. A folder created or moved in during the burst is read when the batch goes out, because inotify starts watching a new folder only after reporting it, and a file saved into it before then has no event of its own.
  - The CLI runs the selection once, then waits for a batch or Ctrl-C. A batch sets `SelectRequest::saved`, which stands in for `--changed`: the selected tests in the saved files and those that call an api in one, or every selected test when the config, `.env` or `.env.schema` was saved. Batches that arrive during a run are merged into the next.
  - A run's error (a save that leaves the project with errors) is printed and the watch goes on. Ctrl-C interrupts a run in flight, as in `vc run`, and ends the watch with exit 130.
  - Saving a dataset, schema or hook file does not re-run anything yet: that needs the program to record which tests read each `$file:`.

### TUI (`apps/tui`)

`ratatui` with `crossterm`, one screen per tab (Run, Explore, History, Load, Import). It subscribes to the same event stream as the console reporter and uses `Edit`/`Check` for in-place editing; it never blocks the UI thread on I/O (the engine runs on the tokio runtime and sends redraw messages).

The shell keeps each one in flight on its own, as one can start while the other is still returning, so the end of one leaves the other in flight. Release and repeat events are ignored.
- **Screens.** Each tab is a `Screen` (`screen.rs`: `title`, `keys`, `shown() -> Option<Ask>` when the tab is chosen, `typing()` while it takes text, `press(key) -> Option<Ask>`, `take(&Update)`, `draw`), listed by `tabs::screens`. Each task is watched: one that panics (`JoinError::is_panic`) sends its ask's failure (`RunFailed`, `LoadFailed`, `HistoryFailed`, …) with the panic's message, so no tab waits on it, and aborting the watch aborts the task. A run's feed is passed on but for its `Done`: the driver sends the run's one end when `Engine::run` returns, `Run(Done(report))` or `RunFailed`, so a run that fails after its feed's `Done` never ends twice, the second taken by the shell for the end of a run started in between; the terminal loop `select!`s over keys and updates and redraws after each. ### MCP (`apps/mcp`)

`rmcp` server exposed as `vc mcp [--profile] [--set]` (stdio, started by the agent; M7) and at `/mcp` on the local web server (streamable HTTP, M9). `rmcp` is built with only `server` and `transport-io`; vc-mcp's `http` feature adds `transport-streamable-http-server`, and `VcServer::into_http` returns the service (rmcp's local session manager, its loopback `Host` default) and the call that cancels its sessions and streams so `vc ui` can stop. The tool schemas are written by hand (D197).

- `VcServer` (`server.rs`) implements `rmcp::ServerHandler`: `tools/list` comes from the `Tools` registry, `tools/call` looks the tool up by name (an unknown name is a JSON-RPC invalid-params error), refuses an argument the tool's input schema does not list (`McpError::UnknownArgument`, kind `arguments`, naming the ones it takes) and runs it. The agent is the name the client gives in `initialize` (`agent` when none).
- Each tool is a `Tool` (`name`, `description`, `schema`, `reads`, async `call(&Cx, &Args) -> Value`), one struct per tool, kept in `Tools::standard()`. `Cx` holds the engine, the agent and the `--profile`/`--set` layers `vc mcp` was started with: an agent cannot pick its own profile.
- The tools and the engine method each maps to:
  - reading (`read.rs`, `history.rs`): `list_definitions {kind?, ids?, tags?}` → `list`; `search {query}` → `list` over tests and apis, matching ID or name ignoring case; `get_definition {id}` → `explain`; `check {paths?}` → `check` with the `JsonRenderer` diagnostics and a summary; `query_history {limit?, run?}` → `history` or `stored`; `explain_failure {test, run?}` → the test's rows in `stored` beside `explain`.
  - acting (`act.rs`): `run_tests {ids?, tags?, grep?}` → `run` with `RunRequest.agent`; `call_api {api, vars?, keep?}` → `call` with `CallRequest.agent`; `write_definition {path, text}` → `write_definition`.
- Every result is structured content (a JSON object). An error is a tool result with `isError` set and `{kind, reason, help}`: `kind` is `refused` (the policy or a person said no), `arguments` (a bad argument) or `error`.
- Reading tools are logged to `agent_actions` by the server (`ok` or `failed: …`); the acting ones are gated and logged by the engine.
- `vc mcp` writes nothing but the protocol to stdout: an agent's run is quiet (`Setup.quiet`), so the console reporter prints nothing while the report files are still saved.

Every tool call goes through a policy check, done in the engine so that every route is covered. The check reads the active profile's `agents` rules, and it either:

- allows the call;
- refuses it with the rule that applied;
- or creates an approval request in `history.db` and waits for a decision (default timeout 10 minutes).

Decisions are made in the web UI's AI agents page, or with `vc approvals` / `vc approve <id>` in any terminal. Because both processes share `history.db`, a stdio agent and a separate `vc ui` see the same queue; `notify` on the database file wakes the waiting call. Every call is logged to `agent_actions`, with arguments redacted.

The engine reaches the queue and the log through two `vc-interfaces` ports. `vc_adapter_store::SqliteApprovals` implements both over `history.db` (its migration 2 holds the tables): each call opens its own connection, so every process on the project shares one queue, and a wait wakes on file events in the database's folder and looks again every second in case one was missed. A wait looks on one connection it keeps, because a connection opened per look makes and removes the WAL files each time, and their file events would wake it again at once. It makes its watcher on a blocking thread and looks every second meanwhile, since starting a watch can take seconds while the OS's file event service is busy (macOS FSEvents took 0.5 to 1.6s alone, and 20s in a full gates run). `vc_testkit::MemoryApprovals` implements both in memory and runs `approvals_suite` and `agent_action_writer_suite`:

- `Approvals`: `list(pending_only)`, `get(id)`, `create(ApprovalRequest)`, `decide(Decision)` (it gives a `Decided`: the status, and the methods an always-allow kept a rule for, which `vc approve --always` prints), `wait(id, timeout)` and `always_allowed(StandingRule)`.
  - An `ApprovalRequest` holds the agent, the tool, the profile, the methods that need approval, a one-line summary and the redacted arguments.
  - A `Decision` holds an `ApprovalId`, a `Verdict` (`Approve`, `AlwaysAllow` or `Deny`) and who decided.
  - `AlwaysAllow` stores a `StandingRule` for each profile, tool and method.
  - `wait` returns the `ApprovalStatus` once the request is decided, or `Expired` at the timeout. Dropping the future leaves the request pending.
- `AgentActionWriter::record(AgentAction)`: the agent, the tool, the profile, the redacted arguments, the result and who approved it.
- `AgentActionReader::recent(limit)`: the logged calls, newest first, each with when it was logged (`LoggedAction { at_ms, action }`), for the web UI's agents page through `Engine::agent_actions`. `AgentActionLog` is the writer and the reader together, the port `EngineBuilder::approvals` takes.

The engine redacts the arguments before it calls either port.

In the engine, `policy.rs` judges and `approvals.rs` gates:

- `policy_check(&AgentCall) -> Permission`.
  - An `AgentCall` holds the agent, the tool, `--profile`, the methods it would send, whether it runs tests or writes files, a summary and the arguments.
  - The pure `judge` takes each active profile's `AgentPolicy` and judges each field on its own; the most restrictive profile wins (`Refuse` < `Ask` < `Allow`):
    - `runs` needs `run`;
    - each method is allowed when it is in `call`, asks when it is in `approve`, and is refused otherwise;
    - `writes` follows `writeDefinitions`.
  - A project with no profile is judged under the default policy, which allows reads only.
  - `Permission::Ask { profile, methods, writes, code }` names the active profiles comma-joined. It becomes `Allow` when every method has a standing rule for those profiles and that tool, and nothing is written.
  - A call's reach also takes in the steps of each `type: flow` auth the calls it reaches use (the action's, the api's or the api file's), so the methods those steps send are judged too (a flow step is always a request). A call whose reach holds a `command:` or `function:` action (an agent's run, or a `call_api` whose cleanup chain reaches one) always asks, even when `run` and every method are allowed, and no standing rule skips that ask (D202). `AgentCall.code` and `Ask.code` name each such action as `<test or block>: command `<text>`` or `function `<file>#<export>``, and the approval's summary lists them. A person's run is not gated.
- `admit(&AgentCall, wait) -> Admission`: `Allowed { approved_by }` or `Refused { reason }`.
  - An `Ask` creates the request with the arguments redacted as a run's events are (the config's built-in masking, then its `redact.rules`), and waits (`APPROVAL_WAIT`, 10 minutes).
  - A denial or a wait that runs out is a refusal. A refusal is logged at once; the caller logs an allowed call with `record_agent_action(call, AgentOutcome)` when it ends.
  - An agent's `run_tests`, `call_api` or `write_definition` that fails before the gate (a bad selection, an unknown api, a project that does not compile, a path that is not a definition file) is still logged, as `failed: <reason>` (`before_gate`, D204).
- `approvals_list(pending_only)` and `approvals_decide(id, verdict)` back `vc approvals` and `vc approve`. The decider is the OS user (`USER`/`USERNAME`).
- `EngineBuilder::approvals(queue, log)` replaces the default `SqliteApprovals` over `.vibranium/history.db`. `vc_testkit::MemoryApprovals` is the in-memory pair: `answering(verdict)` decides each request at once.
- `call(&CallRequest)` with `agent: Some(name)` is gated as the tool `call_api` with the api's method and, unless `keep`, the methods of its cleanup chain (D178). A refusal is `EngineError::Refused { reason, help }` and nothing is sent.
- `run(&RunRequest)` with `agent: Some(name)` is gated once, before anything runs, as `run_tests` with `runs` and every method its plan can send (`agent_gate.rs`: `beforeRun`, each file's `beforeAll`, `beforeEach`, tests and their steps, `afterEach`, `afterAll`, `afterRun`, and each api's cleanups, each api and test walked once). The run is quiet (`Setup.quiet`): the console reporter prints nothing, so stdout stays free for the MCP protocol, while the report files are still saved. `RunReport.run` gives the run's number in the history, so an agent can look its results up.
- `write_definition(&WriteRequest { path, text, agent, profiles })` (`agent_write.rs`) writes one api, test or load file whole. The path must be one of those in the project, and never `vibranium.config.yaml`, which holds the rules that judge the agent. The text passes the compile guard first, so nothing that would break the project is put to a person; then `writeDefinitions` gates it.
- A gated call, run or write is logged once it ends, as `ok` or `failed`, with who approved it.

### Web server and web UI (`apps/server`, `web/`)

`vc ui` starts `axum` on `127.0.0.1:7420`, loopback only, through `vc_server::ServerBuilder` (`service`, `mcp`, `files`, `bind`); `vc-cli` composes it, serving `EngineApi` at `/api` and mounting the vc-mcp HTTP router at `/mcp` (`ServerBuilder::mcp`), both over the one engine `VcServer::engine()` shares, so the web UI and an agent see the same project, approvals and history. The process holds three secrets (`Token`, D239, D240), each 256 random bits as 43 base64url characters, compared in constant time (an HMAC verify under a per-process key) and never in a log, error, report or history file. The launch token is shown only in the `LaunchUrl` (`http://127.0.0.1:<port>/?token=…`, whose `Debug` is redacted) and works once: the first `GET /?token=…` that matches it flips an `AtomicBool` (`compare_exchange`, so no lock), sets the cookie `vc_token_<port>` to the session secret (`HttpOnly; SameSite=Strict; Path=/`, no `Secure` on plain-HTTP loopback; the port in the name keeps two `vc ui`s on one host apart) and answers 303 to `/`; a later one is 401 `this sign-in link was used already; use the open tab or restart vc ui`, and a `token` query anywhere else is 400. The agent token (`Server::mcp`, an `McpAccess` of the `/mcp` URL and the token, whose `Debug` hides the token) opens only `/mcp`, as `Authorization: Bearer`. Everything else, `/api` and the pages, takes only the cookie: a bearer there is 401 (`a bearer token works only on /mcp`), and so is the cookie on `/mcp`. A write the cookie signs in must carry `Origin` (403 without). `Host` must be `127.0.0.1:<port>` or `localhost:<port>` (403, against DNS rebinding), a write whose `Origin` is not that host is 403, and there is no CORS. Every response carries `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and a CSP the server builds itself: `default-src 'self'; script-src 'self' <hashes>; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`, where only the `'sha256-…'` sources of the embedded `index.html`'s CSP meta are copied in (the meta is found with attribute names in any case and double-quoted, single-quoted or unquoted values; with no page the header is `default-src 'self'; frame-ancestors 'none'`, and so it is when the page is not UTF-8 or no CSP meta lists a hash, but then `Server::csp_problem` says why and `vc ui` prints it as an error, since the page cannot load; the builder makes the header once and hands it to the guard, so every fallback is that one policy). A `GET` no route answers gets the file at that path, 404 for a missing path with an extension or under `/api/`, and `index.html` otherwise (the app's own routing). It serves:

- the embedded web UI, built with Vite and embedded with `rust-embed`;
- the engine API over the Connect protocol: one `vibranium.engine.v1.EngineService` whose RPCs are thin adapters over engine facade methods, served at `/api/vibranium.engine.v1.EngineService/<Method>`. Calls take binary protobuf bodies (`application/proto` unary, `application/connect+proto` streaming) or protobuf JSON ones (`application/json`, `application/connect+json`; the contracts' pbjson mapping, above, D254), a `Codec` the content type picks, and are answered in the same one; any other content type is 415 and errors are Connect error JSON (a method the service does not have is HTTP 404 with code `unimplemented`, as a Connect router answers a path it does not serve); the `Run` stream is server-streaming over HTTP/1.1, one `RunEvent` per `vc_model::Event`, a `RunPlanned` with the plan's instances right after `RunStarted`, and a final `RunReport`. Besides the project, definitions, check, run, files and approvals, it serves the M9b client and insights calls: `Call`, `SaveCallAsTest`, `Import` (the spec's text, previewed or written), `ListRuns`, `GetRun` and `Trends` over the history. There is no per-test history RPC, since the history reader has none. `GetProject` is `Engine::project_info` (the config's `project` or the folder's name, the profiles, the `default: true` ones). `ReadFile` and `WriteFile` are `Engine::read_file` and `Engine::save_file`: only `vibranium.config.yaml`, the root `.env.schema` (secret names, never values, for Settings; D247 lifts D227 for this one file) and api, test and load files outside hidden folders that discovery reads (the config's `paths` globs, read from the config alone, allow them and `SourceProvider::ignores` says no ignore file leaves them out; otherwise a refused edit, `invalid_argument` with help), so `.env`, `.env.*` other than the root `.env.schema`, a `.env.schema` in a folder, `.git/` and `.vibranium/` are never read or written through the UI, nor through a link: `FsSources` refuses a link whose target is outside the root, or in a hidden file or folder unless the link's own path is hidden and the target is a secrets schema (named `.env.schema` or `env.schema`, in any case) outside `.git/` and `.vibranium/`, so a `.env.schema` linked to `.config/env.schema` is read but one linked to `.env`, `.npmrc`, `.git/config` or `.vibranium/cache.db` is refused (`SourceError::OutsideRoot`), and `SourcePath` already refuses `..`, absolute paths, `\\` prefixes and drive letters; the digest is the file's BLAKE3 hash in hex; only a missing file opens as none (`NoFilesMatch`) or saves as new, while a file that is there but cannot be read or is not UTF-8 is an `EngineError::Sources` the editor shows, and a save whose file changed, appeared or was removed since it was opened writes nothing (`EngineError::Stale`, Connect `aborted`). Once written, the new digest comes back even when the check after it fails (`SavedFile::check` is a `Result`; `WriteFileResponse.check_error` says why), so the next save is not stale. `ExplainConfig` is `Engine::config_values`: `vc config explain` for many keys at once (none: every setting, then every var a layer sets), each layer a value and its source, the value in force first. Every value leaves masked by the run's redactor, told the declared secrets' names and loaded values, then `redact.rules` (D229, D232): a secret's value is `••••` wherever it appears, in the replaced layers too, a var named like a secret is masked whole, and so is a value that reads `${secret.*}`. When the secrets cannot be loaded, every value but the built-in ones is masked and a notice says so. A save is not guarded (D107): the editor keeps text with errors and gets the project's diagnostics back. It is a small handler layer over the `prost` types: `EngineApi` (one `Arc<Engine>`, plus `vc ui`'s `--profile` and `--set`, used when a request names no profile, and put before a request's sets) registers each module's RPCs on the `ConnectService` (`project_rpcs`, `history_rpcs`, `authoring_rpcs`, `run_stream`); a synchronous engine call runs on the blocking pool, and so do `Call`, `ExplainConfig`, `Import` and the run behind `Run`, whose async engine calls read and compile the project first and are driven there with `Handle::block_on`, so no compile holds an async worker (`Run`'s relay to the client stays async); and an `EngineError` leaves as its message and `help:` with a Connect code (`Stale` → `aborted`, `NoFilesMatch` → `not_found`, a refused edit, selection or config key → `invalid_argument`, the rest `internal`), never echoing the request. `Call` is the person's, as `vc call` is: the profiles' agent policy and the agent log do not apply (D241, superseding D233), since only the cookie reaches `/api`; `Connection` gives the Connect panel the `/mcp` URL and the agent token (`ConnectionResponse`), and is there only when MCP is mounted; `Import` only takes the pasted text (named `pasted`, so its relative `$ref`s resolve from the root) and never fetches a URL or path for the browser: a pasted spec's fetcher has no transport, so a `$ref` to a URL is refused, its api file has no `source` (there is no file to sync from; V2004 would flag one), and the import runs on the blocking pool; `Trends` with window 0 reads the last 30 runs, and `ListRuns` with limit 0 every run. `Run` relays the run's feed as it comes: `RunStarted` (from the server's clock), `RunPlanned`, each event with its own seq (a `TestFinished` carries the executor's `TestResult.duration`, from when the instance got its turn to its verdict, and its plan `instance`), a `Missed` notice with the seq of the last event it counts (the run numbers its events without gaps and the feed drops them in order, so it stands in for the gap and a client resuming after it continues where the run is), and the `RunReport` with the seq after the highest one the run produced, so neither shares an event's seq; a client that goes away interrupts the run once, and so does the server's shutdown. On Ctrl-C (or, when Ctrl-C cannot be listened for, never: `vc ui` warns and serves until the process ends) `Server::serve` tells every open stream to stop and gives the requests in flight 5 seconds before it returns without them.
- MCP over streamable HTTP at `/mcp`, behind the same guard: an agent sends `Authorization: Bearer <agent token>` and needs no `Origin`. Every tool call goes through the agent policy and log as `vc mcp`'s do (D241).

`vc ui [--port 7420] [--no-open] [--profile] [--set]` exists only in a vc-cli built with the `web-ui` feature (`vc-server/ui` embeds `web/build/` with `rust-embed`, `vc-mcp/http`), off by default; other builds exit 2 with `this vc was built without UI`. A build made before `web/build/` exists warns and serves only `/api` and `/mcp`. It prints two lines on stdout whether or not it opens a browser, `vc ui: <url>` (the one-time sign-in link) and `vc ui: mcp http://127.0.0.1:<port>/mcp token <agent token>`, never logs a secret, exits 2 when the port cannot be listened on, and exits 0 on Ctrl-C.

The web UI is TypeScript and Svelte (SvelteKit with its static adapter, so it builds to plain files the binary embeds), with clients generated by `@bufbuild/protobuf` and `@connectrpc/connect-web` (binary format, `useBinaryFormat: true`). Its editor, API client, Settings, run view and report share one component library styled per the design mockups.

The web app lives in `web/` (a pnpm package in the root workspace) and follows SvelteKit 3:

- **Config.** The adapter and kit options go in the `sveltekit({ … })` call in `web/vite.config.ts`, since Kit 3 has no `svelte.config.js`. `adapter-static` writes `web/build/` with `fallback: 'index.html'`, and the app sets `ssr = false`, so it is a single-page app. `vc ui` embeds `web/build/` and serves `index.html` for any unknown GET outside `/api` and `/mcp`.
- **Imports.** Kit 3 has no `$lib`. App code imports `#lib/*`, a subpath import in `web/package.json` that maps to `./src/lib/*`, and names the file with its extension (`#lib/nav.ts`). Links go through `resolve()` from `$app/paths` with `RouteId`-typed routes, as the `svelte/no-navigation-without-resolve` lint requires.
- **API client.** `protoc-gen-es` (`target=ts`) generates `web/src/lib/gen/` from the same `proto/` that `buf.gen.yaml` generates the Rust types from. The client uses a binary Connect transport at `/api` and sends credentials only to the same origin.
- **CSP.** `vc ui` sends `default-src 'self'`. The page has no inline styles. Kit's `csp: { mode: 'hash' }` puts the sha256 of the one inline bootstrap script into a CSP meta tag in `index.html`, and the server's header must allow that same hash.
- **Token.** `vc ui` prints `vc ui: http://127.0.0.1:7420/?token=<43 base64url chars>`, a launch link that works once (D240): its GET answers 303 to `/` and sets the HttpOnly, SameSite=Strict session cookie `vc_token_<port>`, and the page holds no token, since `/api` takes only that cookie (D239). The Playwright global setup copies `web/tests/fixtures/seed` to a temporary folder (the editor spec saves files), starts `vc ui --no-open` there, opens the launch link, saves the cookie as storage state, hands the used link and the printed `/mcp` URL and agent token to the specs (which check that the link is 401 when opened again, that the agent token is 401 on `/api` and shown in the Connect panel, and that an agent's `list_definitions` over `/mcp` with that token shows in the agent log while a call and a run from the browser do not), and in teardown stops `vc ui` and removes the copy. `pnpm dev` proxies `/api` to a running `vc ui --no-open` with vc ui's own origin: the first proxied request opens the launch link with `$VC_UI_TOKEN` (only the Vite side reads it), and the proxy keeps the session cookie in memory and sends it, never a Bearer header, on every `/api` request. Because the proxy presents vc ui's origin and that cookie, it answers only the page the dev server served (`fromDevPage` in `web/src/lib/dev/origin.ts`): `Host` must be a loopback name (not a LAN address under `vite --host`, nor a rebound DNS name) and `Origin` and `Sec-Fetch-Site`, at least one present, must say same-origin; anything else, a page on another localhost port included (cookies ignore ports), is 403 and never proxied, and the dev server sends no CORS headers (`server.cors: false`). It warns once when vc ui refuses the token, since a used link stays dead until vc ui restarts, and tries again on the next request when vc ui could not be reached.
- **Screens.** Each screen's state is a class in a `.svelte.ts` file (`RunSession`, `Catalog`, `AgentDesk`, `EditorSession`, `ClientSession`, `EffectiveSettings`, `Insights`) that takes a `Pick` of the engine client. Pages build them from the shared client, and components take them as props. One `RunSession` per app is shared through context, so any screen can start a run (there is no global Run button). Trees (Tests, Files, Apis) share `TreeFocus` and `GroupTree` (`#lib/tree/`): the WAI-ARIA tree keys with a roving tabindex over a two-level tree. The Tests query (`#lib/tests/catalog.ts`) filters in the page with `tag:`, `service:`, `file:` and `is:skipped|active`; `changed:<ref>` keeps the tests `ListDefinitions` returns for `Selection.changed`, as `vc run --changed` picks them, asked once per ref when typing pauses for 300 ms and again after the list reloads (a save may have changed the files); a ref that failed shows its reason only while it is in the query, and is asked again when the query changes. The "changed recently" view (D249) waits for `Selection.changed_within`. `#lib/results/` holds what the run view and the HTML report share: the status helpers, `RunProgress`, `CheckList`, `ExchangeView` (bodies load only when the exchange is opened) and `TestList`, a virtualised WAI-ARIA listbox (`aria-activedescendant`, arrow, page, Home and End keys) that renders only the rows in view. It imports no generated types. `#lib/ui/` holds the shared WAI-ARIA `Tabs` (roving tabindex, arrow keys, Home and End) and a native `<dialog>` `Dialog`. A screen whose RPCs came later talks to a small port interface (`ClientPort` in `#lib/client/port.ts`) served by `enginePort` from the engine client, so components and tests never see generated types.
- **Editor.** The editor keeps per open file the text as read or saved (`original`), the edited `text` and the `digest` it read. Save is `WriteFile` with that digest; `Aborted` means the file changed on disk, and the user reloads it or keeps their version (read the digest again, then write). `Engine::save_file` compares the digest when it reads the file, then writes through `SourceWriter::write_unchanged`: `FsSources` hashes the target first, so a refused save creates no folder, then stages the text in a hidden file beside the target (`.<name>.<pid>-<thread>-<nanos>.vc-tmp`), hashes the target again and renames the staged file over it only when the hash is still the one read (no file, for a new one); otherwise it removes the staged file and refuses (`SourceError::Changed`, which the engine turns into `Stale`). No lock is taken, since locks are allowed only in the token cache and the redactor, so a window remains: a change another writer makes between that second hash and the rename is overwritten and lost. Diagnostic spans map to string indices by 1-based line and character column; fix edits are UTF-8 byte offsets. The diff is an LCS line diff folded to three lines of context. Problems come from `Check` on open, from `Check` with an `overlay` of the unsaved text on every change (compiled in place of the files on disk; the compile cache is read but not saved), and from each `WriteFile`; when its check fails (`check_error`), the file is still saved, its digest is the new base, and Problems says why in place of the list. Save is blocked while errors remain (R44): it first checks the text it is about to write, since the last overlay check may be older than the last keystroke, and refuses on an error. A save updates only the buffer's `original` and `digest`, so keys typed while it is in flight stay unsaved, and an open drops any read, save result or keep-mine read that a later open overtook, so a late answer never changes the state of another file. A failed save, open or listing stays shown until one of those succeeds; a failed check of the typed text is shown only while no such failure is, and is cleared by the next good check, so a check never hides a save that went wrong, and a conflict stays until the user reloads or saves.
- **API client.** `ClientSession` calls an api by its full ID through `Call`, as `vc call` does, with a var row for each name in `Definition.vars`; the response panel reads `response_json` (status, headers, body). Save as test sends that same `response_json` and the chosen scalar body paths to `SaveCallAsTest`, which reads the values from it and does not call again (D176). Flow mode lists the tests whose `Definition.steps` is above 0 and runs one through the shared `RunSession`. Import HAR sends the file's text to `Import` with `kind: har`, first with `write: false` to show each `FileChange` as a diff and the importer's notes, then with `write: true`. A file must fit in one message (the server's 4 MiB cap, less 64 KiB for the rest of the request); a larger one is refused before it is read, with its size limit, and nothing stays chosen.
- **Settings.** `EffectiveSettings` explains every setting and `vars.<name>` under the profile picked (from `GetProject`) through `ExplainConfig`, the RPC over `Engine::config_values`, masked (D129). Each row shows the winning value with its layer, then each value it replaced. A value from a secret arrives as the redactor's mask (`••••`) and is shown as masked; the browser never receives it. Changes are made in `vibranium.config.yaml` in the editor; the mockups' form view over the config comes later. Its Secrets section (D247) lists the names the root `.env.schema` declares, with their `# @…` annotations and the comment lines just above them, never a value: `ReadFile` reads the file (none yet opens empty), names are read as the engine reads them (`vc_model::schema_names`: a `NAME=` line, with only a literal `export ` before it) and added (letters, digits and underscores, not starting with a digit, each once) or removed with their comment block, and Save writes it with `WriteFile` and the digest it was read with, so a file changed on disk since is not overwritten: a banner offers to reload it. The status line says how many problems the project's check found after the save. The browser may read `.env.schema` whole, since it is committed to git and so holds no secrets by definition.
- **Agents.** `AgentDesk` polls the pending approvals and the agent log, and loads `Connection` for the Connect panel, once it succeeds; while it fails for a reason that may pass (`unavailable`, `deadline_exceeded`, or a request that never reached the server) it tries again every 60 s (`linkRetryMs`), and an `unimplemented` or `not_found` answer stops it. Its HTTP tab shows the `/mcp` URL, the agent token and a ready-to-paste `.mcp.json` server entry; the token is masked (`••••`) until Show token is pressed, and Copy copies it unmasked. The token is kept only in that object's memory, never in storage, the URL or a log.
- **Insights.** `Insights` reads the last 10, 30 or 100 runs of kind `run` (`ListRuns`) and the per-test `Trends` over the same window through `InsightsPort` (`#lib/insights/port.ts`). It shows KPI tiles, a pass-rate bar per run (passed and flaky over the tests that ran; a run with blocked tests is marked and labelled), a run-duration bar per run, a table of the last 10 runs and the flakiest tests. Bars carry their reading as an `aria-label`, and the table is the chart's text view. Slowest APIs, coverage and quarantine actions come later.
- **Tests.** Unit and component tests sit next to the code as `*.test.ts` and run in vitest with jsdom and Testing Library, over an in-memory engine (`createRouterTransport` with fake handlers in `#lib/testing/engine.ts`), so they need no `vc ui`. The Playwright suite in `web/tests/` drives the real server and runs only with `VC_E2E=1`.

The self-hosted team server (`vc serve`) is the same binary with SQLite history (D253), accounts (OIDC) and run ingestion added; it is a later release.

Its defaults for sign-in, sessions, CI ingestion and binding are decided in D261: OIDC with PKCE, accounts keyed by issuer and subject with the role `viewer` or `admin`, sign-in closed until `serve.auth.allow` names domains or groups, hashed per-project ingestion tokens or GitHub Actions OIDC, and a loopback bind unless TLS or `--behind-proxy` is set.

### Plugins (`adapters/plugins`)

Third-party plugins are separate processes speaking JSON-RPC 2.0 over stdio, with LSP-style `Content-Length` framing; HTTP services and gRPC (for executors on the hot path) use the same method set.

- **Start-up.** The host starts a plugin on first use, checks its manifest (`vibranium-plugin.yaml`: kind, entry, permissions), and exchanges `initialize` (protocol version, capabilities, config schema).
- **Calls.** The host calls the methods for the plugin's kind: `auth/credentials`, `reporter/onEvent`, `importer/read`, `executor/send`, and so on.
- **Secrets.** Only the secrets the manifest lists are ever sent, and everything a plugin returns passes through the redactor.
- **Network and files.** Permissions are declared and shown at install, and enforced on the plugin process where the OS can (D254): Landlock on Linux, Seatbelt on macOS, declared only elsewhere. `confine.rs` turns the manifest into a `Policy` of real paths: the project folder is closed but for the install folder (read) and the data folder and the `files:` it names (read and write); a `files:` entry that is not a plain relative path staying inside the project, links resolved, keeps the plugin from starting (for a file not made yet, the real path of its nearest existing folder decides, and a link to nowhere fails). Outside the project the plugin reads anything and writes only the temporary folder (not when the project is inside it), `/dev/null` and `/dev/tty`. A plugin naming no `network:` host gets no network (on Linux no TCP bind or connect, Landlock's network rules needing kernel 6.7); one naming any reaches every host, since neither OS filters by host name. On Linux, with `unsafe_code = "forbid"` and so no `pre_exec`, the host starts `vc __vc-plugin-launcher <policy JSON> <program> <args>…` (`EngineBuilder::plugin_launcher`, which `vc` sets to its own path; `vc_engine::launch_plugin` is the first thing `main` calls): the launcher, still single-threaded, applies a Landlock ruleset (ABI 4, best effort, so an older kernel enforces what it can and one without Landlock nothing) with `no_new_privs`, then `exec`s the plugin, which keeps its pid and inherits the rules. Landlock only grants, so reading outside the project is granted entry by entry beside each folder on the way to the root, leaving out an entry whose real path leads into the project or to a folder holding it (a rule follows links). A `files:` path that does not exist when the plugin starts is granted as make-and-write (no read, no removal) beneath its nearest existing folder inside the project; never the project folder itself, so a file to be made at the project's top stays closed until it exists. On macOS the host runs the entry under `/usr/bin/sandbox-exec -p <profile>`: allow by default, deny every write but the policy's write paths, deny reading file contents in the project but the policy's paths (later rules win), and deny `network*` without a host. The host builds the policy off the runtime's workers. Before it starts a confined plugin, it checks that confinement can work here (`Confiner::ready`, off the runtime's workers, asked once by the one `Confiner` the engine shares with every host): on Linux that there is a launcher and the kernel has Landlock (a ruleset made with `CompatLevel::HardRequirement` and dropped), on macOS that `sandbox-exec` can start a program (a `vc` that is itself sandboxed cannot). When it cannot (D260), Linux stays best effort: the plugin runs unconfined. macOS fails closed: the plugin does not start, with V5119, which says why and names the opt-out, unless the user allows it to run unconfined. Only the user can: `plugins.allowUnconfined: true` in the user config (`UserConfig::allows_unconfined_plugins`, a preference and not a setting), or `VIB_PLUGINS_ALLOW_UNCONFINED=1` in the process environment (`Engine::unconfined_allowed`, which hands it to `StdioPluginHost::allow_unconfined`). It is never read from `vibranium.config.yaml` (where `plugins` is a list), a profile or `.env`, so a cloned project cannot switch confinement off. A plugin that runs unconfined, on any OS, sends `plugin `<id>` runs unconfined: <why>` to the run's `told` channel as it starts, once a run, and the line becomes a run notice in the report. Library users who build their own engine get Seatbelt on macOS, and Landlock only when they set a launcher.
- **Failures.** A plugin that exceeds its deadline or crashes fails only the work that used it.
- **Host.** `StdioPluginHost` in `vc-adapter-plugins` starts the entry (never through a shell) in the plugin's folder with only a fixed set of environment variables (`PATH`, `HOME`, …) plus `VIB_PLUGIN_DATA` when it has a data folder, on the first call, and sends `initialize` with `protocolVersion`, `plugin` and the literal `config`. It answers the plugin's `secrets/get` only for secrets both the manifest and the lock name (−32001 otherwise), and `PluginHost::shutdown` (which `Hosts::shutdown` calls for every plugin once `vc run` or `vc load` has closed its reporters and sent its alerts) sends `shutdown`, closes its stdin and waits for the process to exit, each step given one second before it is killed (GRACE), so the plugin hears both before `vc` exits; dropping the host instead (as `vc call` does) starts the same steps without waiting for them. Its stderr follows `PluginStderr`, chosen with `EngineBuilder::plugin_stderr`: `Inherit` (the default, for `vc`) passes it through; `Log` (for `vc tui`, whose raw-mode screen it would garble) copies it to `.vibranium/plugin-logs/<id>/stderr.log` (`StdioPluginHost::stderr_log`), up to 1 MiB a start with the rest drained and dropped. That folder is the host's and the plugin is never told of it: the log never goes in the plugin-writable data folder, where a planted link could make the host write any of the user's files. Before the spawn the log before is renamed `stderr.log.1`; when that fails it is removed instead, and the new log's first line says so. The new one is opened with `create_new`, which never follows a link (on Windows it is opened with `FILE_FLAG_OPEN_REPARSE_POINT`, so the handle is a link itself, and a reparse point is refused); Every folder from the project root on the way to the log (`.vibranium`, `plugin-logs`, `<id>`) is made with `create_dir` and, when something is already there (another host may have just made it), checked with `symlink_metadata` (`owned::folder`, the walk the data folder takes too), as the plugin starts and never before (on a blocking task with the data folder's walk, `spawn_blocking`, as no runtime worker may wait on the file system), so a plugin the run never starts gets no folder: a link among them is refused, so neither rotation nor removal nor creation ever lands in its target. When a folder is refused or the log cannot be made, stderr is discarded and the host sends why (`StdioPluginHost::told`, a `broadcast` channel the run's `Hosts` holds); `vc run` adds those lines to its notices once its reporters finish. Its session task reads the plugin's messages into a bounded queue (1024) without ever waiting on it, so a plugin writing while the host writes never deadlocks; a malformed message, a write the plugin does not read within the call's deadline, more than 1023 unread messages or the process exiting stops the session (killing the process), fails the calls in flight, and makes every later call fail at once. `docs/design/plugin-protocol.md` is the wire contract.
- **Run wiring.** `Engine::plugin_hosts` (`plugin_hosts.rs`) builds a `Hosts` once per run (and per call, load and cache cleanup), shared by the reporters and the action context: a host for each `plugins:` item that is installed, approved and asks for no more than its lock entry, and a reason for each other one, which becomes one run notice (`Hosts::notices` leaves out the reporter plugins `reports.formats` names, since the reporting names each of those with `; its report is not written`). A lock or manifest that cannot be read makes only the plugins it concerns unusable. Each host gets a data folder, `.vibranium/plugin-data/<id>/` (`VIB_PLUGIN_DATA`, made as it starts by the same walk as its log folder, so a `.vibranium` or `plugin-data` that is a link keeps the plugin from starting), since its install folder must not change. A `blake3-` lock integrity is checked against the installed folder (`PluginStore::integrity`) by `plugin_intact.rs` on the host's first call, in `spawn_blocking`, so a run hashes only the plugins it uses; files that changed since fail that host's calls with V5118 (`PluginError::Start`). An npm `sha512-` integrity is the tarball's, so it is checked only when `vc plugin add` fetches it. A `${…}` in `plugins[].config` makes the plugin unusable (literal values only, so no secret reaches it past the lock). Auth reads only `auth` hosts and reporting only `reporter` hosts, and a host starts lazily, so each plugin is still one process per run (G8).
- **Reporter plugins.** A `reports.formats` name that is a configured plugin's ID (checked at link time; any other unknown name is V2302) gets a `PluginReporter` (`vc-adapter-reporters`): each event goes to `reporter/onEvent` in the JSON reporter's shape through a bounded queue (1024) that a task of its own drains, never awaited by the event pump: a plugin that falls a whole queue behind is dropped with one notice and writes no report, and `reporter/finish`, sent once the queue is drained, gets the summary and answers with `files` the host writes into the run's report folder, refusing a name outside it. A failing reporter plugin is dropped with a notice; the run's other reports and its status are unaffected.
- **Auth plugins.** `PluginAuth` (`vc-adapter-auth`) is the `plugin` auth type: it calls `auth/credentials` with the auth ID and its `config`, and turns the answer's `headers`, `query`, `cookies` and `expiresIn` into `Credentials`. Any failure is `AuthError::Plugin` (V5114); an auth naming a plugin the run cannot use fails with that plugin's reason (`PluginAuth::unusable`).
- **Port.** `PluginHost` in `vc-interfaces` is one running plugin: `manifest()` and `call(method, params, deadline)`, with `INITIALIZE_DEADLINE` (5 s) and `CALL_DEADLINE` (30 s). A `PluginError` is V5118 and keeps its JSON-RPC code (`PERMISSION_DENIED` −32001, `DEADLINE_PASSED` −32002). `PluginPermissions::beyond` lists what a manifest asks for past what `vibranium.lock` granted. `FakePlugin` in `vc-testkit` answers from scripts and keeps only the declared secrets; every host runs `plugin_host_suite`.
- **Install and lock.** `PluginStore` in `vc-interfaces` fetches a source into `.vibranium/plugins/.staged/` (`npm pack` and `tar` for `npm:`, a copy for `path:`), installs it to `.vibranium/plugins/<id>/` (a copy keeps each file's permissions, so an executable entry stays executable), hashes an installed folder (`integrity`: BLAKE3 over the sorted files, skipping `.git`, `.vibranium` and `__pycache__`), discards or uninstalls it, and reads `vibranium.lock` and the installed manifests; `FsPluginStore` in `vc-adapter-plugins` is the one implementation; a failed `npm pack` is reported with npm's error code and first line that says why (`npm.rs`: the `error` of its `--json` report, else its `npm error` lines, skipping `syscall`, `errno` and the log pointer). The engine parses the manifest and the lock (`plugin_manifest`, `plugin_lock`) and writes the config item and the lock as `Changes`, the config through the compile guard (`Engine::plugin_fetch`, `plugin_approve`, `plugin_decline`, `plugin_list`, `plugin_remove`). `plugin_list` gives a ready plugin the state a run would find: `Changed` when its installed files no longer hash to a `blake3-` integrity in the lock (`plugin_intact::unchanged`, the V5118 check), `NoEntry` when `vc_adapter_plugins::entry_found` cannot find its `entry.command` (a file in its folder, a path to a file, or a program on `PATH`, as `StdioPluginHost` starts it); `plugin_fetch` puts the same missing-entry reason in `PluginOffer::warnings`.

### Performance budgets

Budgets are enforced in two ways (D120): instruction-count benches (`gungraun`) run on every PR and fail at a regression over 5%; wall-clock benches (`criterion`) run nightly against the targets below and open an issue on a breach.

The compile benches check a 1,000-file project from `vc_testkit::generate_project(seed, files)`: a seeded, clock-free generator whose config, api and test files use vars, profiles, pipes, matchers, CEL, steps, loops, lifecycle blocks and cross-file references, and which `vc check` reports nothing on. Each bench runs `Engine::check` over in-memory sources three ways: cold (empty compile cache), warm (the cache from the same files) and changed (that cache, with the last file edited).

| Bench | Tool | Where | Runs |
| --- | --- | --- | --- |
| `compile_instructions` | `gungraun`, Linux only (valgrind) | `crates/engine/benches` | `ci.yml` job `bench-instructions` on every PR, against a baseline from the base branch; with no baseline it passes with a notice |
| `compile_wall` (`compile/cold_1000`, `warm_1000`, `changed_1000`) | `criterion` | `crates/engine/benches` | `mise run bench`; nightly |
| `request_overhead` (`request/overhead`: per request outside the network) | `criterion` | `crates/engine/benches` | `mise run bench`; nightly |
| `startup` (`startup/version`: `vc --version`) | `criterion` | `crates/apps/cli/benches` | `mise run bench`; nightly |
| `load_5k` (`load/5k_users`: tool CPU per second of a 5,000-user run), Unix only | `criterion` | `crates/engine/benches` | `mise run bench`; nightly |

`request_overhead` runs one test whose `call` step repeats 500 and then 1,000 times, one at a time, against the in-process mock server. The transport is wrapped to time each send. The bench takes the run's time less its transport time, and divides the difference between the two runs by 500, so the run's fixed cost (compile, plan, reports) cancels out.

`load_5k` runs a scenario of 5,000 users, each sending one `POST /echo` and then thinking for 1 s, for a 1 s ramp and 15 s at full load. The mock server runs in a child process (the bench binary started again), so the process CPU clock (`clock_gettime(CLOCK_PROCESS_CPUTIME_ID)`) counts only the tool. A sample is the tool's CPU time divided by the run's wall time, so its median in ms is thousandths of a core and the budget of 70% of 8 cores is 5,600 ms. A run that exits non-zero or averages under 4,500 iterations a second fails the bench, because a tool that falls behind its users would look cheap. The bench raises the soft open-file limit to 10,240 first.

`scripts/bench-budgets.sh` (`mise run bench:budgets`) holds the criterion medians to the targets below; the nightly `budgets` job runs it and opens an issue, or comments on the open one, on a breach.

| Budget | Target |
| --- | --- |
| Compile and link 1,000 definition files | under 500 ms cold, under 100 ms warm (measured with the postcard cache and the M1 lints: 168 ms cold, 71 ms warm, 82 ms with one file changed) |
| Overhead per request outside the network (render, checks, events) | under 50 µs at p50 |
| Hook call | under 50 µs at p50 for a `beforeRequest` hook |
| History write | 10,000 test results committed in under 1 s |
| HTML report for 10,000 tests | first paint under 1 s, any test opened in under 100 ms |
| Load | 5,000 virtual users on 8 cores at under 70% tool CPU |
| Binary size | under 30 MB per platform |
| Start-up | `vc --version` under 20 ms; `vc check` on the sample under 100 ms |

### Build and release

- **Toolchain.** Rust 1.99 pinned through rustup and `rust-toolchain.toml` (D98); other tools pinned in `mise.toml` (D99); `cargo build --release` with thin LTO, 4 codegen units and debug info stripped; symbol names are kept so the exit-70 debug bundle has readable backtraces (D127). The web UI and report front ends are built with Vite first and embedded.
- **Targets.** macOS (arm64, x64), Linux (x64, arm64, statically linked with musl), Windows (x64).
- **Distribution** through `cargo-dist`: GitHub releases with checksums and build provenance, a one-line installer (`curl -fsSL https://…/install.sh | sh` and a PowerShell equivalent), a Homebrew tap, a Docker image, and an npm package `@vibranium/cli` that downloads the right binary (for JavaScript projects that want it in `devDependencies`).
- **Command names.** `vc-cli` builds both `vc` and `vibranium`; `vibranium` runs the `vc` in the folder of its real file (after symlinks, never from `PATH`) with the same arguments and exits with its code, or exits 2 with the install command when that `vc` is missing. The installer ships both with `vc-demo`, and warns if another `vc` is already on `PATH`. `vc completion` registers both names, and its hook asks the name that was typed (fish gets separate `vibranium` lines that ask `vibranium`, and bash expands a typed `~/`).
- **CI.** Every PR runs `gates.sh` and the instruction-count budgets on Ubuntu, and builds and runs the tests (including e2e) on macOS and Windows; a nightly job runs full mutation testing and the wall-clock budgets (D119, D120). PRs merge into `master` (D97, D118); releases are cut from tags by `cargo-dist`'s workflow.
